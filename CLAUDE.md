# pascal-amqp-faa — contexto do projeto

Cliente AMQP 0-9-1 dual-compiler (**FPC/Lazarus + Delphi**) numa única codebase, MIT. É o porte multiplataforma da `../delphi-amqp-faa` (mesmo autor); aquela permanece como projeto à parte, Delphi/Windows-only. A arquitetura, os invariantes de concorrência e as lições de protocolo estão documentados no `CLAUDE.md` de lá e valem aqui integralmente.

> **Histórico detalhado do submódulo broker** (bugs achados workstream a workstream, mutações de teste, contagens de suíte rodada a rodada, validações de plataforma) está em `docs/broker-worklog.md` — não é carregado automaticamente; leia sob demanda. Este arquivo guarda só o estado atual, as decisões travadas e as regras vivas.

## Regra inegociável: proveniência do código (herdada da lib original)

**Nunca copiar, adaptar ou se basear em código-fonte de bibliotecas Pascal/Delphi AMQP de terceiros sem licença permissiva clara.** Este projeto deriva exclusivamente da `delphi-amqp-faa` (MIT, mesmo autor) e da especificação AMQP 0-9-1. Consultas a outras implementações são permitidas apenas como conhecimento de protocolo, nunca como fonte a transcrever. O submódulo broker (server) segue a mesma regra: deriva só da spec e do próprio cliente desta lib. O RabbitMQ (Erlang/MPL) é consultado só como conhecimento de protocolo.

## Regras da codebase dual (Delphi + FPC 3.2.2)

Toda unit começa com `{$I amqp.inc}` (ativa `{$MODE DELPHI}` no FPC e define `AMQP_WINDOWS`). O que NÃO usar, e o que usar no lugar:

| Proibido (não existe no FPC 3.2) | Usar |
|---|---|
| `reference to procedure` / métodos anônimos / `TThread.CreateAnonymousThread` | `procedure ... of object`; work items (`TAMQPWorkItem`) para capturar estado; threads nomeadas |
| `System.Threading` (`TTask.Run`) | `AmqpPool.Queue(...)` de `AMQP.Threading` |
| `System.TMonitor` (Enter/Wait/PulseAll) | `TAMQPMonitor` de `AMQP.Threading` |
| `TInterlocked.*` / `AtomicXxx` direto | `AmqpAtomicInc/Dec/Get/Read64/Write64` de `AMQP.Threading` |
| `TThread.GetTickCount64` | `AmqpTickMs` |
| `GetLastOSError` (só existe no FPC; o Delphi tem `RaiseLastOSError`, que **levanta** em vez de devolver) | `AmqpLastOsError` de `AMQP.Server.Wal` |
| `System.Net.Socket` direto | `TAMQPTcpSocket` de `AMQP.Transport` |
| `TEncoding.UTF8.GetBytes/GetString` | `AmqpUtf8Encode/Decode` de `AMQP.Wire` (no FPC respeitam o codepage dinâmico) |
| uses com namespace (`System.SysUtils`) | nome curto (`SysUtils`); no Delphi resolve via unit scope names `System;Winapi` |
| inline `var` em bloco | declarar no `var` da rotina |
| `TStringHelper` (`.Split` etc.) | rotinas manuais (`Pos`/`Copy`) |
| `TArray.Sort<T>` | ordenação manual (não existe no Generics.Collections do FPC) |

Gotchas de FPC já encontrados no porte:

- `TValue.From<TArray<TValue>>(x)` não parseia (o `>>` vira `shr` e nem com espaço passa) → usar o alias `TAMQPValueArray` (AMQP.Wire). `TValue.AsType<T>` não existe → `GetArrayLength/GetArrayElement`.
- `Boolean` tem `Kind = tkBool` no FPC (não `tkEnumeration`); `AnsiString` é `tkAString` — os `case AValue.Kind` do codec tratam os dois via `{$IFDEF FPC}`.
- Enum anônimo inline como campo de classe não compila → tipo nomeado (`TAMQPAsmState`).
- `PWideChar(string)` não existe (string é Ansi) → campos que vão para APIs wide são `UnicodeString` (ver `AMQP.Transport.Tls.FTargetName`).
- `Format('%x')` com `LongInt` negativo imprime 16 dígitos → passar `Cardinal(valor)`.
- Fontes em UTF-8 **com BOM**: Delphi exige o BOM para ler UTF-8; o FPC com BOM trata literais como UTF-8 corretamente. Manter o BOM ao criar units novas (inclusive `.md` gerados por script — um `Write`/redirecionamento que não preserva BOM quebra silenciosamente a contagem de headings de scripts de verificação).
- FPC 3.2.2 trava com **erro interno** (`Internal error 2015071704` / `200510032`) em duas combinações específicas envolvendo `TValue`: (1) encadear `.Put(...)` de `TAMQPFieldTable` terminando num `TValue.From<T>(literal)` inline — separar em chamadas `.Put()` distintas resolve; (2) `Tabela['chave'].AsString` / `.AsExtended` / `.AsObject` encadeado direto no indexador — atribuir o resultado do indexador a uma variável `TValue` local antes de chamar o accessor resolve (`.AsBoolean`/`.AsInteger`/`.AsInt64` encadeados direto não têm esse problema).
- Apps console FPC puro (fora do Lazarus/LCL) têm `DefaultSystemCodePage` diferente de UTF-8 por padrão — strings acentuadas literais saem transcodificadas errado ao passar por `AmqpUtf8Encode`. Chamar `SetMultiByteConversionCodePage(CP_UTF8)` no início do `program` resolve.
- `TInterlocked` (System.SyncObjs) não existe no FPC → usar `AmqpAtomicInc/Dec/Get/Set/CompareExchange` de `AMQP.Threading`.
- **O runner FPCUnit chama `SetMultiByteConversionCodePage(CP_UTF8)`, e isso pode CEGAR um teste.** Com `DefaultSystemCodePage = 65001`, `AmqpUtf8Encode` de uma string montada byte a byte é passthrough — então um codec que (erradamente) passe binário por string parece correto **dentro da suíte**. Numa app console FPC pura, que nasce com codepage 1252, os mesmos 256 bytes viram 401. Teste que depende de codificação deve **fixar o codepage que quer testar** e restaurar no `finally`, em vez de herdar o do runner.
- **`TThread.WaitFor` NÃO é idempotente no FPC/Unix.** No Windows é `WaitForSingleObject`, que num handle já sinalizado volta na hora, quantas vezes for. No Linux é `pthread_join` **incondicional** (`rtl/unix/tthread.inc` → `WaitForThreadTerminate`), e chamar duas vezes é comportamento indefinido — se o `pthread_t` tiver sido reciclado por uma thread nova, o segundo join espera pela thread **errada**, para sempre. Ou **anule a referência logo após o join** (`WaitFor; FreeAndNil(FThread)` — é o que o cliente já faz), ou **guarde o join com lock + flag** quando o objeto sobrevive ao join (é o que `TAMQPFrameWriter.Stop` e `TAMQPServerConnection.WaitFor` fazem). Um comentário dizendo "seguro chamar mais de uma vez" num join é verdade só no Windows.
- **A convenção de chamada do `IInterface` depende da PLATAFORMA no FPC**: `stdcall` no Windows, `cdecl` no Unix. Uma classe que reimplementa `_AddRef`/`_Release` (para refcount no-op, por exemplo) declarando `stdcall` fixo **compila no Windows e falha no Linux** com `No matching implementation for interface method "_AddRef:LongInt; CDecl"`. Usar `{$IFDEF AMQP_WINDOWS}stdcall{$ELSE}cdecl{$ENDIF}`. Foi o que manteve o submódulo broker sem compilar no Linux da Fase 2 até a Fase 4.
- **Gerar os dois espelhos a partir de um texto só é certo para o CORPO do teste e errado para a RTL.** Manter as asserções e o fluxo idênticos é o objetivo do espelho (as funções `Checa*` das suítes novas existem para isso); mas todo bloco que chama a RTL — temp dir, apagar arquivo, qualificar unit — **tem de ser escrito por dialeto**. Três defeitos desta causa custaram três round-trips pela IDE numa rodada só; as checagens [4] e [6] do `verifica_espelhos.py` existem por causa disso.
- **No Delphi, o RTTI padrão só publica métodos `public` e `published`** — um atributo do DUnitX (`[Setup]`, `[TearDown]`, `[Test]`) numa seção `private`/`protected` **compila e nunca é encontrado**. Numa fixture-base isso faz o `Setup` não rodar e a fixture inteira morrer em access violation lendo campo nil; num `[Test]`, ele some da suíte em silêncio. Não há aviso do lado FPCUnit (lá a visibilidade que importa é `published`). A checagem [5] do `verifica_espelhos.py` pega.
- **Com a unit `Windows` no `uses`, a `Winapi.Windows` sombreia nomes da `System.SysUtils` e o erro só aparece no dcc32.** Medidos: `FindClose` (a versão do Windows toma `THandle`, a da SysUtils toma `var TSearchRec` — dá `E2010 Incompatible types`) e `DeleteFile`. `FindFirst`/`FindNext` **não** colidem (lá são `FindFirstFile`/`FindNextFile`). Qualificar: `SysUtils.FindClose(...)`.
- **`DateTimeToUnix(LocalTimeToUniversal(Now), False)` converte DUAS vezes** (o `False` diz "a entrada é local, converta"), e o erro é **invisível numa máquina com fuso UTC** — todo container e a maioria dos servidores Linux, onde `LocalTimeToUniversal` é no-op e a conta dupla soma zero. Medido: +4 h nesta máquina, 0 no container. Para epoch em ms use `Round((utc - UnixDateDelta) * 86400000)`, que não depende da semântica do flag (que difere entre os compiladores) nem de a RTL zerar os ms antes do `Round` interno.
- `TTestCase.AssertException` do FPCUnit exige a classe **exata** da exceção (não aceita subclasse), diferente do `Assert.WillRaise(proc, EAlgumaClasse)` do DUnitX (aceita `is`/herança) e do `Assert.WillRaise(proc)` sem classe (qualquer exceção). Para "qualquer exceção" no FPCUnit: `try/except` manual com flag booleana + `AssertTrue` (não `Fail()` dentro do próprio `try`, que seria capturado pelo `except`).
- `System.Threading` (`TParallel.For`) não existe no FPC — usar `AmqpPool.Queue(TAMQPWorkItem)`. Cuidado ao compartilhar arrays entre o item de trabalho e o chamador: um parâmetro de construtor tipado como `array of T` é *open array* (copia os elementos) — usar um tipo nomeado de dynamic array como parâmetro para de fato compartilhar o mesmo buffer.
- Citar um diretivo tipo `{$IFDEF FPC}` dentro de um comentário de prosa `{ ... }` quebra a compilação: o `}` do texto citado fecha o comentário mais cedo. Escrever "condicional" ou similar em vez do `{$...}` literal ao documentar isso em comentários.
- `TThread.Queue`/`.Synchronize` do FPC só têm o overload `TThreadMethod = procedure of object` (sem parâmetros) — sem overload de closure anônima. Toda chamada `TThread.Queue(nil, procedure ... end)` precisa virar um método nomeado; com várias threads chamando concorrentemente, usar um objeto de "marshal" descartável por chamada (dados + `procedure Execute; begin Form.Metodo(...); Free; end;`), não um campo compartilhado na form.
- `System.TMonitor` não existe no FPC → `TCriticalSection` (`SyncObjs`).
- **`TypeInfo(TArray<TValue>)` inline não casa com `TAMQPValueArray`** (FPC 3.2): a especialização genérica escrita inline numa unit é distinta do alias de `AMQP.Wire` que o decoder realmente produz — comparar `TValue.TypeInfo` com a forma inline dá False em silêncio. Usar o alias `TAMQPValueArray`, ou (melhor) não testar o tipo do array e chamar `AmqpUnwrapValue` em todo elemento.
- **`TValue.GetArrayElement` sobre `TArray<TValue>` devolve o elemento re-embrulhado no FPC**: um `TValue` de `Kind=tkRecord` contendo o `TValue` interno — `IsObject`/`IsArray`/`As*` falham no embrulho (o Delphi colapsa TValue-em-TValue; o FPC 3.2 não). Correção: `AmqpUnwrapValue` (AMQP.Wire), idempotente e no-op no Delphi — usar após **todo** `GetArrayElement` de um array de field-values.
- **FPC descarta `TThread.Queue(nil, ...)` postado por uma thread que morre antes de a main thread bombear a fila**: `TThread.Destroy` chama `RemoveQueuedEvents(Self)`, que casa pelo `ThreadID` do postador mesmo com `AThread=nil`. No Delphi não afeta (casa só pelo campo `Thread`, que fica `nil`). Morde em callbacks que rodam numa thread que termina logo em seguida (ex.: reconexão). Correção: saltar por um worker do `AmqpPool` (threads persistentes) com um `TAMQPWorkItem` que faz o `TThread.Queue` de lá.
- `ReportMemoryLeaksOnShutdown` (global do `System`) não existe no FPC → `{$IFNDEF FPC}` em volta da atribuição no `.dpr`.
- LCL não tem `Font.Charset` nem `TForm.DesignSize` do jeito que o `.dfm` do Delphi grava — omitir essas linhas ao escrever o `.lfm` equivalente.
- `uses Windows, Messages` nos samples GUI não compila fora do Windows → camada de emulação da LCL: `LCLIntf` (`GetScrollInfo`/`SendMessage`), `LCLType` (`TScrollInfo`, `SIF_ALL`, `SB_VERT`, `SB_BOTTOM`) e `LMessages` (`LM_VSCROLL`, mesmo valor `$0115` do `WM_VSCROLL`).
- FPC/Linux sem `cthreads` como primeira unit do `program`: `SyncObjs`/eventos falham em runtime com `ESyncObjectException`. Vale pra qualquer programa novo que use a lib no Linux.
- Os runners FPCUnit não devem importar `Forms`/`Interfaces`/`GuiTestRunner` incondicionalmente (força link contra LCL mesmo em modo console) — mover para `{$IFDEF MSWINDOWS}`; fora do Windows sempre em modo console.
- **SIGPIPE no Linux**: `send()` num socket já encerrado mata o processo (exit 141) em vez de devolver erro. Fix: `TAMQPTcpSocket.Send` usa `fpsend(..., MSG_NOSIGNAL)` sob FPC+Unix quando a unit `sockets` declara a flag (guarda `Declared(MSG_NOSIGNAL)`).

## Peças novas em relação à lib original

- `AMQP.Threading`: atomics, `AmqpTickMs`, `TAMQPMonitor` (condvar por gerações de eventos — sem wakeups perdidos; waiters re-checam a condição em loop) e `TAMQPThreadPool` (cresce sob demanda até `max(16, 4×núcleos)`; workers persistentes; `AmqpPool` é o singleton global).
- `AMQP.Transport`: `TAMQPTcpSocket` (Delphi: `System.Net.Socket`; FPC: `ssockets.TInetSocket` + `fpshutdown` para desbloquear a thread de leitura sem corrida de FD).
- Work items em `AMQP.Connection` (implementation): `TAMQPDeliveryWork`, `TAMQPReturnWork`, `TAMQPConfirmWork`, `TAMQPBlockedWork`, `TAMQPUnblockedWork`, `TAMQPReconnectThread` — substituem os closures de `TTask.Run`; o contador in-flight é decrementado no `finally` do `Execute`.
- TLS com dois backends e mesma API (`EAMQPTls` vive em `AMQP.Transport` para existir em toda plataforma):
  - `AMQP.Transport.Tls`: SChannel, compila nos dois compiladores mas **só no Windows** (`AMQP_WINDOWS`, automático).
  - `AMQP.Transport.OpenSSL`: OpenSSL, qualquer plataforma, **opt-in** via `-dAMQP_OPENSSL` (tem precedência sobre SChannel se ambos definidos). Bindings próprios (~26 símbolos com assinatura idêntica em 1.1.1 e 3.x), carregados dinamicamente na 1ª conexão TLS com lista de sonames (`libssl.so.3` → `.1.1`; DLLs `libssl-3-x64` etc. no Windows). O engine SSL trabalha sobre **par de BIOs de memória** (nunca `SSL_set_fd`): preserva o desbloqueio da thread de leitura via close do socket E permite proteger o objeto `SSL` (que não aceita read/write concorrentes) com um `TCriticalSection` interno nunca segurado durante I/O de socket. Sem `AMQP_OPENSSL` fora do Windows, `UseTls` levanta a mesma exceção clara de antes.

## Submódulo broker (server) — Fases 1, 2 e 3 completas (branch `feat/broker`)

Units `AMQP.Server.*` em `src\server\`, pacote separado `pascal_amqp_faa_server.lpk` que depende do pacote cliente — quem só usa o cliente não linka nada de server. É a "outra ponta": uma lib para **criar um broker AMQP 0-9-1 dentro de uma app Delphi/FPC**.

**Não-objetivos (todas as fases):** cluster, HTTP management API, federation/shovel, AMQP 1.0, STOMP/MQTT, quorum queues, streams, persistência/recovery (isso é a Fase 4, modelo já pré-decidido — ver seção abaixo), permissões por vhost.

**Histórico WS-a-WS de cada fase** (bugs, mutações, contagens de teste): `docs/broker-worklog.md`.

### Arquitetura travada (vale para as três fases)

- **Modelo de execução: thread-por-conexão, I/O bloqueante** (reusa `TAMQPTcpSocket`, `TAMQPMonitor`, `AmqpPool`, o truque `fpshutdown`/`Close` para desbloquear read pendente). Event loop (IOCP/epoll/kqueue) rejeitado — 3 backends, nenhum existe nas units compartilhadas, e o alvo é dezenas–centenas de conexões.
- **Escrita: 1 objeto writer por conexão com fila outbound limitada + 1 thread escritora** (backpressure natural = flow control TCP). `Connection.PostFrames(array of TAMQPFrame)` enfileira method+header+body sob um único lock (senão o cliente vê UNEXPECTED_FRAME por interleave). `TryPostFrames` (WS4 da Fase 2) é a variante sem bloquear e sem levantar, para uso dentro de atores.
- **Engine: ator-por-fila** — cada `TAMQPServerQueue` tem fila serial de comandos agendada no `AmqpPool` (work item + flag "já agendado", **não** thread por fila — decisão D2). Toda mutação (enqueue, consumer, ack/nack, TTL, delete) passa por ela. **Nenhum comando do ator pode bloquear o worker esperando I/O.** Exchanges são lookup quase-imutável sob `TMultiReadExclusiveWriteSynchronizer` por vhost (`AMQP.Server.VHost`).
- **Mensagem**: `TAMQPMessage` (`AMQP.Server.Message`) com refcount atômico (`AmqpAtomicInc/Dec`); `Body: TBytes` compartilhado por N filas sem cópia (COW), ninguém muta. **Não guarda propriedades decodificadas** — só o `HeaderPayload` cru (decisão D1); quem precisa das propriedades decodifica a tabela viva do canal antes do enqueue.
- **Consumidor lento sai do rodízio sem bloquear o ator**: entrega é post não-bloqueante via `IAMQPDeliveryTarget.TryDeliver`; se recusar, sai do rodízio daquela rodada e a próxima tenta de novo.
- **`TAMQPChannelDeliveryTarget`** é `TInterfacedObject` separado do `TAMQPServerChannel` de propósito — o canal pode morrer enquanto o ator, numa thread do pool, está no meio de uma entrega; o alvo sobrevive por refcount e `Detach` zera o writer sob lock sem esperar I/O.
- **Lifetime das conexões**: cada `TAMQPServerConnection` possui sua read-thread/writer/canais; auto-registra/desregistra no broker sob lock; liberação por **reaper explícito** (a thread monitora do broker, `TAMQPMonitorThread`, a cada `AMQP_SERVER_MONITOR_TICK_MS`), **nunca `FreeOnTerminate`**. A mesma thread monitora cutuca heartbeat, prazo do Close-Ok, expiração de mensagens (TTL) e `x-expires` de fila ociosa.
- **Codec**: `Decode` dos métodos cliente→servidor e `Build` dos servidor→cliente vivem **in-place** nas units `AMQP.*.Methods` existentes (adicionam funções, não alteram as existentes) — a suíte cliente tem que continuar verde após cada mudança. `TAMQPSocketStream` e `TAMQPTcpListener` vivem em `AMQP.Transport` (públicos).
- **Modelo de erro**: `EAMQPChannelError` (Channel.Close, conexão sobrevive) vs. `EAMQPConnectionError` (Connection.Close + espera Close-Ok) vs. `EAMQPServerAbort` (derruba o socket sem Close), em `AMQP.Server.Types`.

### Auth / vhost

SASL PLAIN só (sem `Secure`/`Secure-Ok`, sem `AMQPLAIN`). `IAMQPAuthenticator` + `TAMQPStaticAuthenticator` (default do broker semeado com `guest`/`guest` — o `TAMQPConnectionParams.Localhost` do cliente conecta sem mudança) + `TAMQPAllowAllAuthenticator` (testes). `TAMQPVirtualHostRegistry` default `{ '/' }`. `IAMQPAuthorizer` existe como stub allow-all.

### Decisões travadas — Fase 2 (D1–D8)

1. **A mensagem carrega o payload cru do content-header**, não um clone da `TAMQPFieldTable`: re-emissão fiel byte a byte, sem o `TValue`-em-`TValue` do FPC. O match de bindings de headers usa a tabela **viva do canal**, antes do enqueue.
2. **O ator da fila roda agendado no `AmqpPool`**, não thread por fila — nenhum comando do ator pode bloquear esperando I/O.
3. **Consumidor lento sai do rodízio**: entrega é post sem bloqueio; se a fila outbound recusar, o consumidor fica suspenso até drenar.
4. **`Basic.Recover` implementado com `requeue=true`**; `540` para `requeue=false` — desvio deliberado do RabbitMQ.
5. **Binding exchange→exchange suportado** (D5), com conjunto de visitados por publicação e `AMQP_MAX_EXCHANGE_HOP_DEPTH = 16` (o grafo pode ter ciclo).
6. **`durable` e `delivery-mode 2` aceitos e ignorados** na Fase 2 — desvio deliberado; recusar quebraria clientes que sempre declaram durável.
7. **Teto de segurança de memória**: `TAMQPServer.MaxQueueLength` global (default 0 = ilimitado; ao estourar, descarta da cabeça). O broker roda *dentro* da app do usuário. `x-max-length` por fila (Fase 3, WS6) compõe com este pelo **menor** dos dois.
8. **A suíte de integração do cliente roda contra o broker embutido**, exceto testes de recurso de Fase 3 — cada exceção vira item de backlog explícito, não teste "pulado". (Backlog fechado na Fase 3, WS6.)

**Invariante**: o *match* de bindings roda na thread do publicador (tabela de exchanges quase-imutável sob RWLock; tabela de headers viva do canal). Só o *enqueue* atravessa para o ator da fila.

### Decisões travadas — Fase 3 (D9–D18)

9. **Persistência não entra na Fase 3; a Fase 4 é WAL com fsync por lote.** Journal append-only, group commit, thread própria de escrita (nunca dentro do ator, preserva D2), `Basic.Ack` assíncrono emitido como prefixo com `multiple=true`.
10. **A D1 fica; reescrever header cria mensagem nova, com o corpo compartilhado.** Vive em `AMQP.Server.Header` (`TAMQPHeaderEditor` + `AmqpDeriveMessage`), não espalhado pelo ator.
11. **Escrita de array de field-value entra na `AMQP.Wire`** (unit do cliente): `WriteFieldValue` ganhou `tkDynArray` (por nome — ordinal difere entre FPC/Delphi), com `AmqpUnwrapValue` em cada elemento. As 121 asserções unitárias são o portão, nos dois compiladores.
12. **Prioridade por baldes, não por heap; `x-max-priority` limitado a 0–9** (406 acima disso, não clamp — desvio do RabbitMQ, que aceita até 255). N+1 `TQueue`, FIFO dentro do nível. Requeue volta à cabeça **do próprio balde**. Descarte por teto **começa pelo balde de MENOR prioridade**.
13. **Expiração preguiçosa na cabeça + varredura no tick da monitora.** Relógio injetável (`NowTick` protected virtual) — teste de TTL não depende de `Sleep`.
14. **Ciclo de dead-letter cortado por PROFUNDIDADE** (`AMQP_MAX_DEADLETTER_HOPS = 16`), não por conjunto de visitados — soma dos `count` do `x-death` acima do teto descarta e conta em `DroppedCount`.
15. **`x-overflow: reject-publish` usa enqueue SÍNCRONO** (`TryPostMessage`), e só nessas filas. *(Estava previsto ser substituído na Fase 4; medido contra o desenho da D24, **não precisa** — o enqueue síncrono não faz I/O, então a recusa é conhecida antes de o pendente de confirm ser registrado.)*
16. **`durable` e `delivery-mode 2` continuam aceitos e ignorados** (D6 segue valendo) — "nada sobrevive a um restart" fica em destaque no README, não em nota de rodapé, porque TTL/DLX/prioridade agora funcionam de verdade. *(A partir da Fase 4 isto vale só com `DataDir` vazio — ver D19.)*
17. **O dead-letter roda dentro do ator** — reescrever header é CPU, rotear é ler topologia sob RWLock e postar noutra caixa; nenhum dos dois espera I/O (D2 preservada). O ator executa comandos **fora** do lock da própria caixa, então nunca segura dois locks de caixa ao mesmo tempo.
18. **Permissões por vhost ficam fora**, amarradas a uma fase de segurança futura junto com guest restrito a loopback e delay/rate-limit pós-falha de auth (`APeerAddress` de `Authenticate` já pronto para isso).

### Decisões travadas — Fase 4, durabilidade (D19–D28)

Planejada em 2026-09-04, em sessão própria e em Opus. Plano completo com as medições: artifact `Broker AMQP — Fase 4` (https://claude.ai/code/artifact/46b89cbc-060b-406c-b10b-31f9e8c99bd1). **A D9 já tinha fixado o MODELO** (WAL append-only, fsync por lote, thread de journal própria para a D2 seguir valendo, confirm assíncrono como prefixo com `multiple=true`); estas dez fixam o DESENHO. Histórico WS-a-WS em `docs/broker-worklog.md`.

19. **Persistência é opt-in por `TAMQPServer.DataDir`.** Vazio (default) = o broker é exatamente o da Fase 3, e a D16 continua valendo; preenchido = durabilidade ligada. Mesma forma do `UseTls`. O broker roda *dentro* da app do usuário: ninguém ganha arquivo em disco por ter chamado `Start`.
20. **Regra clássica dos três, sem desvio:** vai para o disco a mensagem com `delivery-mode=2`, publicada em fila `durable`, num broker com `DataDir`. **Fila não durável nunca toca o journal** (o caminho quente da Fase 3 fica intacto). `delivery-mode` é lido pela thread do publicador, junto com prioridade e `expiration` (razão da D1). Fila `exclusive` **nunca** é persistida; fila `auto-delete` durável é, e volta com `EverHadConsumer=False` (senão o guard da WS7 da Fase 2 a apagaria no boot).
21. **O relógio monotônico nunca vai para o disco.** O journal grava `EnqueuedAtWall` (ms desde a epoch, UTC) + `EffectiveTtlMs`; a recuperação recompõe `ExpiraEm := NowTick + max(0, Ttl - (NowWall - EnqueuedAtWall))`. Monotônico na memória, parede no disco, conversão só nas duas fronteiras — salto de NTP não afeta fila viva. Mensagem já vencida no restart entra pelo **caminho normal de expiração** (dead-letter incluso), no passe que roda depois de topologia e entradas carregadas. **`x-expires` reinicia na recuperação** (fila recuperada conta como usada agora — senão o broker apagaria filas duráveis no boot). `NowTick` virtual (D13) ganha o irmão `NowWall`.
22. **Duas espécies de registro: conteúdo e colocação.** `CONTENT(ContentId, Body)` escrito uma vez; `ENQ(QueueId, EntryId, ContentId, HeaderBlob, Priority, EnqueuedAtWall, TtlMs)` é uma colocação; `DEQ(QueueId, EntryId)` aposenta; `TOPO` para declare/delete. Espelha o COW da memória, e o dead-letter deixa de ser caso especial: **ENQ novo com o mesmo `ContentId` e `HeaderBlob` novo, mais o DEQ do antigo** — o corpo nunca é reescrito. Um journal para o broker inteiro, com o vhost dentro do registro.
23. **Atomicidade por ORDEM, não por marcador de transação.** Cada registro carrega o próprio comprimento e CRC32; a recuperação replica o maior **prefixo válido** e descarta a cauda torta. Onde a atomicidade importa (dead-letter), **escreve o ENQ novo antes do DEQ antigo**: falhar no meio produz duplicata, não perda. Duplicata é o modo de falha que o at-least-once já admite e que o `count` do `x-death` conta; perda não é.
24. **O confirm é liberado por marca d'água de durabilidade (LSN), e quem escreve o lote do publish é a THREAD DO PUBLICADOR** — é a única que, tendo roteado, sabe qual LSN precisa estar durável para aquele seq-no. Ela escreve `CONTENT` + N×`ENQ`, guarda o LSN do último, registra `pendente(canal, seq, lsn)` e **não emite ack**; a thread do journal, após cada fsync, avança a marca e libera todo pendente com `lsn <= marca`, **colapsado por canal num único `Basic.Ack(maiorSeq, multiple=true)`** (a letra da D9). O ator **não** escreve o ENQ do publish — só as retiradas que ele decide (ack, `drop-head`, expiração, dead-letter, purge). Três corolários travados: (a) **confirms saem em ordem de seq por canal** — publish transiente atrás de persistente pendente espera e sai colapsado no mesmo `multiple=true`; (b) **a ordem Return-antes-de-Ack sobrevive** (o Return sai na thread de leitura, antes de o pendente ser registrado, e mensagem sem rota não gera registro) — `MandatorySemRota_ReturnAntesDoAck_312` continua válido palavra por palavra; (c) **a contrapressão vive no publicador, nunca no ator** (a fila de submissão é limitada e a thread de leitura *pode* bloquear nela; registro de retirada é sempre aceito — a D2 fica de pé). Quem emite o frame de ack para um canal que pode ter morrido usa o **padrão do `TAMQPChannelDeliveryTarget`** (objeto refcontado com `Detach` sob lock, sem esperar I/O) e `TryPostFrames`, com recusa retentada no lote seguinte (forma da D3).
25. **Group commit auto-ajustável, sem nenhum parâmetro de tempo.** Laço da thread de journal: pega tudo que está na fila → escreve → um fsync → libera confirms → repete. Lote 1 sob carga baixa; sob carga alta cresce sozinho, porque o que chega durante um fsync é o próximo lote. MEDIDO (FPC 3.2.2/Win64, registros de 256 B, QPC): `FlushFileBuffers` 1:1 custa **329–674 µs** (1,5k–2,2k reg/s); a cada 100 registros, **530–1278 µs por fsync** e **78k–188k reg/s** — **35× a 50×**. Nem janela de espera nem tamanho de lote configuráveis.
26. **Crescimento do WAL: segmentos + compactação por reescrita, uma mecânica só.** Segmentos de tamanho fixo (`MaxSegmentBytes`, default 16 MB); segmento fechado só é apagado quando toda entrada nele foi aposentada e nenhum conteúdo dele é referenciado por entrada viva. A compactação reescreve os registros vivos — **inclusive os de topologia** — na cabeça e apaga o segmento, quando a fração viva cai abaixo de `AMQP_WAL_COMPACT_RATIO` (default 25%) ou quando ele bloqueia a recuperação de espaço. **Sem arquivo de snapshot separado.** Teto duro `MaxJournalBytes` (default 0 = ilimitado, forma da D7); ao estourar, o publish persistente é **recusado com `Basic.Nack`** e contado — a diferença que importa em relação à D7: **teto de memória descarta, teto de disco recusa** (descartar da cabeça no disco seria apagar dado já confirmado).
27. **Não-confirmadas voltam PRONTAS e REDELIVERED, sem registro extra.** A entrega não é journalada: uma entrega não confirmada continua sendo um ENQ vivo (o DEQ só é escrito no ack), então o replay já a devolve — e **na ordem certa de graça**, porque a ordem do journal é a ordem de enqueue e o balde está no registro ENQ, o que a coloca exatamente onde o `RequeueFront` da D12 a colocaria. O flag `redelivered` **não** é persistido: **toda entrada recuperada volta com `redelivered=True`** — persistir custaria uma escrita no caminho mais quente que existe, e seria precisão falsa (depois de uma queda o broker não sabe se o consumidor viu).
28. **"Durável" é afirmação verificável, em três camadas — e com uma admissão que vai no README, não em nota de rodapé: matar o processo NÃO testa fsync** (a cache do SO sobrevive à morte do processo; só a queda da máquina a perde). (1) **Varredura exaustiva de truncamento**, in-process e determinística: monta um journal pequeno e recupera a partir de *cada* offset de 0..N, exigindo estado de prefixo consistente e a presença de toda mensagem confirmada — é o teste-âncora, e a mutação que tem de derrubá-lo é tirar o CRC, tirar o comprimento ou inverter a ordem ENQ/DEQ da D23. (2) **Dublê de arquivo injetável** que conta fsyncs e falha no instante escolhido — prova que o fsync acontece na fronteira do lote e que falha de I/O não corrompe estado em memória. (3) **Matriz de morte de processo** (`CrashHostFpc`, irmão do `BrokerHostFpc`), fora do runner como o SmokeTest. O que o README pode afirmar: *recuperação correta para qualquer ponto de truncamento, e fsync comprovadamente chamado na fronteira do lote.*

**A D15 sobrevive, ao contrário do previsto.** Ela estava registrada como "o único ponto da Fase 3 desenhado para ser substituído"; medida contra este desenho, não precisa ser: o `TryPostMessage` é síncrono mas **não faz I/O nenhum**, então a recusa é conhecida *antes* de o pendente de confirm ser registrado. O que muda é só quando o ack sai — isso é a D24, não a D15.

**Não-objetivos da Fase 4** (além dos de sempre): paginação para disco / lazy queues — *durabilidade não é paginação*, a fila continua inteira na memória; `Connection.Blocked` e alarmes de memória/disco; persistir estado de consumidor (não-confirmada volta pronta, não volta não-confirmada); recuperar fila exclusiva; criptografia em repouso; ordem entre publicadores além da que a spec garante (por canal).

**Workstreams:** WS0 sondas · WS1 camada de arquivo (`AMQP.Server.Wal`: formato, CRC32, append, flush, leitura por prefixo, lock do `DataDir`) — o nome do plano era `AMQP.Server.Journal.File`, mas **`File` é palavra reservada** e não pode ser segmento de nome de unit · WS2 thread do journal (`AMQP.Server.Journal`) · WS3 topologia durável · WS4 mensagem persistente · WS5 confirm assíncrono · WS6 recuperação (dentro do `Start`, **antes de o socket de escuta abrir**) · WS7 espaço (segmentos/compactação/teto) · WS8 crash-safety · WS9 espelhos (contínuo) · WS10 aceitação (as 28 do cliente **duas vezes**, transiente e durável; SmokeTest ganha passo de restart) · WS11 docs.

### Estado atual e desvios deliberados do RabbitMQ

**Fase 1** (protocolo): handshake SASL PLAIN, canais, todo método cliente→servidor com `*-Ok` correto, remontagem de conteúdo com regra de interleave (spec 2.3.5), heartbeats bidirecionais, modelo de erro canal-vs-conexão, TLS server-side (só backend OpenSSL, `-dAMQP_OPENSSL`; SChannel server-side documentado como trabalho futuro no worklog).

**Fase 2** (engine): exchanges direct/fanout/topic/headers + default `""` + `amq.*` predefinidos; filas em memória ator-por-fila; consume/cancel, entrega assíncrona, `Basic.Get`; ack/nack/reject com requeue e redelivered; `Basic.Qos` (prefetch por canal); publisher confirms reais e `mandatory`→`Basic.Return` (ordem Return-antes-de-Ack); filas exclusive/auto-delete com teardown cruzado; modelo de erro completo (403/404/405/406/540).

**Fase 3** (ciclo de vida): TTL de fila e de mensagem (o menor vence); dead-lettering com `x-death` completo (razões `rejected`/`expired`/`maxlen`, count colapsado por fila+razão, `x-first-death-*`); prioridade (`x-max-priority` 0–9, baldes); tetos por fila (`x-max-length`, `x-max-length-bytes`, `x-overflow` `drop-head`/`reject-publish`); `alternate-exchange`; `x-expires` (fila ociosa — publicar não conta como uso).

**Desvios deliberados do RabbitMQ**: guest aceito fora de loopback (footgun documentado, para uso embarcado); sem permissões por vhost; sem delay pós-falha de auth; validação de `user-id` só entra com sink real (já entrou na Fase 2); tipo de exchange desconhecido é 406 de **canal** aqui, não 503 de conexão; `x-max-priority` recusa acima de 9 em vez de aceitar até 255; `x-overflow` sem o modo `reject-publish-dlx`; 406 sempre nomeia o argumento inválido na mensagem; teto de fila e teto global compõem pelo **menor**; `Queue.Delete`/`Exchange.Delete` de recurso inexistente são idempotentes (Delete-Ok), não erro — a letra da spec manda levantar, mas o RabbitMQ é idempotente há muito e o sample `RetryDlqVcl` deste repo já conta com isso.

O define vai numa `SharedMatrixOptions` amarrada ao mode — é o único jeito de alcançar as units do **pacote** (Custom Options do projeto não recompilam o pacote). O `Default` segue SChannel/plain. Trocar de mode recompila o pacote inteiro (cache de `.ppu` único).
