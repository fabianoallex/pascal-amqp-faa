# pascal-amqp-faa — contexto do projeto

Cliente AMQP 0-9-1 dual-compiler (**FPC/Lazarus + Delphi**) numa única codebase, MIT. É o porte multiplataforma da `../delphi-amqp-faa` (mesmo autor); aquela permanece como projeto à parte, Delphi/Windows-only. A arquitetura, os invariantes de concorrência e as lições de protocolo estão documentados no `CLAUDE.md` de lá e valem aqui integralmente.

## Regra inegociável: proveniência do código (herdada da lib original)

**Nunca copiar, adaptar ou se basear em código-fonte de bibliotecas Pascal/Delphi AMQP de terceiros sem licença permissiva clara.** Este projeto deriva exclusivamente da `delphi-amqp-faa` (MIT, mesmo autor) e da especificação AMQP 0-9-1. Consultas a outras implementações são permitidas apenas como conhecimento de protocolo, nunca como fonte a transcrever.

## Regras da codebase dual (Delphi + FPC 3.2.2)

Toda unit começa com `{$I amqp.inc}` (ativa `{$MODE DELPHI}` no FPC e define `AMQP_WINDOWS`). O que NÃO usar, e o que usar no lugar:

| Proibido (não existe no FPC 3.2) | Usar |
|---|---|
| `reference to procedure` / métodos anônimos / `TThread.CreateAnonymousThread` | `procedure ... of object`; work items (`TAMQPWorkItem`) para capturar estado; threads nomeadas |
| `System.Threading` (`TTask.Run`) | `AmqpPool.Queue(...)` de `AMQP.Threading` |
| `System.TMonitor` (Enter/Wait/PulseAll) | `TAMQPMonitor` de `AMQP.Threading` |
| `TInterlocked.*` / `AtomicXxx` direto | `AmqpAtomicInc/Dec/Get/Read64/Write64` de `AMQP.Threading` |
| `TThread.GetTickCount64` | `AmqpTickMs` |
| `System.Net.Socket` direto | `TAMQPTcpSocket` de `AMQP.Transport` |
| `TEncoding.UTF8.GetBytes/GetString` | `AmqpUtf8Encode/Decode` de `AMQP.Wire` (no FPC respeitam o codepage dinâmico) |
| uses com namespace (`System.SysUtils`) | nome curto (`SysUtils`); no Delphi resolve via unit scope names `System;Winapi` |
| inline `var` em bloco | declarar no `var` da rotina |
| `TStringHelper` (`.Split` etc.) | rotinas manuais (`Pos`/`Copy`) |
| `TArray.Sort<T>` | ordenação manual (não existe no Generics.Collections do FPC) |

Gotchas de FPC já encontrados no porte:

- `TValue.From<TArray<TValue>>(x)` não parseia (o `>>` vira `shr` e nem com espaço passa) → usar o alias `TAMQPValueArray` (AMQP.Wire). `TValue.AsType<T>` não existe → `GetArrayLength/GetArrayElement`.
- `Boolean` tem `Kind = tkBool` no FPC (não `tkEnumeration`); `AnsiString` é `tkAString` — os `case AValue.Kind` do codec tratam os dois via `{$IFDEF FPC}`.
- Enum anônimo inline como campo de classe não compila → tipo nomeado (`TAMQPAsmState`).
- `PWideChar(string)` não existe (string é Ansi) → campos que vão para APIs wide são `UnicodeString` (ver `AMQP.Transport.Tls.FTargetName`).
- `Format('%x')` com `LongInt` negativo imprime 16 dígitos → passar `Cardinal(valor)`.
- Fontes em UTF-8 **com BOM**: Delphi exige o BOM para ler UTF-8; o FPC com BOM trata literais como UTF-8 corretamente. Manter o BOM ao criar units novas.
- FPC 3.2.2 trava com **erro interno** (`Internal error 2015071704` / `200510032`) em duas combinações específicas envolvendo `TValue`: (1) encadear `.Put(...)` de `TAMQPFieldTable` terminando num `TValue.From<T>(literal)` inline — separar em chamadas `.Put()` distintas resolve; (2) `Tabela['chave'].AsString` / `.AsExtended` / `.AsObject` encadeado direto no indexador — atribuir o resultado do indexador a uma variável `TValue` local antes de chamar o accessor resolve (`.AsBoolean`/`.AsInteger`/`.AsInt64` encadeados direto não têm esse problema). Achado portando `tests\Unit\fpc\AMQP.WireTests.pas`.
- Apps console FPC puro (fora do Lazarus/LCL) têm `DefaultSystemCodePage` diferente de UTF-8 por padrão — strings acentuadas literais (mesmo com o `.pas` em UTF-8 com BOM) saem transcodificadas errado ao passar por `AmqpUtf8Encode`. Chamar `SetMultiByteConversionCodePage(CP_UTF8)` no início do `program` resolve (ver `tests\Unit\fpc\AMQPUnitTestsFpc.lpr`).
- `TInterlocked` (System.SyncObjs) não existe no FPC → usar `AmqpAtomicInc/Dec/Get/Set/CompareExchange` de `AMQP.Threading` (`AmqpAtomicSet`/`AmqpAtomicCompareExchange` foram adicionados especificamente para portar os testes de integração, que usavam `TInterlocked.Exchange`/`.CompareExchange(x,new,old)`).
- `TTestCase.AssertException` do FPCUnit exige a classe **exata** da exceção (`E.ClassName = AExceptionClass.ClassName`) — não aceita subclasse, diferente do `Assert.WillRaise(proc, EAlgumaClasse)` do DUnitX (que aceita `is`/herança) e do `Assert.WillRaise(proc)` sem classe (qualquer exceção). Para "qualquer exceção", usar `try/except` manual com uma flag booleana + `AssertTrue` (não `Fail()` dentro do próprio `try`, que seria capturado pelo `except`, já que `EAssertionFailedError` também é `Exception`).
- `System.Threading` (`TParallel.For`) não existe no FPC — para testes que precisavam de N chamadas concorrentes, usar `AmqpPool.Queue(TAMQPWorkItem)` da própria lib. Cuidado ao compartilhar arrays entre o item de trabalho e o chamador: um parâmetro de construtor tipado como `array of T` é *open array* (semântica de valor, copia os elementos) — usar um tipo nomeado de dynamic array (`TFooArr = array of T`) como parâmetro para de fato compartilhar o mesmo buffer.
- Citar um diretivo tipo `{$IFDEF FPC}` dentro de um comentário de prosa `{ ... }` quebra a compilação: o `}` do próprio texto citado fecha o comentário mais cedo, e o resto vira código inválido. Escrever "condicional" ou similar em vez do `{$...}` literal ao documentar isso em comentários.
- Amostras VCL/LCL (samples `*Vcl`): `TThread.Queue`/`.Synchronize` do FPC só têm o overload `TThreadMethod = procedure of object` (sem parâmetros) — sem o overload de closure anônima do Delphi. Toda chamada `TThread.Queue(nil, procedure ... end)` (usada pra levar resultado de callback da lib, que roda numa thread do pool, de volta pra UI) precisa virar um método nomeado. Como várias threads do pool chamam isso concorrentemente, um campo compartilhado na form teria corrida — em vez disso, cada chamada cria um pequeno objeto de "marshal" descartável (dados da chamada + `procedure Execute; begin Form.Metodo(...); Free; end;`) e enfileira `TThread.Queue(nil, LMarshal.Execute)`. Ver `samples\RetaguardaVcl\uRetaguardaMain.pas` (`TRecebidaMarshal`/`TStatusMarshal`).
- `System.TMonitor` (usado nos samples VCL originais pra proteger `FPending`) não existe no FPC → `TCriticalSection` (`SyncObjs`), mesmo padrão já usado no resto do projeto.
- **`TypeInfo(TArray<TValue>)` inline não casa com `TAMQPValueArray`** (FPC 3.2): a especialização genérica escrita inline numa unit é um tipo daquela unit, distinto do alias de `AMQP.Wire` que o decoder realmente produz — comparar `TValue.TypeInfo` com a forma inline dá False em silêncio. Usar o alias `TAMQPValueArray`, ou (melhor) não testar o tipo do array e chamar `AmqpUnwrapValue` em todo elemento. Achado no `AmqpArgsEqual` do WS1 da Fase 2 do broker.
- **`TValue.GetArrayElement` sobre `TArray<TValue>` devolve o elemento re-embrulhado no FPC**: um `TValue` de `Kind=tkRecord` contendo o `TValue` interno — `IsObject`/`IsArray`/`As*` falham no embrulho (o `TValue.Make` do Delphi colapsa TValue-em-TValue; o do FPC 3.2 não). Mordeu ao ler as entradas do header `x-death` (array de tabelas) no sample RetryDlqVcl — e o próprio destrutor da `TAMQPFieldTable` vazava as tabelas aninhadas em arrays no FPC por isso. Correção: `AmqpUnwrapValue` (AMQP.Wire), idempotente e no-op no Delphi — usar após **todo** `GetArrayElement` de um array de field-values. Coberto por `Decode_ArrayDeTabelas_EstiloXDeath` nas duas suítes unitárias.
- **FPC descarta `TThread.Queue(nil, ...)` postado por uma thread que morre antes de a main thread bombear a fila**: `TThread.Destroy` chama `RemoveQueuedEvents(Self)`, que casa pelo `ThreadID` do postador — carimbado pelo `InternalQueue` mesmo com `AThread=nil` (ver `classes.inc`). O post some sem rodar e o objeto de marshal vaza. No Delphi não afeta: o descarte casa só pelo campo `Thread`, que fica `nil`. Morde nos callbacks `OnDisconnect`/`OnReconnect`/`OnReconnectFailed`, que rodam na thread de reconexão da lib (ela termina logo após o `OnReconnect`) — sintoma clássico: o post do `OnDisconnect` chega (a thread ainda vive durante os retries) e o do `OnReconnect` desaparece. Correção: saltar por um worker do `AmqpPool` (threads persistentes) com um `TAMQPWorkItem` que faz o `TThread.Queue` de lá; ver `samples\PublicadorConfiavelVcl\uPublicadorMain.pas` (`TConexaoEventoWork`). Callbacks despachados pelo pool da lib (`OnConfirm`, `OnBasicReturn`, consumers, `OnBlocked`) não têm esse problema.
- `ReportMemoryLeaksOnShutdown` (global do `System`) não existe no FPC → `{$IFNDEF FPC}` em volta da atribuição no `.dpr`.
- LCL não tem a propriedade `Font.Charset` nem `TForm.DesignSize` do jeito que o `.dfm` do Delphi grava — omitir essas linhas ao escrever o `.lfm` equivalente (as demais subpropriedades de `Font` e os `Anchors` de cada controle continuam idênticos nos dois).
- `uses Windows, Messages` nos samples GUI não compila fora do Windows — no FPC, usar a camada de emulação da LCL: `LCLIntf` (`GetScrollInfo`/`SendMessage`, implementadas em todo widgetset, gtk2 incluso), `LCLType` (`TScrollInfo`, `SIF_ALL`, `SB_VERT`, `SB_BOTTOM`) e `LMessages` (`LM_VSCROLL`, mesmo valor `$0115` do `WM_VSCROLL` — não existe unit `Messages` na LCL; alias local `const WM_VSCROLL = LM_VSCROLL` resolve). Vale também no FPC/Windows (widgetset win32), então o condicional é só FPC vs Delphi.
- FPC/Linux sem `cthreads` como primeira unit do `program`: `SyncObjs`/eventos falham em runtime com `ESyncObjectException: Failed to create OS basic event` — as threads da lib (heartbeat, leitura, thread pool) dependem de sincronização de verdade. Vale pra qualquer programa novo que use a lib no Linux, não só ela mesma (aplicado em `SmokeTest.dpr`, `AutorizadorSim.dpr`, `Retaguarda.dpr`, `AutorizadorSimVcl.dpr`, `RetaguardaVcl.dpr` e nos dois runners FPCUnit, sob `{$IFDEF UNIX}`). Nos samples GUI o sintoma aparece só ao clicar Conectar ("Falha ao conectar: Failed to create OS basic event") — a form abre normal.
- Os runners FPCUnit (`AMQPUnitTestsFpc.lpr`/`AMQPIntegrationTestsFpc.lpr`) importavam `Forms`/`Interfaces`/`GuiTestRunner` incondicionalmente pra suportar o modo GUI sem parâmetros — isso força link contra LCL mesmo em modo console. Movido para `{$IFDEF MSWINDOWS}`; fora do Windows os runners rodam sempre em modo console (`consoletestrunner`/`testregistry`), sem precisar de Lazarus/widgetset instalado. `AMQP.TlsIntegrationTests` entra em toda plataforma desde que `EAMQPTls` mudou para `AMQP.Transport` (sempre compilada): sem backend TLS no build, o `Open` do Setup falha e os testes se auto-ignoram, mesmo caminho de broker TLS fora do ar.
- **SIGPIPE no Linux**: `send()` num socket já encerrado mata o processo (exit 141) em vez de devolver erro — visto no SmokeTest `--tls`, porque o destrutor do stream TLS manda `close_notify` best-effort com o socket já derrubado pelo `CloseSocketStream` (no Windows isso é só um erro de send engolido pelo `try/except`). Fix no transporte: `TAMQPTcpSocket.Send` usa `fpsend(..., MSG_NOSIGNAL)` sob FPC+Unix quando a unit `sockets` declara a flag (guarda `Declared(MSG_NOSIGNAL)` no `{$IF}`: cobre Linux e BSDs; Darwin não tem a flag e fica no caminho comum) — EPIPE vira retorno negativo, que o `SendRaw` dos streams TLS converte em `EAMQPTls` engolida. O caminho plain nunca escrevia pós-shutdown, por isso o problema não apareceu na validação Linux original.

## Peças novas em relação à lib original

- `AMQP.Threading`: atomics, `AmqpTickMs`, `TAMQPMonitor` (condvar por gerações de eventos — sem wakeups perdidos; waiters re-checam a condição em loop) e `TAMQPThreadPool` (cresce sob demanda até `max(16, 4×núcleos)`; workers persistentes; `AmqpPool` é o singleton global).
- `AMQP.Transport`: `TAMQPTcpSocket` (Delphi: `System.Net.Socket`; FPC: `ssockets.TInetSocket` + `fpshutdown` para desbloquear a thread de leitura sem corrida de FD).
- Work items em `AMQP.Connection` (implementation): `TAMQPDeliveryWork`, `TAMQPReturnWork`, `TAMQPConfirmWork`, `TAMQPBlockedWork`, `TAMQPUnblockedWork`, `TAMQPReconnectThread` — substituem os closures de `TTask.Run`; o contador in-flight é decrementado no `finally` do `Execute`.
- TLS com dois backends e mesma API (`EAMQPTls` vive em `AMQP.Transport` para existir em toda plataforma):
  - `AMQP.Transport.Tls`: SChannel, compila nos dois compiladores mas **só no Windows** (`AMQP_WINDOWS`, automático).
  - `AMQP.Transport.OpenSSL`: OpenSSL, qualquer plataforma, **opt-in** via `-dAMQP_OPENSSL` (tem precedência sobre SChannel se ambos definidos). Bindings próprios (~26 símbolos com assinatura idêntica em 1.1.1 e 3.x), carregados dinamicamente na 1ª conexão TLS com lista de sonames (`libssl.so.3` → `.1.1`; DLLs `libssl-3-x64` etc. no Windows). O engine SSL trabalha sobre **par de BIOs de memória** (nunca `SSL_set_fd`): preserva o desbloqueio da thread de leitura via close do socket E permite proteger o objeto `SSL` (que não aceita read/write concorrentes) com um `TCriticalSection` interno nunca segurado durante I/O de socket. Sem `AMQP_OPENSSL` fora do Windows, `UseTls` levanta a mesma exceção clara de antes.

## Sub-módulo broker (server) — Fases 1 e 2 completas, Fase 3 planejada (branch `feat/broker`)

Avaliada em 2026-09-02 e iniciada: a "outra ponta" — uma lib para **criar um broker AMQP 0-9-1 dentro de uma app Delphi/FPC**, na mesma codebase (units `AMQP.Server.*`, pacote `pascal_amqp_faa_server.lpk` separado que depende do pacote cliente; quem só usa o cliente não linka nada de server). Plano detalhado e avaliação de modelo de execução: artifact `Broker AMQP — Fase 1` (https://claude.ai/code/artifact/9f07e23c-c200-4435-8770-77164bad0c13).

**Proveniência (reforço da regra inegociável):** o server deriva SÓ da especificação AMQP 0-9-1 e do próprio cliente `pascal-amqp-faa` (MIT, mesmo autor). O servidor RabbitMQ é Erlang/MPL — consulta como conhecimento de protocolo é permitida, transcrição de código não. Nada de outras implementações de broker Pascal/Delphi.

**Escopo Fase 1 ("null broker"):** aceita N conexões, cada uma com N canais; handshake completo; decodifica e aceita todo método cliente→servidor; responde os `*-Ok` corretos; heartbeats bidirecionais; close limpo com o modelo de erro de canal/conexão. **Sem engine**: declares são no-op, publishes descartados, nenhuma entrega real. Fases seguintes: engine em memória (roteamento direct/fanout/topic/headers, consume/get/ack/nack, confirms, mandatory/return), depois durabilidade/TTL/DLX/priority.

**Não-objetivos (todas as fases):** cluster, HTTP management API, federation/shovel, AMQP 1.0, STOMP/MQTT, quorum queues, streams.

**Decisões de arquitetura travadas:**
- Modelo de execução: **thread-por-conexão, I/O bloqueante** (reusa `TAMQPTcpSocket`, `TAMQPMonitor`, `AmqpPool`, o truque `fpshutdown`/`Close` para desbloquear read pendente). Event loop (IOCP/epoll/kqueue) rejeitado — 3 backends, nenhum existe nas units compartilhadas, e o alvo é dezenas–centenas de conexões.
- Escrita: **1 objeto writer por conexão com fila outbound limitada + 1 thread escritora** (backpressure natural = flow control TCP). API `Connection.PostFrames(array of TAMQPFrame)` enfileira method+header+body sob um único lock (senão o cliente vê UNEXPECTED_FRAME por interleave).
- Engine (Fase 2): **ator-por-fila** — cada `TAMQPQueue` tem fila serial de comandos; toda mutação (enqueue, consumer, ack/nack, TTL, delete) passa por ela. Exchanges são lookup quase-imutável sob RWLock. Interface que a Fase 1 já expõe com impl nula: `IAMQPMessageSink.RouteMessage(...)`.
- Mensagem: `TAMQPMessage` com refcount interlocked (`AmqpAtomicInc/Dec`); `Body: TBytes` compartilhado por N filas sem cópia (COW), ninguém muta.
- Lifetime: cada `TAMQPServerConnection` possui sua read-thread/writer/canais; auto-registra/desregistra no broker sob lock; liberação por **reaper explícito** (lista + `OnTerminate`), **nunca `FreeOnTerminate`**.
- Codec: os `Decode` dos métodos cliente→servidor e os `Build` dos métodos servidor→cliente entram **in-place** nas units `AMQP.*.Methods` existentes (adicionam funções, não alteram as existentes) — a suíte cliente (81/81 + 27/27) tem que continuar verde após cada mudança. `TAMQPSocketStream` foi promovido de `AMQP.Connection` (privado) para `AMQP.Transport` (público); `TAMQPTcpListener` vive em `AMQP.Transport`.

**Auth / vhost da Fase 1:** SASL PLAIN só (sem `Secure`/`Secure-Ok`, sem `AMQPLAIN`). `IAMQPAuthenticator` + `TAMQPStaticAuthenticator` (default do broker semeado com `guest`/`guest` — o `TAMQPConnectionParams.Localhost` do cliente conecta sem mudança) + `TAMQPAllowAllAuthenticator` (testes). `TAMQPVirtualHostRegistry` default `{ '/' }`. `IAMQPAuthorizer` existe como stub allow-all para a Fase 2 encaixar. **Desvios deliberados do RabbitMQ (documentados de propósito):** (1) `guest` aceito fora de loopback — o RabbitMQ restringe a conexões locais por padrão (footgun para uso embarcado); (2) sem permissões por vhost; (3) sem delay pós-falha de auth (o param `APeerAddress` de `Authenticate` já está lá para o rate-limit futuro); (4) validação da propriedade `user-id` do `Basic.Publish` só entra com o sink real.

**Modelo por workstream:** WS0/WS1/WS2/WS6/WS7/WS8 (scaffolding, codec, listener, broker skeleton, heartbeat, testes) são mecânicos → Sonnet. WS3 (TLS server), WS4 (handshake FSM), WS5 (regra de interleave de conteúdo) têm correção sutil de protocolo → Opus.

  - Os três defeitos, todos no ramo Delphi (`System.Net.Socket`) e todos no mesmo tema — **a RTL levanta no `shutdown` ANTES de fechar o handle**:
    1. Socket **aceito** fecha com `FSock.Close(True)`. O `Close` padrão da RTL (`ForceClosed=False`) faz `shutdown(SD_BOTH)` e então **drena o socket num `while recv(...) > 0` na thread que chamou** — roda `recv` concorrendo com a thread de leitura da conexão, e no Windows o `shutdown` num socket aceito não desbloqueia um `recv` pendente (o mesmo achado do WS2 que levou o caminho FPC a usar fd cru + `CloseSocket`). `Close(True)` pula shutdown/drain e vai direto ao `closesocket`. O caminho **cliente** segue com o `Close` padrão (shutdown gracioso), validado contra brokers reais desde a lib original.
    2. **`TAMQPTcpListener.Close` também usa `Close(True)`** e o `Destroy` guarda o `FListen.Free`. Um socket de ESCUTA tem `FState = [Connected, Listening]` (a RTL marca `Connected` no bind), mas nunca esteve conectado de fato — então o `shutdown(SD_BOTH)` do `Close` padrão falha com WSAENOTCONN e levanta antes do `closesocket`. Resultado: `Accept` pendente **nunca desbloqueava** (o `Close_DesbloqueiaAccept` travava) e o `Free` do listener levantava. É a mesma regra que o caminho FPC/Windows já documentava: num listen socket quem desbloqueia o accept é o `closesocket`, não o `shutdown`.
    3. **`Close` nunca escapa** (e `Destroy` guarda o `FSock.Free`). O `shutdown` do `Close` padrão levanta `ESocketError` WSAENOTCONN (10057) quando o peer JÁ derrubou o TCP — o que passou a acontecer sempre porque o broker fecha o socket logo após o `Connection.Close-Ok`. Pior: a RTL levanta **antes** de limpar o `FState`, então o `TSocket.Destroy` refaz o `shutdown` e a exceção sai de dentro do `Free`. Agora o `except` força `Close(True)` para tirar o socket de "Connected". Sem isso, todo teste do cliente erra no teardown com "on API 'shutdown'" — e há risco de o `StopReadThread` travar no `WaitFor`, já que a exceção abortava o `Close` antes do `closesocket` que desbloqueia o `recv` da thread de leitura. **Vale para qualquer peer que feche o TCP abruptamente, não só o broker desta lib.**

    **O que seria preciso, se um dia for requisito** (TLS de servidor em Delphi/Windows sem depender das DLLs do OpenSSL):
    1. *Credencial.* O SChannel não come PEM: precisa de um `PCCERT_CONTEXT` **com chave privada associada**, o que na prática significa importar um PKCS#12 (`PFXImportCertStore` + `CertFindCertificateInStore`) ou achar um cert já instalado no store da máquina (`CertOpenStore(CERT_STORE_PROV_SYSTEM, 'MY')` + `CertFindCertificateInStore` por subject/thumbprint).

Só isso e o passo 1 é que são novos.

### Fase 2 — engine de roteamento em memória (completa)

Entra inteira pelo `IAMQPMessageSink` que a Fase 1 já expõe: nem o cliente nem a forma do protocolo mudam. Plano de workstreams: artifact `Broker AMQP — Fase 2` (https://claude.ai/code/artifact/50acd241-e591-44c1-aa90-9879e28969d2).

**Escopo:** exchanges direct/fanout/topic/headers + o default `""` + os `amq.*` predefinidos; filas em memória com ator-por-fila (declare/bind/unbind/purge/delete de verdade); `Basic.Consume`/`Cancel`, entrega assíncrona e `Basic.Get`; `Ack`/`Nack`/`Reject` com requeue e `redelivered`; `Basic.Qos` (prefetch por canal); publisher confirms reais e `mandatory` → `Basic.Return`; filas `exclusive`/`auto-delete`; modelo de erro completo (403/404/405/406/540).
**Fora (Fase 3):** persistência, TTL, DLX/`x-death`, `x-max-priority`, `x-max-length` por fila, alternate exchange, permissões por vhost.

**Workstreams e modelo por frente** — Opus onde a correção é de concorrência/ciclo de vida entre threads ou de ordem de frames no wire; Sonnet onde a spec já é tabela ou o trabalho é espelhar:
WS1 mensagem + descritores de recurso (Sonnet) · WS2 topologia por vhost + matchers (Sonnet) · WS3 fila-ator (**Opus**) · WS4 entrega/QoS/ack (**Opus**) · WS5 despacho real na FSM (Sonnet) · WS6 confirms + mandatory/Return (**Opus**) · WS7 ciclo de vida cruzado e teardown (**Opus**) · WS8 suítes espelhadas FPCUnit↔DUnitX (Sonnet, contínuo) · WS9 aceitação: integração do cliente + SmokeTest contra o broker embutido (Sonnet) · WS10 docs (Sonnet).

**Decisões travadas (D1–D8, aprovadas em 2026-09-02 — não reavaliar do zero):**
1. **A mensagem carrega o payload cru do content-header**, não um clone da `TAMQPFieldTable`: re-emissão fiel byte a byte e nada do `TValue`-em-`TValue` do FPC. Consequência: o canal guarda os bytes do content-header e os entrega no `TAMQPServerMessage`. O match de bindings de headers usa a tabela **viva do canal**, antes do enqueue. A Fase 3 (`x-death`) vai precisar de um caminho de reescrita (decodifica → muda → re-encoda) só quando o header mudar de fato.
2. **O ator da fila roda agendado no `AmqpPool`** (work item + flag "já agendado"), não uma thread por fila — N filas ociosas não podem virar N threads. Regra que isso impõe: nenhum comando do ator pode bloquear o worker esperando I/O.
3. **Consumidor lento sai do rodízio**: a entrega é post sem bloqueio; se a fila outbound do writer recusar, o consumidor fica suspenso até drenar. Bloquear o ator seria head-of-line para todos os consumidores daquela fila.
4. **`Basic.Recover` implementado com `requeue=true`** (constantes e codec novos), `540` para `requeue=false` — mesmo desvio do RabbitMQ.
5. **Binding exchange→exchange suportado** (`Exchange.Bind`/`Unbind` já estão no codec), com conjunto de visitados por publicação e profundidade máxima: o grafo pode ter ciclo.
6. **`durable` e `delivery-mode 2` aceitos e ignorados** na Fase 2 (tudo em memória), documentado como desvio deliberado — recusar quebraria clientes que sempre declaram durável.
7. **Teto de segurança de memória**: `TAMQPServer.MaxQueueLength` global (default 0 = ilimitado; ao estourar, descarta da cabeça). O broker roda *dentro* da app do usuário — uma fila sem consumidor não pode derrubar o processo hospedeiro. `x-max-length` por fila continua Fase 3.
8. **O WS9 roda a suíte de integração do cliente contra o broker embutido**, exceto os testes que dependem de recurso de Fase 3 (TTL, DLX/`x-death`, prioridade); cada exceção vira item do backlog da Fase 3, não teste "pulado".

**Invariante nova:** o *match* de bindings roda na thread do publicador (tabela de exchanges quase-imutável sob RWLock; tabela de headers viva do canal). Só o *enqueue* atravessa para o ator da fila.

**Progresso:**
- **WS1** concluído — mensagem e descritores de recurso, sem roteamento nenhum ainda (isso é WS2+):
  - `AMQP.Server.Message` (novo): `TAMQPMessage` — Exchange/RoutingKey/UserId/HeaderPayload/Body, refcount atômico (`AddRef`/`Release`, via `AmqpAtomicInc/Dec`; o último `Release` libera). Nasce com RefCount=1; nunca chamar `Free` direto. Guarda Body e HeaderPayload por referência (sem copiar) — quem constrói decide se copia antes. `TAMQPMessage.FromServerMessage` converte a partir de um `TAMQPServerMessage` já remontado pelo canal. **Deliberadamente não guarda `TAMQPBasicProperties`/`TAMQPFieldTable` nenhuma** — coerente com D1: quem precisa das propriedades decodificadas (ex.: match de headers exchange) decodifica a tabela viva do canal antes do enqueue, não a mensagem já enfileirada. `AmqpSplitBody(Body, AMaxPayload)` fatia o corpo em `TAMQPBodyChunks` pelo frame-max do destinatário — a WS4 (entrega) usa isso para gerar os body frames.

  - **O matcher nasceu recursivo e foi reescrito iterativo — não desfazer isso.** A forma recursiva ("para cada `#`, tente 0, 1, 2… palavras") passa nos 35 vetores mas é **exponencial no número de `#`**: medido com routing key de 24 palavras, 6 `#` = 15 ms, 7 = 110 ms, 8 = **453 ms** por casamento — e uma binding key cabe mais de 100 `#`. Como o match roda na thread do publicador **com o RWLock de leitura na mão**, um único `Queue.Bind` com essa chave transformaria cada publish num travamento do broker: negação de serviço com uma linha de declare. A versão em uso é o backtracking clássico de curinga (`#` faz o papel do `*` de glob, `*` o do `?`), que só precisa lembrar o **último** `#`: O(n·m) no pior caso, O(n) no comum, sem recursão e sem alocar. Coberto por `MuitosHash_NaoExplode` nas duas suítes. Regra própria do projeto (a spec é omissa aqui, decidida no arquivo de vetores do WS2): chave vazia (`""`) tem **zero** palavras, não uma palavra vazia — só isso já derruba a implementação ingênua de "split e compara arrays". `AmqpHeadersMatch` implementa `forall`/`exists` com o caso vazio correto (`all` sem critério é verdade vácua; `any` sem critério é falso vácuo — vetores #8/#9), ignora toda chave `x-` do binding (inclusive o próprio `x-match`).

- **WS3 (fila-ator)** concluído — `AMQP.Server.Queue` (novo): `TAMQPServerQueue`, o coração da Fase 2. O desenho travado na rodada anterior foi implementado como estava, com três acréscimos que valem registro:
  - **Comando síncrono refcontado (chamador + caixa), não "propriedade do chamador".** Se um síncrono estourar o timeout, o dono liberar o objeto enquanto o ator ainda o tem na mão seria use-after-free empilhado sobre um bug que já é ruim. Custou quatro linhas (`AmqpAtomicInc/Dec`, igual à `TAMQPMessage`) e apagou a classe inteira de crash.
  - **`Stop` não usa "comando de parada".** Marca `FStopping` sob o lock (recusa post e agendamento novos), espera `FScheduled=False` no monitor com deadline e só então drena inline. Um comando de parada postado num pool já em shutdown (a finalização de `AMQP.Threading` libera itens enfileirados **sem executá-los**) nunca rodaria, e o `Stop` só voltaria no timeout. No timeout, `Stop` levanta e **não libera nada** — vazar é melhor que liberar sob os pés de um ator vivo; o destrutor engole a exceção.
  - **Pool injetável, default `AmqpPool`** (letra da D2). O parâmetro existe para o broker isolar seus atores num pool próprio sem mudança de estrutura, caso a inanição apareça — o `AmqpPool` tem teto (`max(16, 4×núcleos)`) e é compartilhado com os callbacks de consumer do cliente, que "podem bloquear em IO por segundos". A mensagem do timeout de comando síncrono diz explicitamente "verifique saturação do pool de threads", que é o que transforma um diagnóstico enganoso em óbvio.
  - Estado só do ator: FIFO de mensagens refcontadas em **duas** `TQueue` (`FRequeued` é a cabeça lógica — requeue devolve à posição original, como a spec manda, e `TQueue` não tem push-front), lista de não-confirmadas por `(ChannelId: NativeUInt, DeliveryTag)` (lista e não dicionário: `multiple` precisa varrer faixa e o volume por fila é o prefetch, pequeno — mesma escolha consciente dos bindings do WS2), consumidores e contadores. `MaxLength` (D7) descarta da cabeça e conta em `Stats.DroppedCount`; `PostMessage` numa fila já parada também conta (nada some sem métrica).
  - Semântica de referência: `PostMessage` faz `AddRef` (quem publica em N filas continua dono da dele); `Get` devolve uma referência **do chamador**, e em modo ack a fila guarda a dela nas não-confirmadas. Uma fila parada **descarta** publish em silêncio (publish não falha por corrida de teardown) e **levanta** em comando síncrono (a WS5 mapeia para 404).
  - **Escopo, decidido com o usuário: o WS3 para na costura.** A unit registra consumidores e define `IAMQPDeliveryTarget` (com `TryDeliver` não-bloqueante, D3), mas não despacha `Basic.Deliver`, não faz rodízio, não aplica prefetch e não olha `Channel.Flow` — é tudo WS4. Note que o `TAMQPFrameWriter.PostFrames` de hoje **bloqueia** com a fila outbound cheia, incompatível com D2/D3: o `TryPostFrames` que a entrega precisa entra na WS4.
  - **`TAMQPServer.MaxQueueLength` (D7) ainda NÃO existe** — o broker só cria filas na WS5, e property que ninguém lê é config morta. O teto entra por parâmetro da fila.

O motivo é que um wakeup perdido é **ressuscitado pelo post seguinte** (que encontra `FScheduled=False` e reagenda), então o bug só é fatal no **último post antes da ociosidade** — que é justamente o caso comum de um publish chegando numa fila parada. Com a implementação correta passa em ~15 ms; com a mutação falha (e **só** ele falha). **Uma janela de corrida que nenhum teste alcança é uma janela sem cobertura — mutar de propósito é o jeito barato de descobrir isso.**

- **WS4 (entrega, QoS e ack)** concluído — o ator entrega, a conexão escreve, e entre os dois entra o alvo de entrega:
  - `TAMQPFrameWriter.TryPostFrames` (novo): lote atômico **sem bloquear e sem levantar** — era a dívida que o WS3 registrou, porque o `PostFrames` bloqueia com a fila outbound cheia e o ator não pode esperar I/O (D2).
  - `AMQP.Server.Delivery` (nova): `TAMQPChannelDeliveryTarget`, classe **separada do `TAMQPServerChannel` de propósito**. O canal morre (Channel.Close, queda do socket, reaper) enquanto o ator, numa thread do pool, pode estar no meio de uma entrega — um ponteiro para o canal seria o use-after-free que o plano marca como o risco da fase. A saída é refcount + detach: o alvo é `TInterfacedObject` (cada fila que tem um consumidor lá segura uma referência, então o objeto sobrevive ao canal) e o `Detach` zera o writer sob o lock do alvo; a partir daí todo `TryDeliver` devolve False e as filas descartam o consumidor na rodada seguinte (`IsAlive`). `Detach` nunca espera I/O, então o teardown não trava atrás de um consumidor lento.
  - **Prefetch é lista de tags, não contador.** O limite é por canal e o `Basic.Ack/Nack` com `multiple` resolve **todas** as tags <= a informada — sem saber quais estão abertas, o contador dessincronizaria do que o cliente realmente confirmou. Como a sequência é monotônica, a lista já nasce ordenada e o `multiple` remove um prefixo. Quem **incrementa** é a entrega; quem **decrementa** é a thread de leitura da conexão ao ver o método do cliente (`NoteResolved`, já ligado no `DispatchBasic`) — os dois lados sozinhos não veem o total. Entrega em `no-ack` não conta e não vira não-confirmada.
  - **A delivery-tag é do canal, não da fila** (uma fila entrega para N canais; um canal recebe de N filas), então quem a gera é o alvo, e ela só é **consumida quando o lote é aceito**: uma recusa não abre buraco na sequência. O `Basic.Get` da WS5 puxa da mesma sequência via `NextDeliveryTag`.
  - **Rodízio e a D3 sem estado persistente**: o ator roda uma *rodada* de entrega depois de todo comando que pode ter destravado entrega (enqueue, consumidor novo, ack/nack/reject) e escolhe o próximo consumidor por índice de rodízio. Quem recusa sai do rodízio **daquela rodada** — não há flag "suspenso" para ressincronizar quando o canal drena; a rodada seguinte simplesmente tenta de novo (uma tentativa custa um lock e uma comparação). Para o caso degradado em que ninguém acka e todos recusam (consumidor em `no-ack` mais lento que o produtor), existe `PostDeliverTick`, que a thread monitora do broker vai cutucar na WS5/WS7.
  - **A mensagem só sai do estoque depois de o alvo aceitar** (`PeekReady` e só então `TakeReady`): com a ordem invertida, uma recusa perderia a mensagem.
  - **`TAMQPServerConsumer` deixou de ter `ChannelId` próprio** — ele vem do alvo (`ATarget.ChannelId`, agora obrigatório). Havia duas cópias da mesma identidade (consumidor e alvo) e é ela que chaveia as não-confirmadas e casa o `PostRemoveChannel` do teardown: divergirem significaria requeue no canal errado. A identidade é um contador global monotônico, não o endereço do objeto — endereço reusado casaria uma não-confirmada órfã com o canal errado.
  - `AMQP.Server.Connection` passou a `AttachDelivery` no `AddChannel` e a `DetachAllDelivery` **nos dois caminhos de morte** (o `Shutdown` e o `finally` do read loop), sempre antes de parar o writer.

- **WS5 (despacho real na FSM)** concluído — **o broker deixou de ser nulo**: declara, roteia, entrega, confirma e apaga de verdade. Um cliente real publica e consome contra ele.
  - `AMQP.Server.Engine` (nova): `TAMQPEngine` junta as três peças que as frentes anteriores construíram separadas — a topologia por vhost (WS2), as filas vivas (WS3) e a entrega (WS4). A FSM fala **só** com ela; a engine não conhece número de canal, não levanta exceção de protocolo e não sabe reply-code nenhum — devolve `TAMQPEngineResult` e quem traduz é a FSM, que é quem tem o canal na mão. Descritor (`TAMQPQueueDef`, no vhost) e fila viva (`TAMQPServerQueue`, na engine) nascem e morrem juntos: não há caminho que crie um sem o outro.

  - **Dois bugs de ciclo de vida achados pelos testes, os dois da mesma família** ("quem sabe o quê, e quando"):
    1. *A identidade do canal sumia antes de ser usada.* O teardown chama `DetachAllDelivery` **antes** de varrer os canais, então quando `ReleaseChannelResources` ia perguntar "de qual canal soltar as não-confirmadas?", o alvo já era `nil`. Resultado: **mensagem não confirmada de uma conexão derrubada nunca voltava para a fila**. Correção: `TAMQPServerChannel.DeliveryId`, gravado no attach e que sobrevive ao detach; e o `DetachDelivery` passou a **manter a referência** ao alvo (só faz o `Detach`), porque a varredura ainda precisa perguntar a ele em que filas há entrega em aberto.

- **WS7 (ciclo de vida cruzado e teardown)** concluído — quatro regras, cada uma com dono diferente, e o ponto todo é **quem detecta** vs. **quem executa**:
  | Regra | Quem detecta | Quem executa |
  |---|---|---|
  | fila `exclusive` some com a conexão dona | teardown da conexão (fim do read loop) | `TAMQPEngine.DeleteExclusiveQueuesOf` |
  | fila `auto-delete` some ao sair o último consumidor | quem remove o consumidor (Basic.Cancel ou queda do canal) | `MaybeAutoDeleteQueue` |
  | exchange `auto-delete` some ao perder o último binding | quem desfaz binding (unbind explícito, ou o implícito de apagar uma fila) | `MaybeAutoDeleteExchange` / `SweepAutoDeleteExchanges` |
  | fila apagada avisa os consumidores | o ator, no comando de delete | `IAMQPDeliveryTarget.TryCancel` |
  - **"O último consumidor saiu" só é verdade depois que o ator processou a saída.** A remoção é assíncrona (`PostRemoveChannel`/`PostRemoveConsumer`), então `MaybeAutoDeleteQueue` lê `Stats` — comando **síncrono** — e a caixa FIFO garante que essa leitura já enxerga a remoção postada antes. Não há sleep nem polling nessa decisão.
  - **`EverHadConsumer`**: uma fila `auto-delete` que **nunca teve** consumidor não some — senão ela desapareceria entre o `Queue.Declare` e o primeiro `Basic.Consume`. Mesma regra do RabbitMQ.
  - **Exchange órfão por fila apagada**: apagar uma fila leva junto os bindings dela, e de fora não dá para saber quais exchanges ficaram órfãos. Como exchange `auto-delete` é raro, uma varredura sobre os exchanges do vhost sai mais barata que rastrear origem por origem.
  - `TryCancel` entrou na `IAMQPDeliveryTarget` pelo mesmo contrato do `TryDeliver`: não bloqueia, e um `False` (canal já morto) é aceito em silêncio — a fila está sendo destruída, não há retentativa. **O cliente desta lib trata o `Basic.Cancel` do servidor removendo o consumer internamente, sem expor callback** — por isso a asserção desse aviso é no nível da fila, com o dublê de alvo, e não pelo cliente.

### Fase 3 — ciclo de vida da mensagem (planejada)

Planejada em 2026-09-03, em sessão própria e em Opus, porque três pontos colidiam com invariantes travados na Fase 2. Plano completo: artifact `Broker AMQP — Fase 3` (https://claude.ai/code/artifact/5fdf5f48-dd2c-4084-9884-7b1d862c3d04). **A Fase 2 está completa** — o broker roteia, entrega, confirma e apaga de verdade, e a suíte de integração do cliente passa contra ele.

**Escopo:** TTL (`x-message-ttl` por fila e `expiration` por mensagem, o menor vence) · DLX (`x-dead-letter-exchange`, `x-dead-letter-routing-key`, header `x-death`) · prioridade (`x-max-priority` + propriedade `priority`) · tetos por fila (`x-max-length`, `x-max-length-bytes`, `x-overflow` nos modos `drop-head` e `reject-publish`) · `alternate-exchange` · fila ociosa (`x-expires`) · escrita de array no field-table (`AMQP.Wire`, ver a sonda 2 abaixo).
**Fora:** persistência e recovery (Fase 4, modelo já escolhido) · permissões por vhost (vai junto com o resto de segurança) · paginação para disco (nunca foi objetivo — durabilidade é sobreviver a restart, não segurar mais mensagem que a RAM) · os não-objetivos de sempre (cluster, management API, federation/shovel, AMQP 1.0, STOMP/MQTT, quorum queues, streams).

**As três colisões, resolvidas antes de qualquer código:**
1. **Persistência × D2** (o ator não pode bloquear esperando I/O) — some com o adiamento. Quando entrar, a escrita vai para uma **thread de journal própria** (a forma da thread monitora do WS7 da Fase 1: uma para o broker inteiro), nunca para dentro do ator. A D2 sai da Fase 4 intacta.
2. **Persistência × timing do confirm** — some junto. O `Basic.Ack` continua saindo inline logo após o `RouteMessage`, e com ele a ordem Return-antes-de-Ack, que tem teste de socket cru (`MandatorySemRota_ReturnAntesDoAck_312`) e que qualquer mexida no timing derrubaria.
3. **`x-death` × D1** — **resolvida, fica na Fase 3.** O ponto que desfaz o nó: a D1 proíbe clonar no caminho **quente** (todo publish, toda entrega), não no frio — uma mensagem morre uma vez. E a `TAMQPMessage` já é imutável por invariante, então a reescrita não muta nada: **deriva uma mensagem nova**, com `HeaderPayload` reconstruído e **o mesmo `Body` por referência**. O caro nunca é copiado.

**Sondas medidas antes de planejar** (regra da Fase 2: relatório não é evidência; uma sonda de 20 linhas resolve em minutos o que uma suposição custa numa rodada):
1. Round-trip do content-header (`DecodeContentHeader` → `BuildContentHeader`): **byte a byte idêntico** — 98 bytes, com content-type, delivery-mode, priority, correlation-id, expiration, timestamp, app-id e tabela de headers aninhada. É o que sustenta a D10.
2. **O codec é ASSIMÉTRICO: lê arrays `'A'` e não escreve.** `TAMQPWriter.WriteFieldValue` trata `tkClass` (tabela aninhada) e array nenhum — escrever a forma do `x-death` levanta `EAMQPWire: field-table: TValue.Kind nao suportado (21)`, e 21 é `tkDynArray`. **Não existe `x-death` sem consertar isso**, e o conserto é na `AMQP.Wire`, unit do CLIENTE. Efeito colateral: hoje uma aplicação cliente também não consegue publicar header de array — o conserto serve às duas pontas.
3. Ler array `'A'` vindo do wire continua como a Fase 2 documentou: `IsArray`, elemento é `TAMQPFieldTable`, e o `TypeInfo` casa com `TAMQPValueArray` (a divergência documentada é só da especialização escrita *inline* em outra unit).

**Decisões travadas (D9–D18, aprovadas em 2026-09-03 — não reavaliar do zero; contestar só com medição):**
9. **Persistência não entra na Fase 3; a Fase 4 é WAL com fsync por lote.** Journal append-only, group commit, thread própria de escrita, e `Basic.Ack` assíncrono emitido **como prefixo com `multiple=true`** para o cliente nunca ver seq-no fora de ordem. Conferido no código do cliente: o `ResolveConfirms` de `AMQP.Connection` remove todas as chaves ≤ tag e não presume ordem — aguenta os dois formatos.
10. **A D1 fica; reescrever header cria mensagem nova, com o corpo compartilhado.** O caminho de reescrita vive numa unit própria (`AMQP.Server.Header`), não espalhado pelo ator.
11. **Escrever array de field-value entra na `AMQP.Wire`, e é o primeiro trabalho da fase.** O `WriteFieldValue` ganha o caso `tkDynArray` (por NOME — o ordinal difere entre FPC e Delphi), aplicando `AmqpUnwrapValue` em cada elemento, porque um array relido do wire no FPC devolve os elementos embrulhados. Unit do cliente: as 117 asserções unitárias são o portão, nos dois compiladores.
12. **Prioridade por baldes, não por heap; `x-max-priority` limitado a 0–9.** N+1 `TQueue` e um índice do maior balde não vazio (o RabbitMQ aceita 255 e recomenda ≤ 5). FIFO dentro do nível é invariante testada; requeue volta à cabeça **do próprio balde**, não da fila. **Descarte por teto começa pelo balde de MENOR prioridade** — descartar da cabeça absoluta jogaria fora justamente o que o cliente marcou como mais importante. Fila sem `x-max-priority` mantém a estrutura de hoje: custo zero para quem não usa.
13. **Expiração preguiçosa na cabeça + varredura no tick da monitora.** Com consumidor, checar a cabeça a cada rodada basta; sem consumidor e com DLX, a mensagem tem de morrer no prazo mesmo sem ninguém pedir nada — a thread monitora (200 ms, já cutuca o `DeliverTick`) passa a cutucar `PostExpireTick`, e só em fila que tem TTL. **Relógio injetável**, seam protegido no molde do `ActorRoundEnding`: teste de TTL não pode depender de `Sleep`.
14. **Ciclo de dead-letter cortado por PROFUNDIDADE, não por conjunto de visitados.** Mesmo espírito do `AMQP_MAX_EXCHANGE_HOP_DEPTH = 16` que o `Route` já usa: soma dos `count` do `x-death` acima do teto descarta e conta em `DroppedCount`. O RabbitMQ compara o conjunto de filas visitadas — mais caro, e o efeito prático numa engine em memória é o mesmo.
15. **`x-overflow: reject-publish` usa enqueue SÍNCRONO, e só nessas filas.** Quarto ponto de colisão, achado nesta rodada: o publicador precisa saber da recusa **antes** do ack, e o `PostMessage` de hoje é assíncrono e não devolve nada. Das saídas possíveis, a síncrona é a única que preserva a ordem de confirm da WS6 inteira sem construir agora o registro de confirms pendentes da Fase 4. Bloquear o publicador não é efeito colateral: é literalmente a semântica que `reject-publish` pede. O comando é síncrono **sem I/O**, então o teto de 15 s é rede contra bug nosso, não contra peer lento. **É o único ponto da Fase 3 desenhado para ser substituído** — quando a Fase 4 tiver o registro assíncrono, migra para ele.
16. **`durable` e `delivery-mode 2` continuam aceitos e ignorados** (a D6 segue valendo), agora com uma frase a mais na doc: TTL, DLX e prioridade passam a funcionar **de verdade**, o que torna mais fácil supor que durabilidade também. "Nada sobrevive a um restart" vai na primeira linha da seção do broker no README, não numa nota de rodapé.
17. **O dead-letter roda dentro do ator, e por isso é só CPU e post.** Reescrever header é CPU; rotear é ler a topologia sob RWLock e postar na caixa de outras filas — nenhum dos dois espera I/O, então a D2 continua satisfeita. A ordem de locks também: o ator executa comandos **fora** do lock da própria caixa, então postar na caixa de outra fila nunca segura dois locks de caixa ao mesmo tempo. Isto é invariante, não observação: se algum dia o dead-letter precisar esperar alguma coisa, ele sai do ator.
18. **Permissões por vhost ficam fora**, amarradas a uma fase de segurança junto com os outros dois desvios da Fase 1: guest restrito a loopback e delay/rate-limit pós-falha de auth (o `APeerAddress` do `Authenticate` já está lá esperando por isso desde o WS0).

**Workstreams e modelo por frente** — mesmo critério das fases anteriores; a ordem importa, a WS1 destrava a WS3, que destrava a WS5:
WS1 escrita de array no field-table (`AMQP.Wire`) (Sonnet) · WS2 política de fila: `x-arguments` → `TAMQPQueuePolicy`, com validação → 406 (Sonnet) · WS3 reescrita de content-header, `AMQP.Server.Header` (**Opus**) · WS4 estoque com prioridade e expiração (**Opus**) · WS5 dead-lettering: razões `rejected`/`expired`/`maxlen`, `x-death` com `count` colapsado por (fila, razão), `x-first-death-*`, guarda de ciclo (**Opus**) · WS6 tetos por fila e `x-overflow` (Sonnet) · WS7 alternate exchange (Sonnet) · WS8 `x-expires` (**Opus** — apagar fila viva a partir do tick é o mesmo teardown cruzado que mordeu na WS7 da Fase 2) · WS9 suítes espelhadas FPCUnit↔DUnitX (Sonnet, contínuo) · WS10 aceitação (Sonnet) · WS11 docs (Sonnet).

- **WS4 (estoque com prioridade e expiração)** concluída — a frente de superfície mais larga da fase: tudo que conta mensagem passou a somar sobre N baldes.
  - **Baldes, não heap (D12).** `FStock`/`FRequeued` viraram `array of TQueue` indexado por prioridade. Fila sem `x-max-priority` tem `FMaxPriority = 0`, logo **um balde só e o mesmo caminho de código de antes** — sem ramo condicional espalhado e sem custo para quem não usa. `TakeReady`/`PeekReady` varrem do balde mais alto para o mais baixo; dentro do balde, as devolvidas antes das novas.
  - **FIFO dentro do nível é invariante testada**: prioridade reordena **entre** níveis, nunca dentro de um.
  - **Requeue volta à cabeça do PRÓPRIO balde**, com o prazo original. Voltar à cabeça absoluta faria uma mensagem de prioridade baixa furar a fila das altas; zerar o prazo daria sobrevida a quem já devia ter morrido. Por isso `TAMQPUnackedEntry` passou a guardar `Priority` e `ExpiraEm` — a não-confirmada tem de lembrar os dois para devolver certo.
  - **Prioridade e `expiration` são lidas na thread do PUBLICADOR**, não no ator: a mensagem guarda o header cru (D1), e quem ainda tem as propriedades decodificadas é quem publicou. O `PostMessage` ganhou `APriority` e `AMessageTtlMs` já prontos; o ator só limita a prioridade ao próprio teto e combina os TTLs. É a mesma invariante do match de headers da Fase 2.
  - **TTL: o menor entre fila e mensagem vence.** `x-message-ttl` da fila e `expiration` da mensagem; ausentes os dois, a mensagem não vence nunca.
  - **Relógio injetável (D13)**: `NowTick` é `protected virtual` (molde do `ActorRoundEnding`). Teste de TTL não pode depender de `Sleep` — a suíte sobrescreve e faz o tempo andar na mão, o que torna a expiração determinística e instantânea. Os dez testes novos rodam em ~8 ms somados.
  - **Expiração preguiçosa na cabeça, com uma limitação deliberada e documentada.** `ExpiraVencidas` drena da cabeça de cada balde enquanto vencido — O(vencidas), não O(n). Com `x-message-ttl` da **fila** (o caso comum) as entradas já estão em ordem de vencimento e isso é exato. Com `expiration` **por mensagem** elas não estão, então uma mensagem de prazo curto atrás de uma de prazo longo só é recolhida ao chegar à cabeça — **mesmo comportamento do RabbitMQ**, e varrer a fila inteira a cada tick seria O(n) por tick para consertar um caso raro.
  - Roda no início do `DeliverPending`, **antes do early-exit por falta de consumidor** — é o que faz uma fila sem consumidor nenhum vencer no prazo (D13), acordada pelo tick da monitora que já existia. Também no `Basic.Get` (o outro caminho de saída) e no enqueue, **antes** de aplicar o teto: com a ordem invertida, uma mensagem já vencida ocuparia vaga e faria descartar uma viva.
  - **Teto de memória descarta do balde de MENOR prioridade** (D12) — descartar da cabeça absoluta, que é a de maior prioridade, jogaria fora justamente o que o cliente marcou como mais importante.
  - `Stats.ExpiredCount` novo, pela mesma razão do `DroppedCount`: sem métrica, mensagem some sem ninguém saber. Na WS5 as vencidas passam a ir para o DLX e a contagem continua valendo.
  - **`DescartaExpirada` existe como método próprio de propósito**: é o ponto único por onde uma vencida sai, e a WS5 troca o corpo dele por "reescreve o header com `x-death` e republica no DLX" sem tocar em mais nada.
  - **`expiration` malformada é 406, não ignorada.** É TTL em ms como **string decimal** (assim a spec define). Ignorar em silêncio faria uma mensagem que o cliente mandou expirar viver para sempre, sem ele ter como descobrir. `AmqpParseExpirationMs` (em `AMQP.Server.Resources`) valida dígitos e estouro; a FSM recusa no `CompleteContent`, na mesma linha do 406 de x-argument inválido da WS2.
  - Construtor ganhou sobrecarga com `TAMQPQueuePolicy`; a antiga continua e equivale a passar `Empty` — foi o que evitou tocar nas 23 asserções da `TQueueActorTests`. A engine cria a fila com a política **do descritor**, não reparseando os argumentos: o descritor já é a fonte da verdade e reparsear abriria espaço para os dois divergirem.
  - **As três mutações que o plano fixou antes de os testes existirem, todas conferidas**, e cada uma derruba exatamente o teste que deveria: não expirar no caminho de entrega → 3 testes de TTL; requeue na cabeça absoluta → `Prioridade_RequeueVoltaAoProprioBalde`; teto descartando do balde de maior prioridade → `MaxLength_DescartaDoBaldeMenosPrioritario`.
  - Fixture nova `TQueuePriorityTtlTests` (10), de estado puro — nenhum socket, nenhum broker.
  - Suíte do server: **228/228 → 238/238** (Default) e **232/232 → 242/242** (`openssl`). Regressão nos dois compiladores: FPC — server 238/238 e 242/242, unitária 121/121, integração 28/28 contra o RabbitMQ real, SmokeTest PASS, todas com `0 unfreed memory blocks`. Delphi (IDE) — server **238/238** no Debug e **242/242** no OpenSSL, unitária 121/121 e integração 28/28 nos dois configs, **0 leaks** nos seis runs.
  - **Escopo:** a WS4 entrega o estoque. Dead-lettering do que vence é a WS5; `x-max-length`/`x-overflow` por fila é a WS6 (o teto que existe aqui é o global da D7); `x-expires` é a WS8.

- **WS5 (dead-lettering)** concluída — o `x-death` deixou de ser mecanismo e virou semântica. Com ela a Fase 3 entrega o recurso que motivou a colisão do planejamento.
  - **As três razões**, cada uma no ponto onde a morte já acontecia: `rejected` (nack/reject sem requeue, no `ResolveUnacked`), `expired` (TTL, no `DescartaExpirada` que a WS4 deixou pronto) e `maxlen` (teto, no `EnforceMaxLength`). `delivery_limit` fica de fora: é de quorum queue, que não existe aqui.
  - **`MorreCom` é o ponto único de saída de uma morte**, e sempre consome a referência da entrada — republicando ou não. Foi o `DescartaExpirada` da WS4 crescendo, exatamente como aquela frente previu.
  - **ACK e nack-sem-requeue chegavam indistinguíveis** ao `ResolveUnacked` (os dois com `ARequeue=False`). Sem separá-los, **toda mensagem confirmada iria para o DLX** — daí o parâmetro `ARejeitada`, e o teste `Ack_NaoVaiParaODlx` existe só para travar isso.
  - **`x-death` colapsa por (fila, razão)**: entrada existente tem o `count` incrementado, não uma entrada nova. É para isso que a spec tem o campo — sem o colapso, um laço de retry infla o header a cada volta até estourar o frame-max. Entrada nova vai para a **frente** do array (mais recente primeiro), como o RabbitMQ.
  - **`x-first-death-queue`/`-reason`/`-exchange`** são gravados só na primeira morte e nunca sobrescritos.
  - **A propriedade `expiration` é RETIRADA ao dead-letterar** e vira `original-expiration` na entrada. Sem isso, uma mensagem morta por TTL levaria o mesmo prazo para a DLQ, morreria no ato, e o padrão retry-com-espera — o do sample `RetryDlqVcl` — não funcionaria. `TAMQPHeaderEditor.TakeExpiration` existe só para isso.
  - Sem `x-dead-letter-routing-key`, a chave **original** é mantida — é o que faz um DLX topic continuar roteando pelo mesmo critério.
  - **Guarda de ciclo por profundidade (D14)**: `AMQP_MAX_DEADLETTER_HOPS = 16` contra a soma dos `count`. Ao estourar, a mensagem morre de vez em vez de circular.
  - **`IAMQPDeadLetterSink` + `TAMQPDeadLetterAdapter`**: a fila não pode enxergar a engine (que já a enxerga — ciclo de units), e a interface não carrega vhost porque a fila não sabe em que vhost mora. Um adaptador por vhost fixa o nome e mantém a interface com o que interessa. Ele é `TInterfacedObject` e a fila segura a referência, então vive enquanto a fila viver.
  - **O `RepublishTo` decodifica o header** para poder casar um DLX do tipo headers. É CPU na thread do ator, o que a D17 permite: é o caminho **frio** (uma mensagem morre uma vez), não o do publish.
  - Uma morte que não consegue ser republicada (header ilegível, DLX sumido) **vira descarte, e não exceção** — levantar ali mataria a rodada e deixaria a fila meio processada.
  - **Três defeitos meus nesta frente, e os dois primeiros valem como regra:**
    1. **`Exit` dentro de `try..except` sai da FUNÇÃO e pula o código depois do bloco.** A primeira versão do `MorreCom` liberava a referência depois de um `try..except` que tinha `Exit` no caminho "sem DLX" — e nesse caminho o `Release` nunca rodava. Pegou-o um teste da WS3 (`Nack_SemRequeue_Descarta`) e o heaptrc confirmou com 21 blocos. **A liberação que tem de valer para todos os caminhos vai em `try..finally`, nunca depois do bloco.**
    2. **Dublê `TInterfacedObject` cuja única referência de interface está no objeto sob teste morre junto com ele.** O teste do ciclo reusa o mesmo sink em várias filas e deu `Access violation` na segunda: liberar a fila zerou o refcount. Todo teste da fixture agora guarda também um `LSinkRef: IAMQPDeadLetterSink`.
    3. Chave de fechar dentro de comentário de bloco fecha o comentário — o mesmo gotcha que o `CLAUDE.md` já registra para diretivas citadas, agora mordendo ao documentar a forma do `x-death` em notação de chaves. Os campos foram para uma lista.
  - **As três mutações do plano, conferidas**, cada uma derrubando só o teste que deveria: remover a guarda de ciclo → `GuardaDeCiclo_ParaDepoisDoTeto`; não colapsar o `count` → `MesmaFilaEMesmaRazao_ColapsaNoCount`; tratar ack como rejeição → `Ack_NaoVaiParaODlx`.
  - Fixture nova `TDeadLetterTests` (11), de estado puro com um sink dublê que copia o que recebeu — nenhum socket, nenhum broker.
  - Suíte do server: **238/238 → 249/249** (Default) e **242/242 → 253/253** (`openssl`). Regressão nos dois compiladores: FPC — server 249/249 e 253/253, unitária 121/121, integração 28/28 contra o RabbitMQ real, SmokeTest PASS, todas com `0 unfreed memory blocks`. Delphi (IDE) — server **249/249** no Debug e **253/253** no OpenSSL, unitária 121/121 e integração 28/28 nos dois configs, **0 leaks** nos seis runs. **Aceitação** (o projeto que o `F2613` tinha quebrado) revalidada nos dois configs: 28/28, com o padrão esperado de auto-ignorados — 6 no Debug (5 de TLS, porque esse build não tem TLS de servidor, mais o de `x-max-length`) e apenas 1 no OpenSSL, onde os 5 de TLS rodam de verdade. É também a confirmação de que a WS5 não quebrou o caminho ponta a ponta.
  - **Escopo:** falta o teste ponta a ponta pelo cliente real (`Queue.Declare` com `x-dead-letter-exchange` de verdade contra o broker embutido) — entra na WS10, junto com o SmokeTest de TTL+DLX. O que existe aqui prova o mecanismo no nível da fila.

**Mutações obrigatórias, decididas ANTES de escrever os testes** (regra da Fase 2: verde não prova cobertura; se a mutação não derruba nada, a suspeita é do teste):
- WS4 — entregar a mensagem expirada em vez de expirá-la → tem de derrubar o teste de TTL **sem** consumidor, não só o com consumidor.
- WS4 — requeue voltando à cabeça absoluta em vez da cabeça do balde → derruba o FIFO-dentro-do-nível após nack.
- WS4 — descarte por teto começando pelo balde de MAIOR prioridade → derruba o teste da D12.
- WS5 — remover a guarda de ciclo da D14 → o teste de A→DLX→A não termina.
- WS5 — não colapsar o `count` do `x-death` → o teste de retry repetido passa a inflar o header a cada volta.
- WS3 — reusar o `HeaderPayload` da mensagem original em vez de derivar um novo → derruba o teste que publica a mesma mensagem em duas filas e dead-lettera de uma só.

**Critérios de aceitação:** integração do cliente contra o broker embutido vai a **28/28** (o `Confirm_WaitForConfirms_DetectaNackJaResolvido` deixa de se auto-ignorar e o backlog da Fase 2 fecha zerado) · SmokeTest ganha passos de TTL+DLX e de prioridade, PASS contra o RabbitMQ **e** contra o broker embutido (a prova dupla: os mesmos passos contra os dois brokers dizem que a semântica é a da spec, não a nossa) · suíte do server verde nos dois build modes e nos dois compiladores, heaptrc em zero e 0 leaks no DUnitX · **unitária do cliente intacta em 117/117** depois da WS1, que é a única mudança da fase fora de `src\server\`.

**Riscos conhecidos, escritos agora para não serem descobertos depois:**
- **A reescrita de header descarta palavras de continuação** — o `DecodeContentHeader` consome e ignora as palavras extras do property-flags. Nenhuma propriedade da classe Basic vive além da primeira palavra, então é teórico; mas se um peer mandar, a reescrita apaga em silêncio. A sonda 1 mediu sobre o conjunto que a classe define — o teste da WS3 deve cobrir **todas** as catorze propriedades, não uma amostra.
- **O `x-death` cresce a cada hop** — é para isso que a spec tem o campo `count`. Sem colapsar repetições da mesma (fila, razão), um laço de retry infla o header até estourar o frame-max.
- **Prioridade toca em tudo que conta mensagem** — `ReadyCount`, `Purge`, o teto da D7, o `MessageCount` do `Declare-Ok` e as não-confirmadas passam a somar sobre N baldes. É a superfície mais larga da fase, e a razão de a WS4 ser Opus.
- **TTL curto transforma reescrita de header em caminho quente** — uma fila com TTL de milissegundos e DLX reescreve um header por mensagem expirada. Aceitável (o corpo continua sem cópia), mas é a única circunstância em que a D10 encosta no caminho quente.
- **A WS1 mexe em unit compartilhada?** Não: `AMQP.Wire` **não** está na lista de units copiadas para o `pascal-pipes-faa` e o `pascal-redis-faa` (a lista é `Threading` e `Transport*`), então não há propagação manual a fazer. Registrado porque a pergunta vai aparecer.

**O que já ficou decidido da Fase 4** (adiar não é deixar em aberto — estas amarras existem para a Fase 3 não construir nada que precise ser desfeito): modelo WAL append-only com fsync por lote (cobre queda de máquina, não só do processo hospedeiro — é o único modelo que merece a palavra "durável" na doc) · escrita numa thread de journal própria, nunca no ator · confirm assíncrono emitido como prefixo com `multiple=true` · a ordem Return-antes-de-Ack sobrevive, porque o `Basic.Return` continua saindo na thread de leitura, antes de o confirm pendente sequer ser registrado, e o teste de socket cru da WS6 permanece válido palavra por palavra.

**Verificador de espelhos (`tests	oolserifica_espelhos.py`):** `python tests	oolserifica_espelhos.py` — roda **sem compilador** e checa as duas coisas que só aparecem no espelho Delphi, onde cada erro custa um round-trip pela IDE: (1) código declarado **depois do `initialization`** (em Pascal `procedure` ali vira diretiva, `E2070` no dcc32); (2) **paridade dos espelhos** — todo teste declarado de um lado existe do outro, e toda fixture **com testes** está registrada. O segundo pega o defeito silencioso: fixture nova não registrada no DUnitX **não dá erro de compilação**, dá suíte verde com N testes a menos. Sai com código 1 em divergência, então dá para amarrar num hook. **Rode antes de mandar a suíte para a IDE.** Não tem lista de exceções de propósito: a primeira versão comparava toda `procedure` e exigia registro de toda classe, acusou 7 divergências e as 7 eram falso-positivo — a correção foi usar os discriminadores exatos de cada dialeto (`[Test]`/`[TestFixture]` no DUnitX; `published` dentro de fixture no FPCUnit, com fecho transitivo de herança, porque as fixtures do server descendem de um `TServerFixture` comum e não direto de `TTestCase`). Exigir registro só de fixture **que declara teste** é o que deixa uma classe base fora da conta sem abrir buraco. Ganhou na WS5 uma **terceira checagem**: toda unit de `src\server\` tem de estar listada em **todo** `.dpr` que compila o sub-módulo, e o `.dproj` irmão tem de listar as mesmas. O FPC não pega isso — lá as units vêm do **pacote**, então basta acrescentar ao `.lpk`; no Delphi cada projeto lista uma a uma, e a que faltar só aparece como `F2613 Unit not found` na IDE. Foi exatamente o que aconteceu com a `AMQP.Server.Header`: entrou no projeto da suíte do server na WS3 e ficou de fora do da aceitação, e o erro só apareceu na WS5, quando o `AMQP.Server.Queue` passou a usá-la. As **seis** mutações que ele tem de pegar (conferidas): registro removido, `procedure` após o `initialization`, teste presente só de um lado, **registro DUnitX sem o prefixo `TDUnitX.`**, unit de `src\server\` fora de um `.dpr`, e unit no `.dpr` mas não no `.dproj`. Esta última entrou depois de o próprio verificador dar falso-negativo: o regex casava `RegisterTestFixture(X)` com ou sem prefixo, e deu por registrada uma fixture num arquivo que o `dcc32` recusava com `E2003`. **A forma da chamada importa, não só o nome** — no DUnitX o registro é método de classe e o `TDUnitX.` é obrigatório; no FPCUnit o `RegisterTest` é função solta.

**Build/teste do server:** `fpc -Fusrc -Fusrc\server -Fisrc -FEbuild -FUbuild src\server\AMQP.Server.Broker.pas` compila o server inteiro; pacote `lazbuild packages\pascal_amqp_faa_server.lpk`. Os runners FPCUnit do server e da unitária rodam com **heaptrc ligado** (`UseHeaptrc` no `<Debugging>` de cada `<CompilerOptions>` do `.lpi` — inclusive o de cada build mode): a última linha da execução é `N unfreed memory blocks`, e com N > 0 vem a pilha de alocação de cada bloco — é o jeito de caçar leak sem depender da IDE Delphi. Suíte em `tests\Server\AMQP.ServerTests.dproj` (DUnitX, dentro do `AMQP.groupproj`) e `tests\Server\fpc\AMQPServerTestsFpc.lpi` (FPCUnit) — **espelhos um do outro: mesmos nomes de teste e mesmas asserções, mantenha os dois em sincronia**. A fixture sobe o broker in-process em porta efêmera e aponta o `TAMQPConnection` do cliente nele. Certs de TLS: reusar `docker\certs`.
