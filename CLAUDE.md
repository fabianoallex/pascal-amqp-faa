# pascal-amqp-faa — project context

Dual-compiler AMQP 0-9-1 client (**FPC/Lazarus + Delphi**) in a single codebase, MIT. It is the cross-platform port of `../delphi-amqp-faa` (same author); that one remains a separate project, Delphi/Windows-only. The architecture, the concurrency invariants and the protocol lessons are documented in that project's `CLAUDE.md` and apply here in full.

> **Detailed history of the broker sub-module** (bugs found workstream by workstream, test mutations, suite counts run by run, platform validations) is in `docs/broker-worklog.md` — it is not loaded automatically; read it on demand. This file keeps only the current state, the locked decisions and the live rules.

**The `dual-compiler-delphi-lazarus` skill is not in this repository.** It lives in
[pascal-skills-faa](https://github.com/fabianoallex/pascal-skills-faa), which is a Claude Code plugin and marketplace. If it
is not loaded in this session, ask the user to install it (user scope, so it also applies
in an application that uses this library as a submodule):
`/plugin marketplace add fabianoallex/pascal-skills-faa` and then
`/plugin install pascal-skills-faa@pascal-skills-faa`. The index of all the `*-faa` libraries is in
`dual-compiler-delphi-lazarus/references/faa-libraries.md` in that repository.

## Non-negotiable rule: code provenance (inherited from the original library)

**Never copy, adapt or base anything on source code from third-party Pascal/Delphi AMQP libraries without a clear permissive license.** This project derives exclusively from `delphi-amqp-faa` (MIT, same author) and from the AMQP 0-9-1 specification. Looking at other implementations is allowed only as protocol knowledge, never as a source to transcribe. The broker (server) sub-module follows the same rule: it derives only from the spec and from this library's own client. RabbitMQ (Erlang/MPL) is consulted only as protocol knowledge.

## Rules of the dual codebase (Delphi + FPC 3.2.2)

Every unit starts with `{$I amqp.inc}` (turns on `{$MODE DELPHI}` in FPC and defines `AMQP_WINDOWS`). What NOT to use, and what to use instead:

| Forbidden (does not exist in FPC 3.2) | Use |
|---|---|
| `reference to procedure` / anonymous methods / `TThread.CreateAnonymousThread` | `procedure ... of object`; work items (`TPcWorkItem`) to capture state; named threads |
| `System.Threading` (`TTask.Run`) | `PcPool.Queue(...)` from `PascalCommon.ThreadPool` (pascal-common-faa) |
| `System.TMonitor` (Enter/Wait/PulseAll) | `TPcMonitor` from `PascalCommon.ThreadPool` |
| `TInterlocked.*` / `AtomicXxx` directly | `PcAtomicInc/Dec/Get/Read64/Write64` from `PascalCommon.Threading` |
| `TThread.GetTickCount64` | `PcTickMs` (`PascalCommon.Threading`) |
| `GetLastOSError` (exists only in FPC; Delphi has `RaiseLastOSError`, which **raises** instead of returning) | `AmqpLastOsError` from `AMQP.Server.Wal` |
| `System.Net.Socket`/`ssockets` directly | `PcTcpConnect`/`PcTcpListen`/`PcTlsWrap`/`PcTlsListen` from pascal-common-faa, read through `TAMQPEndpointStream` (`AMQP.Transport`) |
| `TEncoding.UTF8.GetBytes/GetString` | `AmqpUtf8Encode/Decode` from `AMQP.Wire` (in FPC they honor the dynamic codepage) |
| uses with a namespace (`System.SysUtils`) | short name (`SysUtils`); in Delphi it resolves through the unit scope names `System;Winapi` |
| inline `var` in a block | declare in the routine's `var` |
| `TStringHelper` (`.Split` etc.) | manual routines (`Pos`/`Copy`) |
| `TArray.Sort<T>` | manual sorting (does not exist in FPC's Generics.Collections) |

FPC gotchas already found during the port:

- `TValue.From<TArray<TValue>>(x)` does not parse (the `>>` becomes `shr`, and not even a space helps) → use the `TAMQPValueArray` alias (AMQP.Wire). `TValue.AsType<T>` does not exist → `GetArrayLength/GetArrayElement`.
- `Boolean` has `Kind = tkBool` in FPC (not `tkEnumeration`); `AnsiString` is `tkAString` — the codec's `case AValue.Kind` handle both via `{$IFDEF FPC}`.
- An inline anonymous enum as a class field does not compile → a named type (`TAMQPAsmState`).
- `PWideChar(string)` does not exist (string is Ansi) → fields that go to wide APIs are `UnicodeString` (that was `FTargetName` in the old `AMQP.Transport.Tls`; today SChannel lives in pascal-common-faa).
- `Format('%x')` with a negative `LongInt` prints 16 digits → pass `Cardinal(value)`.
- Sources in UTF-8 **with BOM**: Delphi requires the BOM to read UTF-8; FPC with BOM treats literals as UTF-8 correctly. Keep the BOM when creating new units (including `.md` files generated by script — a `Write`/redirect that does not preserve the BOM silently breaks the heading count of verification scripts).
- FPC 3.2.2 crashes with an **internal error** (`Internal error 2015071704` / `200510032`) in two specific combinations involving `TValue`: (1) chaining `.Put(...)` of `TAMQPFieldTable` ending in an inline `TValue.From<T>(literal)` — splitting into separate `.Put()` calls fixes it; (2) `Table['key'].AsString` / `.AsExtended` / `.AsObject` chained directly on the indexer — assigning the indexer's result to a local `TValue` variable before calling the accessor fixes it (`.AsBoolean`/`.AsInteger`/`.AsInt64` chained directly don't have this problem).
- Pure FPC console apps (outside Lazarus/LCL) have a `DefaultSystemCodePage` other than UTF-8 by default — literal accented strings come out wrongly transcoded when going through `AmqpUtf8Encode`. Calling `SetMultiByteConversionCodePage(CP_UTF8)` at the start of the `program` fixes it.
- `TInterlocked` (System.SyncObjs) does not exist in FPC → use `PcAtomicInc/Dec/Get/Set/CompareExchange` from `PascalCommon.Threading`.
- **`TCP_NODELAY` is on for every socket, client and accepted** (since v0.6.0 through pascal-common-faa: `AmqpTcpOptions` passes the zeroed record, `Nagle = False`; tests `TcpOptions_NagleOff` and `RequestReply_NoNagleDelay`, the latter measuring 20 write-write-read round trips in < 400 ms, which with Nagle on Linux take ~40 ms each; the common library's endpoint has no way to read the option back). The protocol is request/response with small frames: with Nagle on, each round trip gains ~40 ms of delayed ACK on Linux (up to 200 ms on Windows outside loopback). **Measured on Debian 12/Docker, loopback: opening a connection 180 → 6 ms, `CreateChannel` 88 → 4 ms, and the server suite (457 tests) from 12 min 59 s to 50 s.** Found by pascal-dfe-broker, whose publisher waits for one confirm per message. On Windows the loopback hides the problem (that is why it only showed up on Linux). Delphi side (`ws2_32` directly, so as not to make `TSocket` ambiguous) **confirmed by the user on 2026-09-19 (Delphi Win32): `AMQP.ServerTests` 458/458 in Debug and 462/462 in OpenSSL, 0 leaks.**
- `TThread.WaitFor` called from the **main thread** in FPC/Linux waits in 100 ms steps (`CheckSynchronize`): each join of `Close/Destroy/Stop` done by the main thread costs up to ~0.1 s. It is the RTL; it does not affect worker threads.
- **The FPCUnit runner calls `SetMultiByteConversionCodePage(CP_UTF8)`, and that can BLIND a test.** With `DefaultSystemCodePage = 65001`, `AmqpUtf8Encode` of a string built byte by byte is a passthrough — so a codec that (wrongly) passes binary through a string looks correct **inside the suite**. In a pure FPC console app, which starts with codepage 1252, the same 256 bytes become 401. A test that depends on encoding must **pin the codepage it wants to test** and restore it in the `finally`, instead of inheriting the runner's.
- **`TThread.WaitFor` is NOT idempotent in FPC/Unix.** On Windows it is `WaitForSingleObject`, which on an already-signaled handle returns immediately, as many times as you like. On Linux it is an **unconditional** `pthread_join` (`rtl/unix/tthread.inc` → `WaitForThreadTerminate`), and calling it twice is undefined behavior — if the `pthread_t` has been recycled by a new thread, the second join waits for the **wrong** thread, forever. Either **nil the reference right after the join** (`WaitFor; FreeAndNil(FThread)` — which is what the client already does), or **guard the join with a lock + flag** when the object outlives the join (which is what `TAMQPFrameWriter.Stop` and `TAMQPServerConnection.WaitFor` do). A comment saying "safe to call more than once" on a join is true only on Windows.
- **The calling convention of `IInterface` depends on the PLATFORM in FPC**: `stdcall` on Windows, `cdecl` on Unix. A class that reimplements `_AddRef`/`_Release` (for a no-op refcount, for example) declaring a fixed `stdcall` **compiles on Windows and fails on Linux** with `No matching implementation for interface method "_AddRef:LongInt; CDecl"`. Use `{$IFDEF AMQP_WINDOWS}stdcall{$ELSE}cdecl{$ENDIF}`. That is what kept the broker sub-module from compiling on Linux from Phase 2 to Phase 4.
- **A single test body for both compilers is right for the assertions and wrong for the RTL.** Since the test kit (see "Mirrored tests"), the DUnitX master is the only text; every block that calls the RTL in a way that differs between the compilers — temp dir, ignoring a test, exception of an exact class — goes into `tests\AMQP.TestSupport.pas` (with `{$IFDEF FPC}` inside it), never into the body. `GetTempDir` or `SysUtils.DeleteFile` in the body compile in FPC and only dcc32 refuses them; check [5] of `check_mirrors.py` catches it. (Before the kit, three defects with this cause cost three round trips through the IDE in a single round.)
- **In Delphi, the default RTTI only publishes `public` and `published` methods** — a DUnitX attribute (`[Setup]`, `[TearDown]`, `[Test]`) in a `private`/`protected` section **compiles and is never found**. On a `[Setup]` this makes the whole fixture die in an access violation reading a nil field; on a `[Test]`, it silently disappears from the suite. There is no warning on the FPCUnit side (there the visibility that matters is `published`, and the generator puts it in by itself). Check [4] of `check_mirrors.py` catches it.
- **The mirror generator does not accept inheritance between fixtures** (`[TestFixture] TX = class(TBase)` is an error). Fixtures that share state keep their own fields and call routines of the unit with the fields as same-named parameters (`ServerSetUp(FBroker)`, `Params(FBroker)`, `WalSetUp(FDouble, FWalFile)`); a base with a single descendant was folded into it. The skill is not edited from here: if the pattern gets in the way, the proposal goes to the generator over there.
- **With the `Windows` unit in the `uses`, `Winapi.Windows` shadows names from `System.SysUtils` and the error only shows up in dcc32.** Measured: `FindClose` (the Windows version takes a `THandle`, the SysUtils one takes a `var TSearchRec` — gives `E2010 Incompatible types`) and `DeleteFile`. `FindFirst`/`FindNext` do **not** collide (there they are `FindFirstFile`/`FindNextFile`). Qualify: `SysUtils.FindClose(...)`.
- **`Halt` called from inside a routine LEAKS the managed locals.** It abandons the stack frames without finalizing the strings, `TBytes` and interfaces of the routines on it — heaptrc reports it as a leak, and correctly. Measured in `CrashHostFpc`: four constant blocks, independent of the work done, which disappear by replacing `Halt(n)` with `ExitCode := n; Exit`. Applies to any program in this codebase.
- **`DateTimeToUnix(LocalTimeToUniversal(Now), False)` converts TWICE** (the `False` says "the input is local, convert it"), and the error is **invisible on a machine in the UTC time zone** — every container and most Linux servers, where `LocalTimeToUniversal` is a no-op and the double conversion adds zero. Measured: +4 h on this machine, 0 in the container. For epoch in ms use `Round((utc - UnixDateDelta) * 86400000)`, which depends neither on the semantics of the flag (which differ between the compilers) nor on the RTL zeroing the ms before the internal `Round`.
- **Delphi Win64: `Length` of a dynamic array, `.Count` of a generic collection (including `TAMQPFieldTable`) and `TValue.GetArrayLength` are `NativeInt` (= `Int64`)**, and DUnitX's generic `Assert.AreEqual(3, Length(B))` does not infer a single `T` (`E2532`). The kit's `TAssert` has concrete overloads (`Integer`, `Int64`), so the problem is gone from the tests; it still applies to code that uses the DUnitX `Assert` directly. `Length` of a string is still `Integer`.
- **The kit's `TAssert` has no `QWord`** (FPCUnit's has; Delphi doesn't even have the type): compare `UInt64`/`Cardinal` with a cast to `Int64` (`TAssert.AssertEquals(Int64(12), Int64(LDecoded.DeliveryTag))`) or through a `Check*` with the type fixed. It also has no `AssertNotNull` (`TAssert.AssertTrue(msg, Assigned(X))`) nor `AssertException` (`CheckRaises` from `AMQP.TestSupport`, which requires the **exact** class, like FPCUnit's — DUnitX's `Assert.WillRaise` accepted a subclass). For "any exception": a manual `try/except` with a boolean flag + `AssertTrue` (not `Fail()` inside the `try` itself, which would be caught by the `except`).
- `System.Threading` (`TParallel.For`) does not exist in FPC — use `PcPool.Queue(TPcWorkItem)`. Careful when sharing arrays between the work item and the caller: a constructor parameter typed as `array of T` is an *open array* (it copies the elements) — use a named dynamic-array type as the parameter to really share the same buffer.
- Quoting a directive such as `{$IFDEF FPC}` inside a prose `{ ... }` comment breaks compilation: the `}` of the quoted text closes the comment early. Write "conditional" or similar instead of the literal `{$...}` when documenting this in comments.
- FPC's `TThread.Queue`/`.Synchronize` only have the `TThreadMethod = procedure of object` overload (no parameters) — no anonymous-closure overload. Every `TThread.Queue(nil, procedure ... end)` call has to become a named method; with several threads calling concurrently, use a disposable per-call "marshal" object (data + `procedure Execute; begin Form.Metodo(...); Free; end;`), not a shared field on the form.
- `System.TMonitor` does not exist in FPC → `TCriticalSection` (`SyncObjs`).
- **Inline `TypeInfo(TArray<TValue>)` does not match `TAMQPValueArray`** (FPC 3.2): the generic specialization written inline in a unit is distinct from the `AMQP.Wire` alias that the decoder actually produces — comparing `TValue.TypeInfo` with the inline form gives False silently. Use the `TAMQPValueArray` alias, or (better) don't test the array's type and call `AmqpUnwrapValue` on every element.
- **`TValue.GetArrayElement` over `TArray<TValue>` returns the element re-wrapped — in Delphi AND in FPC**: a `TValue` of `Kind=tkRecord` containing the inner `TValue` — `IsObject`/`IsArray`/`As*` fail on the wrapper. Fix: `AmqpUnwrapValue` (AMQP.Wire), idempotent — use it after **every** `GetArrayElement` of an array of field-values, **without `{$IFDEF}`**. This note used to say that Delphi collapsed TValue-in-TValue and only FPC wrapped: **wrong**, measured on 2026-10-02 (probe `p30_tvalue_nested` of the `dual-compiler-delphi-lazarus` skill, identical output on Delphi 12 and FPC 3.2.2; `TValue.Make` in Delphi 12's `System.Rtti.pas` has no collapsing branch). The code was always right because the unwrap was never behind a conditional.
- **FPC discards `TThread.Queue(nil, ...)` posted by a thread that dies before the main thread pumps the queue**: `TThread.Destroy` calls `RemoveQueuedEvents(Self)`, which matches by the poster's `ThreadID` even with `AThread=nil`. Delphi is not affected (it matches only by the `Thread` field, which stays `nil`). It bites callbacks that run on a thread that ends right after (e.g. reconnection). Fix: hop through a `PcPool` worker (persistent threads) with a `TPcWorkItem` that does the `TThread.Queue` from there.
- `ReportMemoryLeaksOnShutdown` (a `System` global) does not exist in FPC → `{$IFNDEF FPC}` around the assignment in the `.dpr`.
- LCL has no `Font.Charset` nor `TForm.DesignSize` the way Delphi's `.dfm` stores them — omit those lines when writing the equivalent `.lfm`.
- `uses Windows, Messages` in the GUI samples does not compile outside Windows → LCL's emulation layer: `LCLIntf` (`GetScrollInfo`/`SendMessage`), `LCLType` (`TScrollInfo`, `SIF_ALL`, `SB_VERT`, `SB_BOTTOM`) and `LMessages` (`LM_VSCROLL`, same `$0115` value as `WM_VSCROLL`).
- FPC/Linux without `cthreads` as the first unit of the `program`: `SyncObjs`/events fail at runtime with `ESyncObjectException`. Applies to any new program that uses the library on Linux.
- FPCUnit runners must not import `Forms`/`Interfaces`/`GuiTestRunner` unconditionally (it forces linking against LCL even in console mode) — move them under `{$IFDEF MSWINDOWS}`; outside Windows always in console mode.
- **SIGPIPE on Linux**: `send()` on an already-closed socket kills the process (exit 141) instead of returning an error. It used to be handled in `TAMQPTcpSocket.Send` with `MSG_NOSIGNAL`; since v0.6.0 it is pascal-common-faa's POSIX endpoint that handles it.

## Dependency: pascal-common-faa (F8)

Since F8 of the `../pascal-common-faa` plan (2026-10-04), atomics, `PcTickMs`, the monitor and the pool come from there — they were an identical, line-by-line copy of the same origin that pipes and redis carried. Rules that apply from now on (pascal-common-faa's own are in its `CLAUDE.md` and `docs/migrating.md`):

- **Submodule `external/pascal-common-faa`** (pinned tag — v1.27.0 since v0.6.0, the one with the TCP/TLS transport; checkout **without** `--recursive` — it has its own `external/pascal-jsonmapper-faa`, which we don't care about). It serves **only** tests, samples and CI: the application provides the single copy. **Never** change pascal-common-faa from here — whatever needs to change there goes into `.ci/f8-findings-for-pascal-common-faa.md`.
- **Packages**: `pascal_amqp_faa.lpk` and `pascal_amqp_faa_server.lpk` require `pascal_common_faa` **by name only**, with `MinVersion` 1.27 (since v0.6.0) — a `DefaultFilename` pointing into `external/` would make Lazarus fall into the private copy (the diamond it forbids). Every test/sample `.lpi` lists `pascal_common_faa` **first**, with `DefaultFilename` in `external\pascal-common-faa\packages\` and `Prefer="True"` (without `Prefer`, a copy registered in the IDE silently wins). Every `.dproj` has `external\pascal-common-faa\src` in the search path.
- **Minimum version check in `AMQP.Threading`**, right after the `uses` that brings `PascalCommon.Version` (the `$IF` only sees constants of an already-used unit). That is why `AMQP.Threading` stays in the `uses` of `AMQP.Connection` and of `AMQP.Server.Engine` even without using `AmqpWallMs` there: it is through it that every user of the client or the broker compiles the check (FPC gives the "unit not used" hint — that is expected). Measured: raising the minimum above the submodule's version stops the build with `Fatal: User defined: pascal-amqp-faa precisa da pascal-common-faa ...`. **Since v0.6.0 the minimum is 1.27.0** (`< 12700`): it is the one that brings the transport (`PascalCommon.Transport*`). (1.8.0, the minimum from v0.2.0 to v0.5.0, brought `PascalCommon.Tracing`.) (1.1.3, the minimum of v0.1.2, is the one that fixed the `PcPool` burst, where the client's callbacks run.)
- **Rename with `\b`, always**: `TAMQPMonitorThread` (the broker's monitor thread) is another type, and a `s/TAMQPMonitor/TPcMonitor/` without a word boundary runs over it.
- **Finalization**: `PcPool` is freed in the finalization of `PascalCommon.ThreadPool`, **after** the amqp units that use it. No amqp finalization frees an object with work in the pool: the only one left was the `GLibLock` of `AMQP.Transport.OpenSSL`, which only `EnsureOpenSsl` (opening a TLS connection) touched — since v0.6.0 the OpenSSL is pascal-common-faa's and amqp has no finalization with state at all — and no work item of the library opens a connection (reconnection is a `TThread` of its own, not a pool item). The client's items (`TAMQPDeliveryWork` & co.) only touch channel/connection, which the **user** frees before the end of the program (and `DrainInFlight` waits, counting from enqueueing). If one day an amqp finalization frees something with work in `PcPool`, the pattern is the one in `migrating.md` over there: count from entry into the queue, decrement in the item's **destructor**, wait by polling.
- **`TPcThreadPool.Destroy` runs the entire queue** before returning (it never discarded); only an item received **after** `Destroy` has started is freed without running. The header of `AMQP.Server.Queue` said the opposite and was fixed.
- **Up to v1.1.2, `TPcThreadPool` did not grow in a burst** (`Queue` only created a worker with `FIdle = 0`, counting as idle whoever had already been woken): with 1 idle worker, 17 blocking items ran **1**. That was the cause of the intermittent `ConsumesAll_WithAck_And_Concurrency` (peak 1). Found here, **fixed there in 1.1.3** and checked with the submodule at 1.2.0 (repro: 16 of 17 start; the consume suite, 40 of 40 at `--cpus=1`). A test that needs to saturate `PcPool` still enqueues **one item at a time, waiting for each to start** (it is the deterministic way of knowing that every worker runs OUR item), and saturates **inside** the `try` that opens the gate: a forgotten blocker poisons tests of other units.
- **In FPC 3.2.2/Linux `TThread.ProcessorCount` is 1**; pascal-common-faa 1.2.0 counts the real cores (`PcProcessorCount`), and the `PcPool` ceiling in the container went from 16 to 48. Use `PcPool.MaxWorkers`, never the formula.
- **64-bit counters**: every target of `PcAtomicRead64/Write64` here is `UInt64` (ticks, LSN, journal bytes) and falls into the `UInt64` overload — a `var` parameter requires the exact type, so the `Int64` overload is not even a candidate.

## Outbox bridge (v0.5.0) — `src/outbox`, decision 11 of M7 of pascal-agenda-faa

`AMQP.Outbox` is pascal-agenda-faa's `Agenda.Outbox.Amqp` with the same API (`TOutboxAmqpSink`, `TOutboxAmqpConsumer`, `TOutboxAmqpQueue`, `OutboxAmqp*`, constants `PROCESSED_SQL_*`). Manual in `docs/outbox.md`. Live rules:

- **Outside both `.lpk` files, on purpose** (like pascal-api-infra-faa's `src/redis`): it needs pascal-db-faa (≥ 0.18.0, `PascalDb.Outbox`), which the client and the broker don't need. Never add it to a package. Whoever compiles it puts `src/outbox` in the search path and, in Lazarus, `src` in *Include files* (the package does not export the include path of `amqp.inc`).
- **Submodule `external/pascal-db-faa`** (pinned tag, checkout **without** `--recursive`: it has its own copies of pascal-common-faa and jsonmapper, which we don't use). It serves **only** the `tests/Outbox` suite. The application provides pascal-db-faa, as it provides pascal-common-faa; never change it from here.
- **The clock is pascal-common-faa's `TClock`** (`DateTimeToUnix(TClock.Now, False)`; the `False` says "the input is local", same meaning on both compilers). In agenda it was pascal-api-infra-faa's `TJwt.UnixNow`, used only as a clock — the M7 review removed it so that the bridge would not pull in a third library. pascal-common-faa has no ready-made "now in Unix seconds"; if a second user shows up, the proposal goes to its `docs/plan.md`, not here.
- **The SQL is the application's, by name** (`PROCESSED.EXISTS/INSERT/PURGE`), like `PascalDb.Outbox`'s. The reference form (`ON CONFLICT ... DO NOTHING`) is only tested on SQLite.
- **Its own suite, `tests/Outbox`** (8 tests, embedded broker + SQLite file; `AMQP.OutboxTestDb` concentrates the SQLdb/FireDAC `{$IFDEF FPC}`, outside the test bodies). It stays out of the other suites so that they don't gain a database dependency. FPC on Windows needs the `sqlite3.dll` **from sqlite.org** (64-bit; Python's lacks the metadata functions — gotcha 23 of pascal-db-faa) next to the runner, or `AMQP_SQLITE_CLIENT`; it is in `.gitignore`. Local copies: `../pascal-db-faa/.deps/sqlite-3.53.4/{x86,x64}`. On Linux, `libsqlite3-0` (`tools/test_fpc_docker.sh` adds the layer if the image doesn't have it).

## Client tracing (v0.2.0) — phase D of pascal-api-infra-faa's observability

`AMQP.Tracing` + the channel open OpenTelemetry spans through `PascalCommon.Tracing` (pascal-common-faa 1.8): `publish <exchange>` (producer, child of the current span), `process <queue>` around the `Consume` callback (consumer, child of the message's `traceparent`) and `receive <queue>` in `BasicGet` (client). Manual, the 11 decisions and the tests in `docs/tracing.md`; **do not re-derive from scratch**. Live rules:

- **Only the client opens spans** (the user, 2026-10-12). The broker passes the header through byte for byte (D1); spans in the broker run into D2/D30 and remain future work.
- **The `traceparent` goes only into the BYTES** (`BuildContentHeader` with trace → `WriteFieldTable` with extra pairs): the caller's `TAMQPFieldTable` is never touched. If it already has a `traceparent`, nothing is injected; a loose `tracestate` stays the caller's (field-table without repeated names).
- **`OnConsumerError` runs INSIDE `process`** (v0.4.1): in the `except` of `TAMQPDeliveryWork.Execute`, `HandleConsumerError` comes before `AmqpFinishSpan(LSpan, E)` (in a `try/finally`), so the handler's log reads the trace id from `TPcTracing.Current`. In 0.4.0 the order was the reverse and the handler ran without a span; the test `OnConsumerError_RunsInsideProcess` catches a regression.
- **Every span is born and ends in the same call, on the same thread** (the threading rule of `PascalCommon.Tracing`): the publish ends on leaving the frames, not on the confirm; `process` ends in `TAMQPDeliveryWork.Execute`. Nothing here needs `StartDetachedSpan`. If one day a span has to end on another thread (on the confirm, on the ack), it is `StartDetachedSpan`, never a current span.
- **Off, zero cost**: every function of `AMQP.Tracing` looks at `TPcTracing.Enabled` first, and a publish without a span builds the header through the old path (identical bytes, tested).
- The queue name for `process` comes from `FConsumerInfo` (tag → queue and no-ack, under `FConsumersLock`; it was `FConsumerQueues` up to v0.3.0): every `FConsumers.Remove` has its counterpart there (a Consume that fails, `Cancel`, the server's `Basic.Cancel`); reconnection doesn't clear it, because the consumer comes back with the same tag.
- Tests: `AMQP.TracingTests` (unit, 10) and `AMQP.ServerTracingTests` (server, 10, real client against the embedded broker, `TPcTracing.Start(..., False)` + `FlushNow`, waiting for the SPAN and not for the callback, because `process` ends after the callback returns).

## New pieces compared to the original library

- **pascal-common-faa** (a dependency since F8 — see its own section above): atomics and `PcTickMs` (`PascalCommon.Threading`), `TPcMonitor` (condvar by event generations — no lost wakeups; waiters re-check the condition in a loop) and `TPcThreadPool` (grows on demand up to `max(16, 4×cores)`; persistent workers; `PcPool` is the pool of the **whole process**, shared with the other `*-faa` libraries) in `PascalCommon.ThreadPool`. That is what `AMQP.Threading` used to have; only `AmqpWallMs` and the minimum version check remained in it.
- **pascal-common-faa's transport (v0.6.0, step 5 of its `docs/transport-design.md`)**: the client connects with `PcTcpConnect` + `PcTlsWrap` and the broker listens with `PcTcpListen`/`PcTlsListen`; `CloseAbort` (any thread, idempotent) is what unblocks the read thread. What remained in `AMQP.Transport`: the exceptions, `TAMQPEndpointStream` (subclass of `TPcEndpointStream`) and the options (`AmqpTcpOptions`, `AmqpDefaultTlsBackend`). Rules:
  - **`TAMQPEndpointStream` is the exception boundary (T6)**: no `EPcTransport*` leaves the library. On reads, `EPcTransportClosed` becomes **0 bytes** (`TAMQPFrame.ReadFrom` raises the usual `EAMQPFrameEOF`, and the read loop treats it as a normal close — a connection reset is also `Closed` in the common library); `EPcTls` becomes `EAMQPTls`, the rest `EAMQPTransport`. On writes, everything raises. Errors outside the stream (connect, `Handshake`, listen) go through `AmqpRaiseTransportError` at the point where they happen.
  - **`EAMQPTls` does NOT inherit from `EAMQPTransport`** (both from `Exception`), on purpose: an old `except on EAMQPTransport` must not start catching TLS. Test `EAMQPTls_DoesNotInheritFromEAMQPTransport`.
  - **No socket deadline**: AMQP has heartbeats. `SetIoDeadline`/`SetRead/WriteDeadline` are never called (they start at 0). The only deadlines are the connect one (`ConnectTimeoutMs`, 0 = the common library's 10 s) and the TLS handshake one (the common library's 15 s, which `TPcTlsEndpoint` itself removes when done).
  - **`AMQP.Transport.Tls` and `.OpenSSL` are empty, obsolete shells** since v0.6.0 (they only pull in the common library's units); they go away in the next minor.
- Work items in `AMQP.Connection` (implementation): `TAMQPDeliveryWork`, `TAMQPReturnWork`, `TAMQPConfirmWork`, `TAMQPBlockedWork`, `TAMQPUnblockedWork`, `TAMQPReconnectThread` — they replace the `TTask.Run` closures; the in-flight counter is decremented in the `finally` of `Execute`.
- **`TAMQPReconnectThread` is not `FreeOnTerminate`** (v0.1.1): the connection keeps the reference under `FReconnectLock` and **joins** it only once (`StopReconnect`, called by `Close`, or before creating the next one), without a deadline; the wait between attempts is `FReconnectWake`, which `Close` signals. A `Close` coming from a callback that runs on it (`OnDisconnect`/`OnReconnect`/`OnReconnectFailed`) skips the join. Before, it was `Sleep` + polling with a 12 s cap, and with a longer delay the thread outlived the freed connection. `AmqpReconnectThreadsAlive` is the proof in the tests.
- **Reconnection replay belongs to the CONNECTION, phase by phase** (`TAMQPRecoveryPhase`: channel → exchanges → queues → binds → consumers, channels in `ChannelId` order; `BeginRecover`/`ReplayRecovery`/`EndRecover`, with each channel's `FRpcLock` held from start to finish). Never iterate `FChannels.Values` expecting an order: it is the hash's (measured: channels 1, 2, 3 → 3 first). Channel by channel, a queue declared on one channel and consumed on another got 404 on every attempt, forever. **A failed attempt is never silent**: `OnReconnectError` + `LastReconnectError` + the reason in the text of `EAMQPConnection`.
- **Publish on a non-writable connection raises `EAMQPConnection` without touching the stream** (`FWritable`, atomic; the handshake writes through `SendHandshakeMethod`, which doesn't look at the flag); a stream write failure also becomes `EAMQPConnection`. In `ReadThreadFinished`, **the reason (`FLostReason`) is recorded BEFORE lowering `FWritable`/`FIsOpen`** — in the reverse order, the Linux container caught a publish with "connection is not open" right after `IsOpen` dropped.
- **An exception in a consumer callback never goes to the pool** (v0.4.0): `TPcThreadPool` swallows it without a hook, and the delivery stayed unacked forever (with `Qos(1)`, the consumer stopped). `TAMQPDeliveryWork` calls `HandleConsumerError` → `OnConsumerError` → the action's `Nack` (default without requeue). **Never settle twice** (406 closes the channel): the library only sends the `Nack` if the tag is still in `FUnsettled` (registered on dispatch, removed by `Ack`/`Nack` and at the end of the callback), checked **after** the handler. There is no session epoch on purpose: `RunReconnect` drains every old callback (`DrainAllChannels`) before reopening the channels, so a late `Nack` always lands on the dead socket — measured, see the v0.4.0 worklog.
- **`Close` of a channel with an active consumer: Cancel → drain → `Channel.Close`** (v0.4.2, found by pascal-agenda-faa). Before, `Channel.Close` went first and the `Ack` of an in-flight callback went out after the Close-Ok: a **connection** `504` (measured on RabbitMQ 3 and on the embedded broker). Safety net: `FClosing` under `FAckLock`, which `Ack`/`Nack` hold from the check until the frame goes out, set before `Channel.Close` (Close) and before `Close-Ok` (closing by the broker) — `Ack`/`Nack` on a closing channel become a silent no-op. **Channel only**: a connection drop does not set `FClosing`, and an `Ack` after it still raises `EAMQPConnection` (the user's decision). Against RabbitMQ, an `Ack` right after the Close-Ok is tolerated (the channel stays in "closing" there); the test `AckAfterClose_DoesNotDropTheConnection` only kills the mutation on the embedded broker (acceptance).
- **`Close`/`Free` of a channel wait for the callbacks from ENQUEUEING**, without a deadline, on purpose (measured and decided in v0.1.1): on a regular channel this depends on `PcPool` moving; the way out is `CreateChannel(True)`, not a deadline.
- TLS with two backends (pascal-common-faa since v0.6.0), **chosen at run time** (`TlsBackend` on the client and on the broker): on Windows both in every build, elsewhere only OpenSSL. **`-dAMQP_OPENSSL` only changes the default** (`AmqpDefaultTlsBackend`). Private CA (`TlsCaFile`, PEM on both) and mTLS on the client and on the broker; one's own certificate is a PEM pair on OpenSSL and PFX + password on SChannel (T7 over there). The test PKI is the common library's `tests/pki`, found through the submodule (`Pki()` in `tests/AMQP.TestSupport.pas`; PFX password in `PKI_PFX_PASSWORD`).

## Broker (server) sub-module — Phases 1, 2 and 3 complete (branch `feat/broker`)

Units `AMQP.Server.*` in `src\server\`, a separate package `pascal_amqp_faa_server.lpk` that depends on the client package — whoever only uses the client links nothing from the server. It is the "other end": a library to **create an AMQP 0-9-1 broker inside a Delphi/FPC app**.

**Non-goals (all phases):** cluster, HTTP management API, federation/shovel, AMQP 1.0, STOMP/MQTT, quorum queues, streams, persistence/recovery (that is Phase 4, model already pre-decided — see the section below), per-vhost permissions.

**WS-by-WS history of each phase** (bugs, mutations, test counts): `docs/broker-worklog.md`.

### Locked architecture (applies to all three phases)

- **Execution model: thread-per-connection, blocking I/O** (reuses pascal-common-faa's endpoint, `TPcMonitor`, `TPcThreadPool`; `CloseAbort` unblocks a pending read). Event loop (IOCP/epoll/kqueue) rejected — 3 backends, none of which exists in the shared units, and the target is tens to hundreds of connections.
- **Writing: 1 writer object per connection with a bounded outbound queue + 1 writer thread** (natural backpressure = TCP flow control). `Connection.PostFrames(array of TAMQPFrame)` enqueues method+header+body under a single lock (otherwise the client sees UNEXPECTED_FRAME from interleaving). `TryPostFrames` (WS4 of Phase 2) is the variant that neither blocks nor raises, for use inside actors.
- **Engine: actor-per-queue** — each `TAMQPServerQueue` has a serial command queue scheduled on a `TPcThreadPool` **owned by the `TAMQPServer`** (work item + "already scheduled" flag, **not** a thread per queue — decision D2; its own pool, not `PcPool` — D37). Every mutation (enqueue, consumer, ack/nack, TTL, delete) goes through it. **No actor command may block the worker waiting for I/O.** Exchanges are a near-immutable lookup under a `TMultiReadExclusiveWriteSynchronizer` per vhost (`AMQP.Server.VHost`).
- **Message**: `TAMQPMessage` (`AMQP.Server.Message`) with an atomic refcount (`PcAtomicInc/Dec`); `Body: TBytes` shared by N queues without copying (COW), nobody mutates it. **It does not keep decoded properties** — only the raw `HeaderPayload` (decision D1); whoever needs the properties decodes the channel's live table before the enqueue.
- **A slow consumer leaves the round-robin without blocking the actor**: delivery is a non-blocking post via `IAMQPDeliveryTarget.TryDeliver`; if it refuses, it leaves that round's round-robin and the next one tries again.
- **`TAMQPChannelDeliveryTarget`** is a `TInterfacedObject` separate from `TAMQPServerChannel` on purpose — the channel may die while the actor, on a pool thread, is in the middle of a delivery; the target survives by refcount and `Detach` zeroes the writer under a lock without waiting for I/O.
- **Connection lifetime**: each `TAMQPServerConnection` owns its read thread/writer/channels; it registers/unregisters itself with the broker under a lock; freeing is done by an **explicit reaper** (the broker's monitor thread, `TAMQPMonitorThread`, every `AMQP_SERVER_MONITOR_TICK_MS`), **never `FreeOnTerminate`**. The same monitor thread pokes the heartbeat, the Close-Ok deadline, message expiration (TTL) and the `x-expires` of idle queues.
- **Codec**: the `Decode` of client→server methods and the `Build` of server→client ones live **in-place** in the existing `AMQP.*.Methods` units (they add functions, they don't change the existing ones) — the client suite has to stay green after every change. The listener is the common library's `TPcListener` (port 0 → `TPcListener.Port`, T1); the connection receives a `TPcEndpoint` and runs the `Handshake` (server TLS) on **its own thread**, never on the accept thread. The certificate is loaded **at `Start`** (`EAMQPTls` there, broker stopped), and a `Start` that cannot listen undoes what it had already brought up (journal, notifier). `Backlog` is ignored (the common library uses its own).
- **Error model**: `EAMQPChannelError` (Channel.Close, the connection survives) vs. `EAMQPConnectionError` (Connection.Close + wait for Close-Ok) vs. `EAMQPServerAbort` (drops the socket without a Close), in `AMQP.Server.Types`.

### Auth / vhost

SASL PLAIN only (no `Secure`/`Secure-Ok`, no `AMQPLAIN`). `IAMQPAuthenticator` + `TAMQPStaticAuthenticator` (the broker's default, seeded with `guest`/`guest` — the client's `TAMQPConnectionParams.Localhost` connects without changes) + `TAMQPAllowAllAuthenticator` (tests). `TAMQPVirtualHostRegistry` default `{ '/' }`. `IAMQPAuthorizer` exists as an allow-all stub.

### Locked decisions — Phase 2 (D1–D8)

1. **The message carries the raw content-header payload**, not a clone of the `TAMQPFieldTable`: faithful byte-for-byte re-emission, without FPC's `TValue`-in-`TValue`. Matching of headers bindings uses the **channel's live** table, before the enqueue.
2. **The queue actor runs scheduled on a thread pool**, not a thread per queue — no actor command may block waiting for I/O. *(It was the global `AmqpPool`; since F8 it is the `TAMQPServer`'s own pool — D37.)*
3. **A slow consumer leaves the round-robin**: delivery is a non-blocking post; if the outbound queue refuses, the consumer is suspended until it drains.
4. **`Basic.Recover` implemented with `requeue=true`**; `540` for `requeue=false` — a deliberate deviation from RabbitMQ.
5. **Exchange→exchange bindings supported** (D5), with a visited set per publish and `AMQP_MAX_EXCHANGE_HOP_DEPTH = 16` (the graph can have cycles).
6. **`durable` and `delivery-mode 2` accepted and ignored** in Phase 2 — a deliberate deviation; refusing would break clients that always declare durable.
7. **Memory safety cap**: global `TAMQPServer.MaxQueueLength` (default 0 = unlimited; on overflow, drops from the head). The broker runs *inside* the user's app. Per-queue `x-max-length` (Phase 3, WS6) composes with it by the **smaller** of the two.
8. **The client's integration suite runs against the embedded broker**, except tests of Phase 3 features — each exception becomes an explicit backlog item, not a "skipped" test. (Backlog closed in Phase 3, WS6.)

**Invariant**: binding *matching* runs on the publisher's thread (exchange table near-immutable under an RWLock; the channel's live headers table). Only the *enqueue* crosses over to the queue actor.

### Locked decisions — Phase 3 (D9–D18)

9. **Persistence does not enter Phase 3; Phase 4 is a WAL with batched fsync.** Append-only journal, group commit, its own writing thread (never inside the actor, preserves D2), asynchronous `Basic.Ack` emitted as a prefix with `multiple=true`.
10. **D1 stays; rewriting a header creates a new message, with the body shared.** Lives in `AMQP.Server.Header` (`TAMQPHeaderEditor` + `AmqpDeriveMessage`), not scattered through the actor.
11. **Writing arrays of field-values goes into `AMQP.Wire`** (a client unit): `WriteFieldValue` gained `tkDynArray` (by name — the ordinal differs between FPC/Delphi), with `AmqpUnwrapValue` on each element. The 121 unit assertions are the gate, on both compilers.
12. **Priority by buckets, not by heap; `x-max-priority` limited to 0–9** (406 above that, not a clamp — a deviation from RabbitMQ, which accepts up to 255). N+1 `TQueue`s, FIFO within a level. A requeue goes back to the head **of its own bucket**. Dropping by cap **starts with the LOWEST-priority bucket**.
13. **Lazy expiration at the head + a sweep on the monitor's tick.** Injectable clock (`NowTick` protected virtual) — a TTL test does not depend on `Sleep`.
14. **Dead-letter cycles cut by DEPTH** (`AMQP_MAX_DEADLETTER_HOPS = 16`), not by a visited set — the sum of the `x-death` `count`s above the cap drops the message and counts it in `DroppedCount`.
15. **`x-overflow: reject-publish` uses a SYNCHRONOUS enqueue** (`TryPostMessage`), and only in those queues. *(It was planned to be replaced in Phase 4; measured against the design of D24, **it doesn't need to be** — the synchronous enqueue does no I/O, so the refusal is known before the pending confirm is registered.)*
16. **`durable` and `delivery-mode 2` are still accepted and ignored** (D6 still applies) — "nothing survives a restart" is highlighted in the README, not in a footnote, because TTL/DLX/priority now really work. *(From Phase 4 on this applies only with an empty `DataDir` — see D19.)*
17. **Dead-lettering runs inside the actor** — rewriting a header is CPU, routing is reading topology under an RWLock and posting to another mailbox; neither waits for I/O (D2 preserved). The actor runs commands **outside** its own mailbox's lock, so it never holds two mailbox locks at the same time.
18. **Per-vhost permissions stay out**, tied to a future security phase together with guest restricted to loopback and a delay/rate-limit after an auth failure (the `APeerAddress` of `Authenticate` is already ready for that).

### Locked decisions — Phase 4, durability (D19–D28)

Planned on 2026-09-04, in a session of its own and in Opus. Complete plan with the measurements: artifact `Broker AMQP — Fase 4` (https://claude.ai/code/artifact/46b89cbc-060b-406c-b10b-31f9e8c99bd1). **D9 had already fixed the MODEL** (append-only WAL, batched fsync, its own journal thread so that D2 keeps holding, asynchronous confirm as a prefix with `multiple=true`); these ten fix the DESIGN. WS-by-WS history in `docs/broker-worklog.md`.

19. **Persistence is opt-in through `TAMQPServer.DataDir`.** Empty (default) = the broker is exactly the Phase 3 one, and D16 still applies; set = durability on. Same shape as `UseTls`. The broker runs *inside* the user's app: nobody gets a file on disk for having called `Start`.
20. **The classic rule of three, no deviation:** a message goes to disk when it has `delivery-mode=2`, is published to a `durable` queue, on a broker with a `DataDir`. **A non-durable queue never touches the journal** (Phase 3's hot path stays intact). `delivery-mode` is read by the publisher's thread, together with priority and `expiration` (the reason for D1). An `exclusive` queue is **never** persisted; a durable `auto-delete` queue is, and comes back with `EverHadConsumer=False` (otherwise the guard from WS7 of Phase 2 would delete it at boot).
21. **The monotonic clock never goes to disk.** The journal records `EnqueuedAtWall` (ms since the epoch, UTC) + `EffectiveTtlMs`; recovery recomputes `ExpiraEm := NowTick + max(0, Ttl - (NowWall - EnqueuedAtWall))`. Monotonic in memory, wall clock on disk, conversion only at the two boundaries — an NTP jump does not affect a live queue. A message already expired at restart goes through the **normal expiration path** (dead-letter included), in the pass that runs after topology and entries are loaded. **`x-expires` restarts on recovery** (a recovered queue counts as used now — otherwise the broker would delete durable queues at boot). The virtual `NowTick` (D13) gets the sibling `NowWall`.
22. **Two kinds of record: content and placement.** `CONTENT(ContentId, Body)` written once; `ENQ(QueueId, EntryId, ContentId, HeaderBlob, Priority, EnqueuedAtWall, TtlMs)` is a placement; `DEQ(QueueId, EntryId)` retires it; `TOPO` for declare/delete. It mirrors the in-memory COW, and dead-lettering stops being a special case: **a new ENQ with the same `ContentId` and a new `HeaderBlob`, plus the DEQ of the old one** — the body is never rewritten. One journal for the whole broker, with the vhost inside the record.
23. **Atomicity by ORDER, not by a transaction marker.** Each record carries its own length and CRC32; recovery replays the longest **valid prefix** and discards the crooked tail. Where atomicity matters (dead-letter), **write the new ENQ before the old DEQ**: failing in the middle produces a duplicate, not a loss. A duplicate is the failure mode that at-least-once already admits and that the `x-death` `count` counts; loss is not.
24. **The confirm is released by a durability watermark (LSN), and whoever writes the publish batch is the PUBLISHER'S THREAD** — it is the only one that, having routed, knows which LSN needs to be durable for that seq-no. It writes `CONTENT` + N×`ENQ`, keeps the LSN of the last one, registers `pending(channel, seq, lsn)` and **emits no ack**; the journal thread, after each fsync, advances the watermark and releases every pending with `lsn <= watermark`, **collapsed per channel into a single `Basic.Ack(maxSeq, multiple=true)`** (the letter of D9). The actor does **not** write the publish's ENQ — only the retirements it decides (ack, `drop-head`, expiration, dead-letter, purge). Three locked corollaries: (a) **confirms go out in seq order per channel** — a transient publish behind a pending persistent one waits and goes out collapsed in the same `multiple=true`; (b) **the Return-before-Ack order survives** (the Return goes out on the read thread, before the pending is registered, and a message without a route generates no record) — `MandatoryNoRoute_ReturnBeforeAck_312` stays valid word for word; (c) **backpressure lives in the publisher, never in the actor** (the submission queue is bounded and the read thread *may* block on it; a retirement record is always accepted — D2 stands). Whoever emits the ack frame for a channel that may have died uses the **`TAMQPChannelDeliveryTarget` pattern** (refcounted object with `Detach` under a lock, without waiting for I/O) and `TryPostFrames`, with a refusal retried in the next batch (the shape of D3).
25. **Self-tuning group commit, without any time parameter.** The journal thread's loop: take everything in the queue → write → one fsync → release confirms → repeat. Batch of 1 under low load; under high load it grows by itself, because whatever arrives during an fsync is the next batch. MEASURED (FPC 3.2.2/Win64, 256 B records, QPC): `FlushFileBuffers` 1:1 costs **329–674 µs** (1.5k–2.2k rec/s); every 100 records, **530–1278 µs per fsync** and **78k–188k rec/s** — **35× to 50×**. Neither a wait window nor a batch size is configurable.
26. **WAL growth: segments + compaction by rewriting, a single mechanism.** Fixed-size segments (`MaxSegmentBytes`, default 16 MB); a closed segment is only deleted when every entry in it has been retired and no content of it is referenced by a live entry. Compaction rewrites the live records — **including topology ones** — at the head and deletes the segment, when the live fraction falls below `AMQP_WAL_COMPACT_RATIO` (default 25%) or when it blocks space recovery. **No separate snapshot file.** Hard cap `MaxJournalBytes` (default 0 = unlimited, the shape of D7); on overflow, the persistent publish is **refused with `Basic.Nack`** and counted — the difference that matters compared to D7: **a memory cap drops, a disk cap refuses** (dropping from the head on disk would be deleting already-confirmed data).
27. **Unacked messages come back READY and REDELIVERED, without an extra record.** Delivery is not journaled: an unacked delivery is still a live ENQ (the DEQ is only written on the ack), so the replay already returns it — and **in the right order for free**, because the journal's order is the enqueue order and the bucket is in the ENQ record, which puts it exactly where D12's `RequeueFront` would put it. The `redelivered` flag is **not** persisted: **every recovered entry comes back with `redelivered=True`** — persisting it would cost a write on the hottest path there is, and would be false precision (after a crash the broker does not know whether the consumer saw it).
28. **"Durable" is a verifiable claim, in three layers — and with an admission that goes in the README, not in a footnote: killing the process does NOT test fsync** (the OS cache survives the death of the process; only the machine going down loses it). (1) **Exhaustive truncation sweep**, in-process and deterministic: builds a small journal and recovers from *each* offset 0..N, requiring a consistent prefix state and the presence of every confirmed message — it is the anchor test, and the mutation that must kill it is removing the CRC, removing the length or inverting the ENQ/DEQ order of D23. (2) **Injectable file double** that counts fsyncs and fails at the chosen instant — proves that the fsync happens at the batch boundary and that an I/O failure does not corrupt in-memory state. (3) **Process-kill matrix** (`CrashHostFpc`, sibling of `BrokerHostFpc`), outside the runner like the SmokeTest. What the README can claim: *correct recovery for any truncation point, and fsync demonstrably called at the batch boundary.*

**D15 survives, contrary to what was expected.** It was recorded as "the only point of Phase 3 designed to be replaced"; measured against this design, it doesn't need to be: `TryPostMessage` is synchronous but **does no I/O at all**, so the refusal is known *before* the pending confirm is registered. What changes is only when the ack goes out — that is D24, not D15.

**Non-goals of Phase 4** (besides the usual ones): paging to disk / lazy queues — *durability is not paging*, the queue is still entirely in memory; `Connection.Blocked` and memory/disk alarms; persisting consumer state (an unacked message comes back ready, not unacked); recovering exclusive queues; encryption at rest; ordering between publishers beyond what the spec guarantees (per channel).

**The eleven workstreams (WS0 probes → WS11 docs) are all complete**; what each one delivered, the defects it found and the mutations that survived are in `docs/broker-worklog.md`.

### Locked decisions — Phase 4.1, observability (D29–D36)

Planned on 2026-09-06. The starting point was a WIP (commit `755a3a7`, branch `feat/broker-observabilidade`) that had the event record and `Subscribe`, but **no call site** — and an `EventSink: TObject` with a cast, actor-origin events planned as synchronous (head-on collision with D2) and `except end` in the dispatch. **Do not extend that WIP as it is**: these eight decisions rewrite it. WS-by-WS history in `docs/broker-worklog.md`.

29. **Observability is opt-in and strictly READ-ONLY: the observer never enters the decision path.** No handler can influence routing, authentication, ack or drop — whoever needs to *decide* uses `IAMQPAuthorizer`, which already exists for that. With no subscriber the cost on the hot path is **one mask read**, and the event record isn't even built (D32). It is the shape of `DataDir` (D19) and `UseTls`: nobody pays for having called `Start`.

30. **A single kind of thread: EVERY event goes through the ring and out through a dedicated notifier thread** (`TAMQPEventNotifierThread`, same shape as `TAMQPJournalThread` and `TAMQPMonitorThread`). The three alternatives were discarded each for its own reason, and none of them is "just a bit worse": **a worker of the actors' pool** (the global `AmqpPool`, at the time; the broker's own pool since D37) would starve the actor, because it is the *same* pool that runs the actors — it would be D2 violated indirectly and harder to see; **the monitor thread** would put heartbeat, the Close-Ok deadline, the TTL sweep and the reaper behind a slow handler; **inline on the read thread** (what the WIP planned for the "safe" events) stalls frame processing for that connection, heartbeat included, until the client drops it. There is no safe half: what changes between them is only the blast radius. Uniformizing gives **one contract, one order and one exception policy**, and makes the two increments differ only in *which* events are emitted, not in mechanism.

31. **Delivery contract: best-effort, drops the NEWEST under pressure, order preserved per origin.** The ring is bounded by count (`EventQueueCapacity`, default `AMQP_EVENT_QUEUE_CAPACITY`); whoever emits **never blocks and never raises** — it is D3 ("a slow consumer leaves the round-robin") applied to the observer: a slow observer loses events, it never holds the broker. Dropping the **newest**, and not the head, is deliberate: what was accepted into the ring is delivered, so the stream seen by the handler is a **contiguous prefix of the emission order with counted gaps** (`DroppedEventCount`) — dropping the head would rewrite history silently. It closes the trio of the three pressures of this codebase: **memory drops the head (D7), disk refuses (D26), events drop the newest.** The order the contract promises is **per origin** (per connection, per queue) — the ring's single consumer does in fact give a total order of acceptance, but between two threads that order means nothing and doesn't become an API promise.

32. **The shape is an interface — `IAMQPEventSink`, never a `TObject` with a cast.** *(Amendment from Inc. 2: it lives in `AMQP.Server.Events`, not in `AMQP.Server.Types` as this decision first said. The queue actor and the journal thread also emit, and neither of those units uses `Types` — declaring it there would force `Queue` and `Journal` to pull in `Auth`, `FrameIO` and `Basic.Methods` to reach an interface. The house rule points to `Events` anyway: just as `IAMQPMessageSink` lives next to `TAMQPServerMessage`, this one lives next to `TAMQPServerEvent`.)* It is the house pattern (`IAMQPMessageSink`, `IAMQPConfirmRegistry`, `IAMQPDeliveryTarget`), and `TAMQPServerConnConfig.Events: IAMQPEventSink` with **`nil` = off** is exactly how `Confirms` already behaves. Two methods: `function Wants(AType): Boolean` — a mask test, without a lock, so the hot path can skip building the record — and `procedure Emit(const AEvent)`. `Subscribe` takes the set of types the handler wants; the sink publishes the **union** as a `Cardinal` mask through the atomics of `PascalCommon.Threading` (whole-value write, lock-free read). Locked corollary: **the cap on event types is 32** — 18 used, 14 spare; going past that means changing the mask's type, not absent-mindedly adding to an enum.

33. **The notifier never dies and nothing is swallowed: `except end` is forbidden here.** A handler's exception is caught as `Exception` (catches `EAccessViolation` on both compilers), **counted** (`FailedHandlerCount`) with the class and message of the last one exposed, and the loop moves on to the next handler and the next event. **Never unsubscribe automatically** — it hides the symptom and surprises. The real danger is an AV from a handler whose owner was destroyed without `Unsubscribe`: the contract is **`Unsubscribe` before destroying the owner**, documented, and the counter is how you find out it was violated. The caveat about `EAMQPServerAbort` escaping into the teardown **ceased to exist with D30**: on the notifier thread there is no connection to abort, so those classes are counted like any other.

34. **The record stays flat, each type populates a FIXED set of fields, and the emitter always starts from a zeroed record.** Flat is what makes asynchrony safe: an event is a **by-value copy, with no pointer to a connection, channel or message that may die before delivery** — the same reason as D1 (no `TValue`, whose pain in FPC is already catalogued). Three ties: (a) **the message body never enters the event** — only `MessageSize`; carrying it would break D1's COW and put a copy on the hottest path there is; (b) the wall clock is `WallMs: Int64` via `AmqpWallMs` (epoch ms UTC), **not `TDateTime`** as in the WIP, because the `DateTimeToUnix(LocalTimeToUniversal(...))` of D21 is an invisible trap on a UTC machine, and `TickMs` (`PcTickMs`) is only for measuring latency; (c) the ring slot is **finalized on consume and on drop**, otherwise it keeps the event's strings alive indefinitely. Which type populates which fields is a frozen table in `docs/observability.md`; whatever is not on the type's row comes out zeroed, and the capture test asserts that.

35. **A test sees events through a drain barrier and through counters, never through `Sleep`.** A capture sink asserts type, fields and order-per-origin; `DrainEvents(ATimeoutMs)` waits for the ring to empty **and** the current handler to finish — it is the sibling of D13's injectable clock: determinism instead of blind waiting. Three anchor tests, each with the mutation that **must** kill it: (1) capture of type/fields/order — breaks if an emitter populates a wrong field; (2) **a slow handler over a loaded queue**, proving that the actor keeps advancing and that `DroppedEventCount` goes up — it is the proof of D2, and breaks immediately if someone swaps the ring for an inline call; (3) a handler that raises — proves that the notifier survives and counts, and breaks if `except end` comes back. FPCUnit↔DUnitX mirror mandatory from the first commit, and `AMQP.Server.Events` in **every** `.dpr`/`.dproj` that compiles the sub-module (check [3] of `check_mirrors.py` fails today because of that).

36. **Non-goals of Phase 4.1** (besides the usual ones): **aggregation** — no ready-made metrics, histograms or Prometheus format; the broker emits raw facts, the handler aggregates. **Persisting events**: this **is not an audit log**, and D31 admits loss by design — it goes in the README **highlighted, not in a footnote**, in the shape of D28's fsync admission. **An event per journal record**: only per batch (`seJournalFlushed`), otherwise the event costs more than the fsync it observes (D25). No distributed tracing and no correlation context beyond the fields already frozen in D34.

### Locked decision — F8, migration to pascal-common-faa (D37)

37. **The queue actors run on a `TPcThreadPool` owned by the `TAMQPServer` itself, not on `PcPool`.** `PcPool` is **a pool for the whole process** (consumer callbacks of this client and of the other `*-faa` libraries — pipes, redis — in the same process), with a ceiling of `max(16, 4×cores)`, and a user callback may block on I/O for seconds. The actor answers **synchronous** commands (`Declare-Ok`, `Get-Ok`, `Purge-Ok`… wait for it), so sharing a pool with work that blocks is starvation with a 15 s deadline. **Measured** (`TPoolIsolationTests.PcPoolSaturated_BrokerKeepsResponding`, PcPool saturated with items stuck on an event): actors on `PcPool` → `Queue.Declare` waited the **15 s** of the synchronous command and the connection dropped; own pool → **26 ms**. The pool is born in the server's `Create` (before any queue: the recovery of `Start` already creates queues), goes into `TAMQPEngine.Pool` and is freed **after** the engine (whose destructor stops each actor). There is no thread before the first `Queue`. The client (`AMQP.Connection`) **stays on `PcPool`** — it is a user callback, the use case the process pool exists for —, and `CreateChannel(True)` still gives the channel a 1-worker pool. `TAMQPServerQueue.Create(..., APool = nil)` still falls back to `PcPool`: it is the loose queue of the state tests, never the broker.

### Current state and deliberate deviations from RabbitMQ

**Phase 1** (protocol): SASL PLAIN handshake, channels, every client→server method with the correct `*-Ok`, content reassembly with the interleave rule (spec 2.3.5), bidirectional heartbeats, channel-vs-connection error model, server-side TLS (on both backends since v0.6.0, with optional mTLS; up to v0.5.0 OpenSSL only). **Known**: a plain-text client against the TLS port of an **SChannel** broker only drops at the handshake deadline (15 s; OpenSSL refuses immediately) — finding recorded in `.ci/transport-findings-for-pascal-common-faa.md`.

**Phase 2** (engine): direct/fanout/topic/headers exchanges + default `""` + predefined `amq.*`; in-memory queues, actor-per-queue; consume/cancel, asynchronous delivery, `Basic.Get`; ack/nack/reject with requeue and redelivered; `Basic.Qos` (per-channel prefetch); real publisher confirms and `mandatory`→`Basic.Return` (Return-before-Ack order); exclusive/auto-delete queues with cross teardown; complete error model (403/404/405/406/540).

**Phase 3** (lifecycle): queue and message TTL (the smaller wins); dead-lettering with full `x-death` (reasons `rejected`/`expired`/`maxlen`, count collapsed per queue+reason, `x-first-death-*`); priority (`x-max-priority` 0–9, buckets); per-queue caps (`x-max-length`, `x-max-length-bytes`, `x-overflow` `drop-head`/`reject-publish`); `alternate-exchange`; `x-expires` (idle queue — publishing doesn't count as use).

**Deliberate deviations from RabbitMQ**: guest accepted outside loopback (documented footgun, for embedded use); no per-vhost permissions; no delay after an auth failure; `user-id` validation only comes with a real sink (it already came in Phase 2); an unknown exchange type is a **channel** 406 here, not a connection 503; `x-max-priority` refuses above 9 instead of accepting up to 255; `x-overflow` without the `reject-publish-dlx` mode; 406 always names the invalid argument in the message; queue cap and global cap compose by the **smaller**; `Queue.Delete`/`Exchange.Delete` of a non-existent resource are idempotent (Delete-Ok), not an error — the letter of the spec says to raise, but RabbitMQ has been idempotent for a long time and this repo's `RetryDlqVcl` sample already relies on it.
