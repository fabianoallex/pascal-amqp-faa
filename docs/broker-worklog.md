## Phase 1 — protocol ("null broker")

Evaluated on 2026-09-02 and started: the "other end" — a library to **create an AMQP 0-9-1 broker inside a Delphi/FPC app**, in the same codebase (units `AMQP.Server.*`, a separate `pascal_amqp_faa_server.lpk` package that depends on the client package; whoever only uses the client links nothing of the server).

**Phase 1 scope ("null broker"):** accepts N connections, each with N channels; full handshake; decodes and accepts every client→server method; answers the correct `*-Ok`s; bidirectional heartbeats; clean close with the channel/connection error model. **No engine**: declares are no-ops, publishes are dropped, no real delivery.

**Model per workstream:** WS0/WS1/WS2/WS6/WS7/WS8 (scaffolding, codec, listener, broker skeleton, heartbeat, tests) are mechanical → Sonnet. WS3 (TLS server), WS4 (handshake FSM), WS5 (content interleave rule) have subtle protocol correctness → Opus.

- **WS8 (DUnitX mirror of the server)** done — `tests\Server\AMQP.ServerTests.dproj` mirrors the 32 assertions of the FPCUnit suite and joined `AMQP.groupproj` (targets `AMQP_ServerTests`): **32/32, 0 leaks**. It was the first time `src\server\` went through a Delphi compiler — WS2/WS4/WS6 had only been compiled by FPC — and the run immediately yielded three defects in the Delphi branch of `System.Net.Socket`, all invisible to FPC.
  - The three defects, all in the Delphi branch (`System.Net.Socket`) and all on the same theme — **the RTL raises in `shutdown` BEFORE closing the handle**:
    1. An **accepted** socket closes with `FSock.Close(True)`. The RTL's default `Close` (`ForceClosed=False`) does `shutdown(SD_BOTH)` and then **drains the socket in a `while recv(...) > 0` on the calling thread** — it runs `recv` concurrently with the connection's read thread, and on Windows `shutdown` on an accepted socket does not unblock a pending `recv` (the same finding as WS2 that led the FPC path to use a raw fd + `CloseSocket`). `Close(True)` skips shutdown/drain and goes straight to `closesocket`. The **client** path keeps the default `Close` (graceful shutdown), validated against real brokers since the original library.
    2. **`TAMQPTcpListener.Close` also uses `Close(True)`** and `Destroy` guards `FListen.Free`. A LISTEN socket has `FState = [Connected, Listening]` (the RTL marks `Connected` on bind), but was never actually connected — so the default `Close`'s `shutdown(SD_BOTH)` fails with WSAENOTCONN and raises before `closesocket`. Result: a pending `Accept` **never unblocked** (`Close_DesbloqueiaAccept` hung) and the listener's `Free` raised. It is the same rule the FPC/Windows path already documented: on a listen socket what unblocks accept is `closesocket`, not `shutdown`.
    3. **`Close` never escapes** (and `Destroy` guards `FSock.Free`). The default `Close`'s `shutdown` raises `ESocketError` WSAENOTCONN (10057) when the peer HAS ALREADY dropped TCP — which started happening every time because the broker closes the socket right after `Connection.Close-Ok`. Worse: the RTL raises **before** clearing `FState`, so `TSocket.Destroy` redoes the `shutdown` and the exception comes out of `Free`. Now the `except` forces `Close(True)` to take the socket out of "Connected". Without this, every client test errors in teardown with "on API 'shutdown'" — and there is a risk of `StopReadThread` hanging in `WaitFor`, since the exception aborted `Close` before the `closesocket` that unblocks the read thread's `recv`. **Applies to any peer that closes TCP abruptly, not just this library's broker.**

- **WS7 (heartbeat)** done — the broker emits heartbeats from its own timer, detects a dead peer and enforces the `Connection.Close-Ok` deadline:
  - **One monitor thread for the whole broker** (`TAMQPMonitorThread`), not a timer per connection: every `AMQP_SERVER_MONITOR_TICK_MS` (200 ms) it takes a snapshot of the live connections and calls `HeartbeatTick` + `EnforceCloseDeadline` on each. Scales to hundreds of connections without multiplying threads, and since the connection's thread is blocked in the read, the timer had to be external anyway.
  - `TAMQPServerConnection.HeartbeatTick` (spec 4.2.7), over the Tune-Ok interval: send idle for ≥ half the interval → posts a heartbeat; nothing received for > 2× the interval → dead peer, closes the socket (which unblocks the read and finishes through the normal path). No-op before Tune-Ok and with interval 0.
  - **WS6's heartbeat echo is gone.** A heartbeat is not answered — each side emits from its own timer; receiving already counts as a sign of life (`FLastReadTick` is updated in the read loop, for any frame, not just heartbeat).
  - Send idleness is measured by the **real flush to the socket** (`TAMQPFrameWriter.LastWriteTick`), not by `Post*`: a frame sitting in the queue has not reached the wire yet.
  - **The reap changed owner**: it was done in `AcceptLoop` (a dead connection was only freed on the *next* accepted connection); now the monitor collects, on every tick. `Stop` brings the monitor down **before** touching the connections — two concurrent reapers would be a double-free.
  - `TAMQPServer.CloseTimeoutMs` (default `AMQP_SERVER_CLOSE_TIMEOUT_MS`) made the Close-Ok deadline configurable — without it the fixed 10 s were not testable.
  - The server suites go to **37/37** on both compilers: `THeartbeatTests` (5) covers the broker emitting on its own, a silent peer dropped at 2× the interval, heartbeat 0 does not drop, an unanswered Close-Ok dropped at the deadline, and the **real client idle for 3 s with a 1 s heartbeat on both sides without anyone dropping anyone**. The old `HeartbeatEcoado` became `HeartbeatRecebido_NaoDerrubaNemResponde` (the echo no longer exists).
  - **Fourth Delphi defect in `System.Net.Socket`, found by the new tests** (the first three are in WS8): `TAMQPTcpSocket.Receive` violated the unit's own contract — "Receive returns <= 0 at end of stream/error" — because Delphi's `TSocket.Receive` raises `ESocketError` instead of returning. It shows up as **WSAECONNRESET (10054)** when the peer closes with RST instead of FIN, exactly what the broker does when dropping for heartbeat or for the Close-Ok deadline. FPC never exposed this: `fprecv` returns -1. Now the Delphi branch catches and returns -1, and both compilers agree. The TLS backends already handled `<= 0` (the OpenSSL one even documented the quirk), so nothing changes for them. **Applies to the client against any broker that sends RST**, RabbitMQ included.

- **WS5 (content + interleave + null dispatch)** done — with it Phase 1 closes the protocol scope: the broker **decodes and answers every client→server method**.
  - `AMQP.Server.Channel` gained content assembly: `BeginContent` (Basic.Publish) → `SetContentHeader` → `AppendBody` until the body-size is complete. It lives **in the channel**, not in the connection, because that is exactly the granularity of the spec rule.
  - **Interleave rule (spec 2.3.5)**: between Basic.Publish and the last body frame, no other frame may appear *on that channel* — no other method, no Channel.Close → `UNEXPECTED_FRAME` (505), a connection error. Different channels remain free to interleave, and there is a test with two interleaved publishes proving it.
  - Other violations that become 505: content-header without a prior Publish, body without header, body larger than the declared body-size, and a content-header whose class-id is not the method's class (read straight from the payload, since `DecodeContentHeader` consumes and discards that field).
  - The body grows as it arrives — no allocating the declared body-size at once, otherwise a hostile peer brings the broker down just by announcing a giant body.
  - `IAMQPMessageSink` + `TAMQPNullMessageSink` (in `AMQP.Server.Types`), pluggable through `TAMQPServer.MessageSink`: it is the point where the Phase 2 engine comes in without changing any caller's signature. - **WS3 (server-side TLS)** done — the broker accepts encrypted connections, and with that **Phase 1 is complete**.
  - `TAMQPOpenSslStream.CreateServer(AUnderlying, ACertFile, AKeyFile)`: a second constructor in the SAME class as the client, not a new class. Only the setup differs (`TLS_server_method`, cert+key in PEM, `SSL_set_accept_state`); the pair of memory BIOs, the two locks, the draining, `Read`/`Write` and the `close_notify` are exactly the same — and already validated by the client's whole TLS suite.   - **The handshake runs on the CONNECTION's thread, not the accept thread.** That is why `FStream` and `FWriter` stopped being born in the constructor and moved to `SetupTransport`, called at the start of `RunReadLoop`: a TLS handshake is blocking and a slow (or hostile) client would hang the whole broker's accept. The connection now keeps `FRawStream` (socket) and `FStream` (the same object in plain; the TLS wrapper when encrypted, and then the wrapper owns the raw one).

    **What it would take, if it ever becomes a requirement** (server TLS on Delphi/Windows without depending on the OpenSSL DLLs):
    1. *Credential.* SChannel does not eat PEM: it needs a `PCCERT_CONTEXT` **with an associated private key**, which in practice means importing a PKCS#12 (`PFXImportCertStore` + `CertFindCertificateInStore`) or finding a cert already installed in the machine store (`CertOpenStore(CERT_STORE_PROV_SYSTEM, 'MY')` + `CertFindCertificateInStore` by subject/thumbprint).
    2. *API consequence:* `TlsCertFile`/`TlsKeyFile` (two PEMs) **do not map 1:1**. An SChannel backend would require something like `TlsPfxFile` + `TlsPfxPassword`, or a store name/thumbprint — that is, the broker's config would have to grow, not just the implementation.
    3. *Acquisition:* `AcquireCredentialsHandle(UNISP_NAME, SECPKG_CRED_INBOUND, ...)` with `SCHANNEL_CRED` (`cCreds`/`paCred` pointing at the cert, `SCH_CRED_NO_SYSTEM_MAPPER`) — or `SCH_CREDENTIALS`, newer, on Win10+.
    4. *Handshake:* a loop with **`AcceptSecurityContext`** in place of the client's `InitializeSecurityContext`, with `ASC_REQ_SEQUENCE_DETECT | REPLAY_DETECT | CONFIDENTIALITY | EXTENDED_ERROR | ALLOCATE_MEMORY | STREAM`, fed with the ClientHello and iterating on `SEC_I_CONTINUE_NEEDED` / `SEC_E_INCOMPLETE_MESSAGE`. Only this and step 1 are new.
    5. *The rest already exists.* After the handshake, `QueryContextAttributes(SECPKG_ATTR_STREAM_SIZES)` and Encrypt/DecryptMessage with the record buffer — the current `TAMQPSchannelStream` already does all of that for the client. That is: the path is the **same as WS3 with OpenSSL** — a second constructor in the existing class, reusing the whole record layer; the real work is in the credential (1–3) and in the accept loop (4).
    6. *Mutual (optional):* `ASC_REQ_MUTUAL_AUTH` + validation of the client's cert, which the OpenSSL side does not do either (Phase 1 has no mutual TLS on any backend).
  - **Bug found by the tests:** when the TLS wrapper's constructor fails (nonexistent cert, plaintext client on the TLS port), the auto-called destructor already frees the underlying stream — and the connection freed it again. It was a **double-free on every handshake failure**. `SetupTransport` now drops the reference (`FRawStream := nil`) before re-raising.

Uses the self-signed certs from `docker\certs`, found by walking up from the executable's folder (the two suites run from different depths).

It is honest — in the Default build the broker really has no TLS. `AMQPServerTestsFpc.lpi` gained the `openssl` build mode (same pattern as the other runners: a define in a `SharedMatrixOptions` tied to the mode).

## Phase 2 — in-memory routing engine

It comes in entirely through the `IAMQPMessageSink` that Phase 1 already exposes: neither the client nor the shape of the protocol changes.

**Scope:** direct/fanout/topic/headers exchanges + the default `""` + the predefined `amq.*`; in-memory queues with actor-per-queue (real declare/bind/unbind/purge/delete); `Basic.Consume`/`Cancel`, asynchronous delivery and `Basic.Get`; `Ack`/`Nack`/`Reject` with requeue and `redelivered`; `Basic.Qos` (prefetch per channel); real publisher confirms and `mandatory` → `Basic.Return`; `exclusive`/`auto-delete` queues; full error model (403/404/405/406/540).
**Out (Phase 3):** persistence, TTL, DLX/`x-death`, `x-max-priority`, per-queue `x-max-length`, alternate exchange, per-vhost permissions.

**Workstreams and model per front** — Opus where correctness is about concurrency/lifecycle between threads or frame order on the wire; Sonnet where the spec is already a table or the work is mirroring:
WS1 message + resource descriptors (Sonnet) · WS2 per-vhost topology + matchers (Sonnet) · WS3 queue actor (**Opus**) · WS4 delivery/QoS/ack (**Opus**) · WS5 real dispatch in the FSM (Sonnet) · WS6 confirms + mandatory/Return (**Opus**) · WS7 cross lifecycle and teardown (**Opus**) · WS8 mirrored FPCUnit↔DUnitX suites (Sonnet, continuous) · WS9 acceptance: client integration + SmokeTest against the embedded broker (Sonnet) · WS10 docs (Sonnet).

### Progress

- **WS1** done — message and resource descriptors, no routing at all yet (that is WS2+):
  - `AMQP.Server.Message` (new): `TAMQPMessage` — Exchange/RoutingKey/UserId/HeaderPayload/Body, atomic refcount (`AddRef`/`Release`, via `AmqpAtomicInc/Dec`; the last `Release` frees). Born with RefCount=1; never call `Free` directly. Keeps Body and HeaderPayload by reference (no copy) — whoever builds it decides whether to copy first. `TAMQPMessage.FromServerMessage` converts from a `TAMQPServerMessage` already reassembled by the channel. **Deliberately keeps no `TAMQPBasicProperties`/`TAMQPFieldTable` at all** — consistent with decision D1 (see `CLAUDE.md`): whoever needs the decoded properties (e.g. headers exchange match) decodes the channel's live table before the enqueue, not the already-queued message. `AmqpSplitBody(Body, AMaxPayload)` slices the body into `TAMQPBodyChunks` by the recipient's frame-max — WS4 (delivery) uses it to generate the body frames.

  - **The matcher was born recursive and was rewritten iterative — do not undo this.** The recursive form ("for each `#`, try 0, 1, 2… words") passes the 35 vectors but is **exponential in the number of `#`**: measured with a 24-word routing key, 6 `#` = 15 ms, 7 = 110 ms, 8 = **453 ms** per match — and a binding key fits more than 100 `#`. Since the match runs on the publisher thread **holding the read RWLock**, a single `Queue.Bind` with that key would turn every publish into a broker stall: denial of service with one line of declare. The version in use is the classic wildcard backtracking (`#` plays the role of the glob `*`, `*` that of `?`), which only needs to remember the **last** `#`: O(n·m) worst case, O(n) in the common case, no recursion and no allocation. Covered by `MuitosHash_NaoExplode` in both suites. A project rule of its own (the spec is silent here, decided in WS2's vectors file): an empty key (`""`) has **zero** words, not one empty word — that alone breaks the naive "split and compare arrays" implementation. `AmqpHeadersMatch` implements `forall`/`exists` with the correct empty case (`all` with no criterion is vacuously true; `any` with no criterion is vacuously false — vectors #8/#9), ignores every `x-` key of the binding (including `x-match` itself).

- **WS3 (queue actor)** done — `AMQP.Server.Queue` (new): `TAMQPServerQueue`, the heart of Phase 2. The design locked in the previous round was implemented as it was, with three additions worth recording:
  - **Refcounted synchronous command (caller + mailbox), not "owned by the caller".** If a synchronous one times out, the owner freeing the object while the actor still has it in hand would be use-after-free stacked on a bug that is already bad. It cost four lines (`AmqpAtomicInc/Dec`, like `TAMQPMessage`) and erased the whole class of crash.
  - **`Stop` does not use a "stop command".** It marks `FStopping` under the lock (refuses new posts and scheduling), waits for `FScheduled=False` on the monitor with a deadline and only then drains inline. A stop command posted to a pool already in shutdown (the finalization of `AMQP.Threading` frees queued items **without executing them**) would never run, and `Stop` would only return at the timeout. On timeout, `Stop` raises and **frees nothing** — leaking is better than freeing under the feet of a live actor; the destructor swallows the exception.
  - **Injectable pool, default `AmqpPool`** (letter of decision D2). The parameter exists so the broker can isolate its actors in a pool of its own without structural change, should starvation appear — `AmqpPool` has a cap (`max(16, 4×cores)`) and is shared with the client's consumer callbacks, which "may block on IO for seconds". The synchronous command timeout message says explicitly "check thread pool saturation", which is what turns a misleading diagnosis into an obvious one.
  - Actor-only state: a FIFO of refcounted messages in **two** `TQueue`s (`FRequeued` is the logical head — requeue returns to the original position, as the spec requires, and `TQueue` has no push-front), a list of unacked by `(ChannelId: NativeUInt, DeliveryTag)` (a list and not a dictionary: `multiple` has to sweep a range and the volume per queue is the prefetch, small — the same conscious choice as WS2's bindings), consumers and counters. `MaxLength` (decision D7) drops from the head and counts in `Stats.DroppedCount`; `PostMessage` on an already stopped queue also counts (nothing disappears without a metric).
  - Reference semantics: `PostMessage` does `AddRef` (whoever publishes to N queues remains owner of theirs); `Get` returns a reference **of the caller**, and in ack mode the queue keeps its own among the unacked. A stopped queue **drops** a publish silently (publish does not fail because of a teardown race) and **raises** on a synchronous command (WS5 maps it to 404).
  - **Scope, decided with the user: WS3 stops at the seam.** The unit registers consumers and defines `IAMQPDeliveryTarget` (with non-blocking `TryDeliver`, decision D3), but does not dispatch `Basic.Deliver`, does not do round-robin, does not apply prefetch and does not look at `Channel.Flow` — that is all WS4. Note that today's `TAMQPFrameWriter.PostFrames` **blocks** with the outbound queue full, incompatible with D2/D3: the `TryPostFrames` that delivery needs comes in WS4.
  - **`TAMQPServer.MaxQueueLength` (D7) does NOT exist yet** — the broker only creates queues in WS5, and a property nobody reads is dead config. The cap comes in as a queue parameter.
- **WS3's testing lesson (applies to WS4/WS6/WS7):** the first suite had 22 green assertions, including stress with 8 producers × 2,000 messages — and it **did not detect** the breaking of the mailbox's central invariant. Measured by deliberate mutation (the "mailbox empty" check moved **outside** the lock): the whole suite passed. The reason is that a lost wakeup is **resurrected by the following post** (which finds `FScheduled=False` and reschedules), so the bug is only fatal on the **last post before idleness** — which is precisely the common case of a publish arriving at an idle queue. Fix: a protected seam `ActorRoundEnding` (no-op in production, called between "the loop ended" and "the end-of-round lock was taken") that the test `CaixaSerial_PostNaJanelaDoFimDeRodada_NaoPerdeWakeup` overrides to post from another thread exactly inside the window, with no further post afterwards. With the correct implementation it passes in ~15 ms; with the mutation it fails (and **only** it fails). **A race window no test reaches is a window without coverage — mutating on purpose is the cheap way to find out.**

- **WS4 (delivery, QoS and ack)** done — the actor delivers, the connection writes, and between the two comes the delivery target:
  - `TAMQPFrameWriter.TryPostFrames` (new): atomic batch **without blocking and without raising** — it was the debt WS3 recorded, because `PostFrames` blocks with the outbound queue full and the actor cannot wait for I/O (D2).
  - `AMQP.Server.Delivery` (new): `TAMQPChannelDeliveryTarget`, a class **separate from `TAMQPServerChannel` on purpose**. The channel dies (Channel.Close, socket drop, reaper) while the actor, on a pool thread, may be in the middle of a delivery — a pointer to the channel would be the use-after-free the plan marks as the phase's risk. The way out is refcount + detach: the target is a `TInterfacedObject` (each queue that has a consumer there holds a reference, so the object outlives the channel) and `Detach` zeroes the writer under the target's lock; from then on every `TryDeliver` returns False and the queues drop the consumer on the next round (`IsAlive`). `Detach` never waits for I/O, so teardown does not hang behind a slow consumer.
  - **Prefetch is a list of tags, not a counter.** The limit is per channel and `Basic.Ack/Nack` with `multiple` resolves **all** tags <= the given one — without knowing which are open, the counter would drift from what the client actually acked. Since the sequence is monotonic, the list is born sorted and `multiple` removes a prefix. Whoever **increments** is the delivery; whoever **decrements** is the connection's read thread on seeing the client's method (`NoteResolved`, already wired in `DispatchBasic`) — neither side alone sees the total. A delivery in `no-ack` does not count and does not become unacked.
  - **The delivery-tag belongs to the channel, not the queue** (one queue delivers to N channels; one channel receives from N queues), so whoever generates it is the target, and it is only **consumed when the batch is accepted**: a refusal does not open a hole in the sequence. WS5's `Basic.Get` pulls from the same sequence via `NextDeliveryTag`.
  - **Round-robin and decision D3 without persistent state**: the actor runs a delivery *round* after every command that may have unblocked delivery (enqueue, new consumer, ack/nack/reject) and picks the next consumer by round-robin index. Whoever refuses leaves the round-robin **for that round** — there is no "suspended" flag to resync when the channel drains; the next round simply tries again (an attempt costs a lock and a comparison). For the degraded case in which nobody acks and everyone refuses (a `no-ack` consumer slower than the producer), there is `PostDeliverTick`.
  - **The message only leaves the stock after the target accepts** (`PeekReady` and only then `TakeReady`): with the order inverted, a refusal would lose the message.
  - **`TAMQPServerConsumer` no longer has its own `ChannelId`** — it comes from the target (`ATarget.ChannelId`, now mandatory). There were two copies of the same identity (consumer and target) and it is what keys the unacked and matches teardown's `PostRemoveChannel`: diverging would mean requeue on the wrong channel. The identity is a global monotonic counter, not the object's address — a reused address would match an orphaned unacked with the wrong channel.
  - `AMQP.Server.Connection` now does `AttachDelivery` in `AddChannel` and `DetachAllDelivery` **on both death paths** (`Shutdown` and the read loop's `finally`), always before stopping the writer.
  - **Scope:** the FSM does not create consumers yet — `Basic.Consume` only answers `Consume-Ok`, as in Phase 1. Wiring consume/cancel/get to the real queues is WS5; WS4 delivers the machinery and the accounting.
  - Server suite: **130/130 → 153/153** (Default) and **134/134 → 157/157** (`openssl`). Two new fixtures: `TQueueDeliveryTests` (10, round-robin and policy, with a fake target) and `TDeliveryTargetTests` (13, the real wire — method+header+body sequence, slicing by frame-max, tags, prefetch, flow, detach and refusal without blocking with the write queue full).   - `AMQP.Server.Engine` (new): `TAMQPEngine` joins the three pieces the previous fronts built separately — the per-vhost topology (WS2), the live queues (WS3) and delivery (WS4).   - **Two lifecycle bugs found by the tests, both of the same family** ("who knows what, and when"):
    1. *The channel identity vanished before being used.* Teardown calls `DetachAllDelivery` **before** sweeping the channels, so when `ReleaseChannelResources` went to ask "from which channel do I release the unacked?", the target was already `nil`. Result: **an unacked message from a dropped connection never went back to the queue**. - **WS6 (publisher confirms + mandatory/Return)** done — what Phase 1 documented as a limitation (`Confirm.Select` accepted but no `Basic.Ack` going out, `WaitForConfirms` timing out against this broker) no longer exists.

- **WS7 (cross lifecycle and teardown)** done — four rules, each with a different owner, and the whole point is **who detects** vs. **who executes**:
  | Rule | Who detects | Who executes |
  |---|---|---|
  | an `exclusive` queue vanishes with its owning connection | connection teardown (end of the read loop) | `TAMQPEngine.DeleteExclusiveQueuesOf` |
  | an `auto-delete` queue vanishes when the last consumer leaves | whoever removes the consumer (Basic.Cancel or channel drop) | `MaybeAutoDeleteQueue` |
  | an `auto-delete` exchange vanishes on losing its last binding | whoever undoes a binding (explicit unbind, or the implicit one of deleting a queue) | `MaybeAutoDeleteExchange` / `SweepAutoDeleteExchanges` |
  | a deleted queue notifies its consumers | the actor, in the delete command | `IAMQPDeliveryTarget.TryCancel` |
  - **"The last consumer left" is only true after the actor has processed the departure.** Removal is asynchronous (`PostRemoveChannel`/`PostRemoveConsumer`), so `MaybeAutoDeleteQueue` reads `Stats` — a **synchronous** command — and the FIFO mailbox guarantees that read already sees the removal posted before. There is no sleep or polling in this decision.
  - **`EverHadConsumer`**: an `auto-delete` queue that **never had** a consumer does not vanish — otherwise it would disappear between `Queue.Declare` and the first `Basic.Consume`. Same rule as RabbitMQ.
  - **Exchange orphaned by a deleted queue**: deleting a queue takes its bindings along, and from outside there is no way to know which exchanges were orphaned. Since `auto-delete` exchanges are rare, a sweep over the vhost's exchanges comes out cheaper than tracking source by source.

## Phase 3 — message lifecycle

Planned on 2026-09-03, in a session of its own and in Opus, because three points collided with invariants locked in Phase 2.

**Scope:** TTL (per-queue `x-message-ttl` and per-message `expiration`, the smaller wins) · DLX (`x-dead-letter-exchange`, `x-dead-letter-routing-key`, `x-death` header) · priority (`x-max-priority` + `priority` property) · per-queue caps (`x-max-length`, `x-max-length-bytes`, `x-overflow` in `drop-head` and `reject-publish` modes) · `alternate-exchange` · idle queue (`x-expires`) · array writing in the field-table (`AMQP.Wire`).
**Out:** persistence and recovery (Phase 4, model already chosen) · per-vhost permissions · paging to disk (never was a goal) · the usual non-goals.

**The three collisions, resolved before any code:**
1. **Persistence × D2** (the actor cannot block waiting for I/O) — goes away with the postponement to Phase 4. When it comes in, writing goes to a **journal thread of its own** (the shape of Phase 1 WS7's monitor thread: one for the whole broker), never into the actor.
2. **Persistence × confirm timing** — goes away along with it. `Basic.Ack` keeps going out inline right after `RouteMessage`, and with it the Return-before-Ack order, which has a raw socket test (`MandatorySemRota_ReturnAntesDoAck_312`) that any change in timing would break.
3. **`x-death` × D1** — **resolved, stays in Phase 3.** D1 forbids cloning on the **hot** path (every publish, every delivery), not the cold one — a message dies once. And `TAMQPMessage` is already immutable by invariant, so the rewrite mutates nothing: **it derives a new message**, with a rebuilt `HeaderPayload` and **the same `Body` by reference**. The expensive part is never copied.

**Probes measured before planning:**
1. Content-header round-trip (`DecodeContentHeader` → `BuildContentHeader`): **byte for byte identical** — 98 bytes, with content-type, delivery-mode, priority, correlation-id, expiration, timestamp, app-id and a nested headers table. It is what backs decision D10.
2. **The codec was ASYMMETRIC: it read `'A'` arrays and did not write them.** `TAMQPWriter.WriteFieldValue` handled `tkClass` (nested table) and no array — writing the shape of `x-death` raised `EAMQPWire: field-table: TValue.Kind nao suportado (21)`, and 21 is `tkDynArray`. **There was no `x-death` without fixing this**, and the fix was in `AMQP.Wire`, a CLIENT unit (WS1 closed it). Side effect: today a client application can also publish an array header — the fix served both ends.
3. Reading an `'A'` array coming from the wire stays as Phase 2 documented: `IsArray`, the element is a `TAMQPFieldTable`, and the `TypeInfo` matches `TAMQPValueArray` (the documented divergence is only for the specialization written *inline* in another unit).

**Workstreams and model per front:**
WS1 array writing in the field-table (`AMQP.Wire`) (Sonnet) · WS2 queue policy: `x-arguments` → `TAMQPQueuePolicy`, with validation → 406 (Sonnet) · WS3 content-header rewriting, `AMQP.Server.Header` (**Opus**) · WS4 stock with priority and expiration (**Opus**) · WS5 dead-lettering: reasons `rejected`/`expired`/`maxlen`, `x-death` with `count` collapsed by (queue, reason), `x-first-death-*`, cycle guard (**Opus**) · WS6 per-queue caps and `x-overflow` (Sonnet) · WS7 alternate exchange (Sonnet) · WS8 `x-expires` (**Opus**) · WS9 mirrored FPCUnit↔DUnitX suites (Sonnet, continuous) · WS10 acceptance (Sonnet) · WS11 docs (Sonnet).

A queue without `x-max-priority` has `FMaxPriority = 0`, hence **a single bucket and the same code path as before**. `TakeReady`/`PeekReady` sweep from the highest bucket to the lowest; within the bucket, the returned ones before the new ones.
  - **FIFO within a level is a tested invariant**: priority reorders **between** levels, never within one.
  - **Requeue goes back to the head of its OWN bucket**, with the original deadline. `TAMQPUnackedEntry` now keeps `Priority` and `ExpiraEm`.
  - **Priority and `expiration` are read on the PUBLISHER thread**, not in the actor: the message keeps the raw header (D1), and whoever still has the decoded properties is whoever published. `PostMessage` gained `APriority` and `AMessageTtlMs` already resolved; the actor only clamps the priority to its own cap and combines the TTLs.
  - **TTL: the smaller of queue and message wins.** The queue's `x-message-ttl` and the message's `expiration`; with both absent, the message never expires.
  - **Injectable clock (decision D13)**: `NowTick` is `protected virtual`. A TTL test overrides it and moves time by hand — the ten new tests run in ~8 ms combined.
  - **Lazy expiration at the head, with a deliberate and documented limitation.** `ExpiraVencidas` drains from the head of each bucket while expired — O(expired), not O(n). With **per-message** `expiration` (not in order) a short-deadline message behind a long-deadline one is only collected when it reaches the head — same behaviour as RabbitMQ.
  - It runs at the start of `DeliverPending`, **before the early-exit for lack of a consumer** — that is what makes a queue with no consumer at all expire on time (D13). Also in `Basic.Get` and in enqueue, **before** applying the cap.
  - **The memory cap drops from the LOWEST-priority bucket** (D12).
  - New `Stats.ExpiredCount`. `DescartaExpirada` exists as a method of its own on purpose: it is the single point through which an expired message leaves, and WS5 swaps its body for "rewrite the header with `x-death` and republish to the DLX" without touching anything else.
  - **A malformed `expiration` is 406, not ignored.** `AmqpParseExpirationMs` validates digits and overflow; the FSM refuses in `CompleteContent`.

- **WS5 (dead-lettering)** done — `x-death` stopped being mechanism and became semantics.
  - **The three reasons**, each at the point where the death already happened: `rejected` (nack/reject without requeue), `expired` (TTL), `maxlen` (cap). `delivery_limit` is left out: it belongs to quorum queues.
  - **`MorreCom` is the single exit point of a death**, and it always consumes the entry's reference.
  - **ACK and nack-without-requeue arrived indistinguishable** at `ResolveUnacked` — hence the `ARejected` parameter, locked by `Ack_NaoVaiParaODlx`.
  - **`x-death` collapses by (queue, reason)**: an existing entry has its `count` incremented, not a new entry. A new entry goes to the **front** of the array.
  - **`x-first-death-queue`/`-reason`/`-exchange`** written only on the first death, never overwritten.
  - **The `expiration` property is REMOVED when dead-lettering** and becomes `original-expiration`. Without it, the retry-with-wait pattern would not work.
  - Without `x-dead-letter-routing-key`, the **original** key is kept.
  - **Cycle guard by depth (decision D14)**: `AMQP_MAX_DEADLETTER_HOPS = 16`.
  - `IAMQPDeadLetterSink` + `TAMQPDeadLetterAdapter` — the queue cannot see the engine (unit cycle); one adapter per vhost fixes the name.

## Phase 4 — durability

Planned on 2026-09-04, in a session of its own and in Opus. **Decisions D19–D28 are in `CLAUDE.md`** — read them from there, do not re-derive. Full plan, with the measurement tables: artifact `Broker AMQP — Fase 4` (https://claude.ai/code/artifact/46b89cbc-060b-406c-b10b-31f9e8c99bd1).

**Scope:** segmented WAL (record with length and CRC32, recovery by valid prefix, exclusive lock on `DataDir`) · journal thread with self-tuning group commit and LSN watermark · durable topology · persistent message (`delivery-mode=2` in a `durable` queue) · asynchronous confirm tied to the fsync · three-pass recovery · segment rotation/compaction and hard cap · crash-safety apparatus.
**Out:** paging to disk (lazy queues) — *durability is not paging*, the queue stays entirely in memory · `Connection.Blocked` and alarms · persisting consumer state · recovering an exclusive queue · encryption at rest · ordering between publishers beyond what the spec guarantees.

**The collision Phase 3 had already measured and pointed out:** the clock (`AmqpTickMs` = `GetTickCount64`) is relative to BOOT and the queue keeps absolute deadlines in it; persisting those numbers is writing a coordinate of a frame of reference that does not exist after the restart. Resolved by D21 (wall clock on disk, monotonic in memory, conversion only at the two boundaries).

**The prediction the measurement disproved:** the project's memory recorded D15 (the synchronous enqueue of `x-overflow: reject-publish`) as "the only point of Phase 3 designed to be replaced". Read against D24's design, it **does not need to be replaced**: `TryPostMessage` is synchronous but does no I/O, so the rejection is known before the confirm pending is registered. What changes is only when the ack goes out.

### Progress

- **WS0 (probes)** done on **both compilers** and both platforms. Probes parked in `build\sondas-ws0\` (a directory ignored by git).

  **1 · Group commit is worth much more than assumed, and worth more the worse the disk.** 256 B records, timed with `QueryPerformanceCounter`:

  | platform | fsync 1:1 | fsync 1:100 | gain |
  |---|---|---|---|
  | FPC 3.2.2 / Win64, local NTFS | 329–674 µs → 1.5k–2.2k rec/s | 530–1278 µs → 78k–188k rec/s | **35×–50×** |
  | FPC 3.2.2 / Linux, Docker VM overlay | 5593–6124 µs → ~170 rec/s | 2405–2560 µs → ~40k rec/s | **~250×** |

  The gain **scales with the cost of the fsync**, which is exactly the desired property in a batch that tunes itself (D25). The Linux numbers come from a Docker Desktop VM, not bare metal — they serve to decide the design, not to quote as performance.

  **2 · The FPC branch needs no platform conditional at all.** Measured against the RTL: `SysUtils.FileFlush` **is** `FlushFileBuffers` on Windows and `fpfsync` on Unix (`rtl/unix/sysutils.pp:492`), with times indistinguishable from `fpfsync` called by hand; and `FileOpen`/`FileCreate` with `fmShareExclusive` **already gives real exclusion on both** — share mode on Windows, `fpflock(LOCK_EX or LOCK_NB)` on Unix (`rtl/unix/sysutils.pp:407..425`). On both OSes the second owner is refused and the lock is released on `FileClose`. Only Delphi needs code of its own (it has no `FileFlush`).

  **3 · The wall clock had a bug that only shows up outside UTC — and the first probe had it.** `DateTimeToUnix(LocalTimeToUniversal(Now), False)` converts **twice**: the `False` says "the input is local, convert it", and the input had already been converted by hand. Closed against an external reference (`[DateTimeOffset]::UtcNow.ToUnixTimeMilliseconds()`):

  ```
  A  DateTimeToUnix(UTC,   True)  + ms  = 1788533217385   correct
  B  DateTimeToUnix(local, False) + ms  = 1788533217385   correct
  C  DateTimeToUnix(UTC,   False) + ms  = 1788547617385   WRONG (+4 h)
  D  Round((UTC - UnixDateDelta) * 86400000) = 1788533217385   correct
  PowerShell reference                  = 1788533217206
  ```

  **What makes this defect dangerous is where it does NOT show up:** on a machine with a UTC time zone — every container and most Linux servers — `LocalTimeToUniversal` is a no-op and the double conversion adds zero. The Linux probe passed with the wrong formula and only the Windows probe caught it. Form **D** was chosen for `AmqpWallMs`, which does not depend on the semantics of `DateTimeToUnix`'s flag (which is what differs between the compilers): convert to UTC (`LocalTimeToUniversal` on FPC, `TTimeZone.Local.ToUniversalTime` on Delphi) and subtract `UnixDateDelta`.

  **4 · Two probe traps, both of the same kind — a silent error path looking like performance.** (a) Naming the test files `flush/1`, `flush/100`: the slash is a path separator on Windows, `FileCreate` failed, and `FlushFileBuffers` on an invalid handle returned in **0.3 µs** — the table said writing *with* fsync was 30× faster than without. (b) Measuring Linux fsync in `/work`, which is the bind mount of the Windows directory: 24 ms per fsync instead of the 2.4 ms of the container's local filesystem. **Phase rule: in an I/O benchmark, check the path before the number.**

  **5 · The Delphi side closed, and it matches FPC.** `SondaWS0Delphi.dpr` in the IDE (Delphi 12 CE, console): the share-mode lock excludes the second owner and releases on close; `FlushFileBuffers` costs **626 µs** at 1:1 (1,597 rec/s) and **843 µs** at 1:100 (**118,635 rec/s**) — a gain of **74×**, within the range measured on FPC. `TTimeZone.Local.ToUniversalTime` checks out: the FPC run gave `1788533217385` at 14:46:57 UTC and the Delphi one `1788537058309` at 15:50:58 UTC — 64 min 1 s apart, exactly the expected 3,841,000 ms. The probe was written with the **Win32 API directly** on purpose, so that the Windows branch is the same text on both compilers — it is the family of debt that yielded the four `System.Net.Socket` defects in Phase 1.

  **6 · Why form D, and not A, even with both measured correct.** Form A (`DateTimeToUnix(utc, True) * 1000 + MilliSecondOf(utc)`) adds the millisecond component to a seconds value produced by `Round()`. If the RTL rounded up a time with `ms >= 500`, the sum would be off by **up to 1 second** — and 1 s in a TTL deadline is exactly the class of defect D21 exists to avoid. On FPC this does not happen because `DateTimeToUnix` does `RecodeMillisecond(T, 0)` before the `Round` (`packages/rtl-objpas/src/inc/dateutil.inc:2274`), and the sweep confirms: **0 divergences between A and D** over the 1000 millisecond values of the same second and over 2001 instants with `ms=500` spread over ~1.6 years. But that exactness is **an implementation detail of one RTL**, not a contract — and it was not verified on the other. Form D (`Round((utc - UnixDateDelta) * 86400000)`) does not call `DateTimeToUnix`, depends neither on the flag's semantics nor on the ms zeroing, and `UnixDateDelta` is 25569 on both. **Chosen because it has nothing that can diverge**, not because it is faster.

- **WS2 (journal thread and group commit)** done on the FPC side, on both platforms; DUnitX mirror written and verified, **to be compiled in the IDE**.

  `AMQP.Server.Journal`: numbers the records, gathers what arrived into a batch, writes, does **one** fsync and only then advances the **watermark** — the number from which a confirm can be released (D24). The loop is the whole of D25: *wait to have something → take everything → write → one fsync → advance and notify → repeat*. No configurable wait window or batch size.

  **The number that proves D25:** 4 threads × 500 submits of 2 records = **4,000 records in 4 fsyncs**, average batch 1,000, largest 2,012. Under load the batch grows by itself, because what arrives *during* an fsync is already the next batch.

  **Who may block, and who may not.** `Submit` blocks while the submission queue is above the cap — the caller is the connection's read thread, and stopping reading that connection *is* the desired backpressure (D24, corollary c). `SubmitNoWait` never blocks and never refuses: it is how the queue actor writes the retirements, and D2 forbids the actor from waiting for I/O. The sink cannot block either — it runs on the journal thread, between the fsync and the next batch.

  **Failure closes the door, but only the right failure.** An `fsync` that fails does **not** advance the watermark and is **recoverable**: the bytes are already in the file, and a later fsync covers the batch. A **write** that fails, however, is final — the record is nowhere, and there is no way to restore the promise: the journal enters a failed state, `Submit` starts raising, `WaitDurable` returns False and the sink is notified once. Both treatments have their own test.

  **This round's coverage hole: nothing tested that the batch is INDIVISIBLE.** The probe passed, group commit measured beautifully, and an implementation that assigned the LSNs under the lock but enqueued **outside** it would pass just the same. ### Phase 2/3 defect found while wiring WS4: requeue of a consumer delivery lost priority and deadline

Found **by reading the code** to know where to fit WS4's `DEQ`, not by a test that failed.

In `TAMQPServerQueue.DeliverPending`, the unacked record was filled with `ChannelId`, `DeliveryTag` and `Msg` — and **only** those. `Priority` and `ExpiraEm` were left with stack garbage. The `Basic.Get` path always copied both; the **consumer** delivery path did not.

**Effect:** every message delivered to a consumer and then returned — `Basic.Nack`/`Reject` with `requeue`, or a channel drop — went back to an **arbitrary priority bucket** and with an **arbitrary TTL deadline**. And the same garbage went into `x-death` when the rejected one went on to the DLX.

**Why it went through two phases without showing up:**
- every requeue test used `Basic.Get`, which is precisely the correct path;
- a queue without `x-max-priority` has **a single bucket**, so a wrong priority is invisible;
- a queue without TTL does not even sweep deadlines (`FTemPrazo` stays false), so a wrong `ExpiraEm` is never read.

That is: the defect only manifests in a queue **with priority or with TTL**, delivering to a **consumer**, and with a **return** — all three things at once, and no combination was covered.

**Two new tests**, both through the consumer path:
- `Ttl_RequeueAposEntregaAConsumidor_PreservaOPrazo` — half-life and full life: with a **small** garbage deadline the message dies early and the first half falls; with a **large** garbage deadline (or zero, which here means "never expires") it never dies and the second half falls. That is what closes in on an indeterminate value.
- `Prioridade_RequeueAposEntregaAConsumidor_VoltaAoProprioBalde` — the `'media'`, published **after** the return, is what makes the test discriminating: without a third level, returning to the *head of the wrong bucket* would still look right.

**Mutation, three mutants, each killed by the right test:** the original bug restored, `Priority := 0` and `ExpiraEm := 0`. Worth recording that the first version of the priority test **failed because of a wrong premise of mine**: with a consumer already attached, the enqueue itself delivers, so the first published message goes out first regardless of priority — and `tag 1` was the `baixa`, not the `alta`. The test now publishes both **before** the consumer and uses the tag the target actually recorded, instead of assuming the number.

  The new piece is `AMQP.Server.Confirm`, with two classes: the **per-channel tracker** (keeps the `(seq, lsn)` pairs that cannot go out yet) and the **broker registry**, which is the `IAMQPDurabilitySink` the journal thread calls after each fsync.   **The detail that almost goes unnoticed is the transient one.** By D24's corollary (a), confirms go out in **seq order per channel** — so a transient publish arriving behind a still pending persistent one **cannot jump ahead**: it is also deferred (with LSN 0) and goes out collapsed in the same `multiple=true`.   **The nack cuts the collapse.** `Basic.Nack` marks ONE seq — it cannot be collapsed with its neighbours. The release emits the accumulated ack up to the previous seq, then the nack alone, and starts accumulating again. A nack does not wait for disk (it promises no durability at all): it only needs to respect the order.

  **Two things the design forced and that were not in the plan.** (1) The release uses `TryPostFrames`, because the caller is the journal thread and it cannot be stuck behind the write queue of a slow channel — it is D3 applied to the confirm. - **WS6, first half: the replay.** `AMQP.Server.Recovery` **does not talk to the engine**. It reads the segments in LSN order and answers a single question: *given this log, what is the state?* The separation is deliberate — the hard part of recovery is the **semantics**, and this way it is testable without bringing up a socket, thread or broker, with the log written by hand record by record. Whoever applies the state to a live broker is the second half.

  **The log is of operations; the state is the final one.** A `QUEUE_DECLARE` followed by `QUEUE_DELETE` leaves no queue — and leaves no **binding** at all nor any **placement** of that queue. An implementation that only took the queue off the list would pass any topology test and **resurrect messages of a queue that no longer exists**. The same goes for exchanges, with an aggravating factor: an exchange can be the source of some bindings and the **destination** of others (D5), so looking only at `Source` leaves an orphaned binding pointing at what vanished.

  **Three properties come for free, and it is good to know why.** (1) A live placement is one that has an ENQ and no DEQ — and since *delivery* is not journaled, a message delivered and not acked stays live and comes back ready: that is the whole of D27, without a single extra record. (2) The order of the placements is the order of the log, and the priority bucket is inside the ENQ — so re-enqueueing in reading order puts each message exactly where D12's `RequeueFront` would put it. (3) The body comes only once (D22), and dead-letter only adds a placement.

  **Two things that needed a decision, and did not come for free.** **Content that no live placement references is released** — without this, recovery would load into memory the body of every message the broker has ever seen in its life, because the log is append-only and the bodies stay there. And **the largest id seen survives**: `EntryId` and `ContentId` come from the same engine counter, and if it restarted from zero a new placement would collide with a recovered one — the DEQ of one would retire the other. Silent and fatal.

  **What the replay does NOT do: it does not decide deadlines.** The ENQ carries the wall-clock instant and the TTL (D21), and both pass through intact — converting to the monotonic one is the job of whoever has the live queue in hand.

- **WS7, first part: segment rotation.** The journal closes the full segment and opens the next one, with `MaxSegmentBytes` (default the WAL's 16 MB). On its own it does not recover any space yet — deleting and compacting are the next parts —, but it is the mechanics both rest on.

  **Rotation happens ONLY at the batch boundary, and after the fsync.** Splitting a batch between two files would give an **artificial** torn tail in the first, and recovery would discard half of an already accepted publish — the batch is indivisible by D24. And after a failed fsync there is no rotating: the bytes are not guaranteed yet, and closing the file now would take away from a later fsync the chance to cover them.

Redone to submit **after** the rotation (with a barrier) and ask then what the next number is.

Without `WaitDurable`, the test looked at the segment before the first byte had gone out. It is the same stumble WS2 had already documented, in a new shape.

- **WS7, second part: compaction.** Compacting is rewriting what is still live and deleting the rest. D26 asks for **a single mechanism** and **no snapshot file**, and the way to get both was to reuse the **replay**: the live set is exactly what recovery already knows how to compute. Compaction has no second implementation of the semantics — it calls `AmqpReplayWal`.

  **Order replaces the transaction, as in D23:** close the active segment → read the log and find the live set → write everything into a new segment **with the same `EntryId`/`ContentId`** → fsync → only then delete the old ones. A crash at any point is safe, and the reason is in the third step: since the identifiers are preserved, a log that contains both copies describes the **same** state. **Crashing between writing and deleting leaves double the bytes, never double the messages.**

  That forced a change in the replay: **a repeated placement is unified by `EntryId`**. And it forced a second, less obvious one — the naive unification would be a linear sweep on *every* ENQ, which would take the replay to O(N × live): with 100 thousand messages sitting in a queue, 10^10 comparisons. It is the same trap as Phase 2's topic matcher (green in the tests, exponential in the algorithm). An `EntryId → position` index came in, and removal became by **tombstone** instead of `Delete` in the middle of the list — which also removed the O(live) the DEQ already paid.

  **The trigger has no time parameter, in the shape of D25:** after each compaction the next threshold becomes **four times what was left**. A genuinely live log grows the threshold along with it and stops firing; a log full of retired entries shrinks, and the threshold shrinks with it. It is D26's 25% live fraction without anyone needing to compute it.

  **A defect found by the test itself: compaction consumed LSNs and did not advance the watermark.** It writes records — which *are* on disk after the fsync — but only `RodaUmLote` touched `FDurableLsn`. Whoever waited for one of those LSNs would wait until the next publish batch, which may never come. `Compact` now advances the watermark after its own fsync.

  **Mutation, seven mutants, and two survived — both were real coverage holes:**
  - *"deletes before the fsync"*: in-process the fsync never fails on its own, so **no** test reached the guard. In came `TAMQPWalFileComFalha` (it wraps a **real** file and fails only the fsync's answer — an in-memory double would not do, because there would be no segment on disk to delete and the test would pass vacuously) and `Compacta_FsyncReprovado_NaoApagaNada`. The invariant it pins: **erring on the side of a larger log is the right error; erring on the other side deletes the only place where the messages exist.**
  - *"rewrites the body per placement"*: the **state** comes out identical and the log comes out three times larger — exactly what compaction exists to avoid, and no state test notices. In came `Compacta_FanOut_GravaOCorpoUmaVezSo`, which counts the records **in the file**.

  **And a time-dependent test, which only Delphi revealed.**  required **more than two** segments, and group commit gathers everything that is in the queue into a single batch — since rotation happens at the *batch boundary*, 60 submits in a burst can become **one** batch and **one** rotation. The number of segments came to depend on who runs faster, the test loop or the journal thread: green on FPC, red on dcc32. Fixed by waiting for **each record** to become durable, which makes each one its own batch and turns the segment count into a function of size, not of the scheduler. **Third distinct shape of the same error in this round — a test that measures before the effect, with uniform data, or depending on the grouping.**

  **What is missing to close WS7:** the hard cap `MaxJournalBytes` (default 0 = unlimited), which on overflow **refuses** the persistent publish with `Basic.Nack` instead of dropping — the difference that matters relative to D7: the memory cap drops, the disk cap refuses, because dropping from the head on disk would be deleting already confirmed data.

- **WS7 closed: the log's hard cap.** `MaxJournalBytes`, default 0 = unlimited — the shape of D7's `MaxQueueLength`: nobody gets a disk cap for having turned on durability. On overflow, the **persistent** publish gets `Basic.Nack`.

  **The difference D26 marks relative to D7, and which is the whole point:** the **memory** cap drops from the head; the **disk** cap **refuses**. Dropping here would be deleting data the broker has already confirmed as durable — exactly the promise Phase 4 exists to keep. Refusing hands the decision back to whoever publishes, who still has the message in hand.

  **Two scope rules, and both are what keep the broker from locking itself up or bringing down someone who is not to blame.** (1) The cap applies **only to the publisher path**. A **retirement** record (the actor's `SubmitNoWait`) always goes through: besides D24 forbidding blocking the actor, refusing a `DEQ` would resurrect the message on the next boot — and it is precisely the DEQs that let compaction shrink the log and **get out** of the situation. Refusing them would be closing the only door. (2) The cap is a **disk** one: a transient publish does not pay for it. Without this second rule, a full durable queue would bring down the whole broker.

  **The size is approximate on purpose.** It is maintained by the journal thread at the three moments it really changes (end of batch, rotation, compaction) and read without a lock by the publishers. Sweeping the directory on the hot publish path is what would be wrong; the worst case here is accepting or refusing a publish at the exact boundary, and the next one already sees the right number.

  **Mutation, four mutants, and one survived: "refuses but posts".** Nack **and** enqueue at the same time is the worst of both worlds — the publisher thinks it failed and resends, while a consumer receives the copy that "failed". None of the other tests noticed, because they all looked either at the nack or at the log, never at the **queue**. In came `Teto_PublishRecusado_NaoEntraNaFila`, which compares the queue count before and after a refused publish. It is the same family as the holes of the two previous rounds: **the test has to look at the side of the system the mutation breaks.**

- **WS8: the process death matrix.** It is D28's third layer. The other two had lived in the suite since WS1 — the exhaustive truncation sweep and the file double that counts fsyncs and fails at the chosen moment. When it kills, the host has already confirmed much more than it read — "407 came back for 150 read" is not a violation, it is the lagging pipe. What can be asserted from outside is the **floor**: everything the driver *saw* confirmed has to be there.

  **And a real defect, which heaptrc caught in the host: `Halt` leaks.** `Halt` called from inside a routine abandons the stack frames **without finalizing the managed locals** — strings, `TBytes`, interfaces. Four blocks, constant, independent of the number of messages. It goes away by swapping `Halt(n)` for `ExitCode := n; Exit`. It went into the traps table of `CLAUDE.md`: it applies to any program in this codebase, not only the host.

- **An intermittent that only Delphi showed, and that was the test's again.** Running WS10's Delphi suites, the server failed **once in ~7** in `Compacta_Automatica_DisparaAcimaDoLimiar`. On FPC, always green — ten runs in a row.

  The cause is in the design, and it is right: **compaction is only consulted ON ROTATION** — on purpose, because rotation is already the moment the journal stops to switch files. With group commit gathering everything into a single batch, there may be only **one** rotation; and if the final batch leaves the active segment below the cap, no rotation happens *after* the size crosses the threshold, and the trigger is never consulted. The log grows large, nothing is wrong with the broker, and the test fails because of a race.

  Fixed with **a barrier per record**: each one becomes its own batch, rotations become frequent, and many happen after the threshold is crossed. The trigger becomes a function of **size**, not of the scheduler. Ten clean runs in a row on FPC, and the mutation "compaction does not fire" keeps dying in the right test.

  **It is the fourth shape of the same error in this phase** — measuring before the effect; uniform data; depending on the grouping to count segments; and now depending on the grouping for the trigger to happen at all. All invisible on one compiler and visible on the other, and none of them findable without repeating the suite.

- **In-flight compaction came out, and the reason is a real defect the test uncovered.** After making the automatic trigger test deterministic — by giving it a barrier per record —, it started submitting **concurrently with compaction**, and the journal fell into a failed state: `EAMQPJournal`, "falha ao escrever no journal".

  **The cause:** the LSN is assigned in `Submit`, on the publisher's thread. Compaction runs afterwards, on the journal thread, and assigns **new** LSNs to the records it rewrites. A publish that got its LSN *before* compaction and was still in the queue is written *after* it — with a number **smaller** than the last one in the file. `Append` refuses (WS1's increasing-LSN invariant), the write fails, and the whole journal goes to failed. It is not silent loss: it is the broker no longer being durable. But it is a concurrency defect that only shows up under load, and the previous version of the test (which submitted everything beforehand) never reached it.

  **There is no cheap fix**, and it is worth recording why so the next round does not rediscover it: the LSN order has to be the file order, and the compacted content is **logically older** than any concurrent submit — writing it afterwards inverts the order, writing it before requires LSNs smaller than the ones already handed to publishers. Compacting in flight requires **quiescing LSN assignment**, which runs into D2 (the actor cannot wait). A possible way out, for when this is picked up again: drain-and-merge the pending ones into the recovered state before allocating the block, in a loop that only allocates when a drain comes back empty with the lock in hand.

  **What stayed:** compaction runs **inside `Start`**, after recovery and before the listening socket opens — where there is no publisher and no actor, and safety is by construction. In practice, the log is pruned **on every restart**; a broker that never restarts depends on `MaxJournalBytes`. It is said that way in both READMEs, without euphemism, and the header comment of `AMQP.Server.Journal` carries the whole analysis.

  **The testing lesson, which is the same as the whole phase's:** the test that exposed this only did so **after** I made it deterministic. While it depended on the batch grouping, it did not reach the window — and it passed. Making a test deterministic is not just making it reliable: it is what turns it into an instrument.

D28's admission — **killing the process does not test fsync** — goes in a highlighted quote, not a footnote, with what the implementation *actually* asserts and tests in its place. ### The Linux hang, investigated and fixed

WS3's finding (two heartbeat tests hanging on Linux) became a front of its own. **Cause found, fixed, and the server suite passes entirely on Linux for the first time: 358/358.**

**The investigation, in order, with the hypotheses that died along the way:**

1. **First hypothesis, wrong:** "the Unix branch's `fpshutdown` does not unblock the `recv` of an accepted socket". A probe with the real code (`TAMQPTcpListener` + `TAMQPTcpSocket`): the accepted socket's `Close` unblocks the peer in **11 ms** on Linux (EOF), practically the same as the 15 ms on Windows. Hypothesis killed.
2. **`gdb` does not attach** in the container (no `SYS_PTRACE`), and `ps`/`pgrep` do not exist in the minimal image. With no user stack, `/proc` was what was left: the hung process's only two threads were in **`futex_wait`**, none in a socket, and the TCP connection was already in `TIME_WAIT`. That is: **it was not a socket, it was a lock.**
3. **Checkpoint instrumentation** (the technique that was left, and that solved it): `WriteLn` + `Flush` in the test, then in `TAMQPServer.Stop`, then in the connection teardown. The trail kept narrowing: the **test passes** (`LDropped=TRUE` — the heartbeat logic works on Linux) → hangs in `FBroker.Stop` → at step 4, the connections' `WaitFor` → inside the read loop, between `DetachAllDelivery` and `FSocket.Close` → **in `FWriter.Stop`**, in `FThread.WaitFor`.
4. **Second hypothesis, also wrong:** "two `TThread.WaitFor` in a row hang on Linux". A 20-line probe: three `WaitFor` in sequence work on both systems. Killed.
5. **The cause, reading the RTL:** on FPC/Unix, `TThread.WaitFor` calls `WaitForThreadTerminate` → **UNCONDITIONAL `pthread_join`**, without checking whether a join already happened (`rtl/unix/tthread.inc:270`). On Windows it is `WaitForSingleObject`, idempotent on a signalled handle. Item 4's probe survived because it joined **from the same thread and without `pthread_t` recycling**; in the broker, the second join comes from **another thread** and after the thread has already been reaped — and if the `pthread_t` was recycled, it waits for the wrong thread, forever.

**Why only these two tests.** `TAMQPFrameWriter.Stop` has two callers: `TAMQPServerConnection.Shutdown` and the end of `RunReadLoop`. On the normal path only one of them runs. In the two heartbeat tests the broker **drops** the peer: the **monitor** thread calls `Shutdown` (join #1) while the read loop is still alive, and the read loop, on finishing, calls `FWriter.Stop` again (join #2, from another thread). Same thing in `TAMQPServerConnection.WaitFor`, called by `TAMQPServer.Stop` **and** by the destructor.

**Fix:** join guarded by lock + flag at both points — the lock (and not just the flag) because the second caller has to **wait for the first join to finish**, not just skip. The client (`AMQP.Connection`) was already safe by construction: it does `WaitFor` and then `FreeAndNil`, so the second call sees `nil`. The project's other joins (`AmqpPool`, `TAMQPJournal.Stop`, accept's `TAMQPServer.Stop`) follow the same pattern of nilling the reference. **The general rule is in `CLAUDE.md`: either nil the reference right after the join, or guard the join; a comment saying "safe to call more than once" on a join is true only on Windows.**

**State on Linux:** server suite **358/358**, 0 failures. Windows regression intact: server 358/358 (Default) and 362/362 (`openssl`) with 0 leaked blocks, integration 28/28, acceptance 28/28, SmokeTest PASS. **Delphi validation (IDE): Build All clean in the group, server 358/358 (Debug) and 362/362 (OpenSSL), acceptance 28/28 in both configs, `Tests Leaked : 0` in all of them** — the number that mattered here, because the fix added one `TCriticalSection` per connection and one per writer.

## Phase 4.1 — observability

Planned on 2026-09-06, in a session of its own and in Opus. **Decisions D29–D36 are in `CLAUDE.md`** — read them from there, do not re-derive.

**Scope:** `IAMQPEventSink` in `AMQP.Server.Types` · bounded ring + `TAMQPEventNotifierThread` · emitters at the lifecycle points (connection, channel, consumer, ack) and at the actor-origin ones (enqueue, deliver, expire, dead-letter, drop) · per-subscriber type mask · emitted/dropped/failed counters · capture sink with drain barrier and FPCUnit↔DUnitX mirror · `docs/observability.md` + a section in both READMEs.

### The starting point: a WIP that compiled and emitted nothing

The front was born from a Haiku WIP (commit `755a3a7`, branch `feat/broker-observabilidade`, stacked on top of the i18n): `AMQP.Server.Events` with `TAMQPServerEventType` (18 types) and a record of ~25 fields, `TAMQPServer.Subscribe/Unsubscribe/NotifyEvent`, an `EventSink: TObject` in `TAMQPServerConnConfig`, a sample and **eight** doc files. It compiled. It emitted **nothing** — `NotifyEvent` did not have a single call site, only a `// TODO Fase 4.2` in `AMQP.Server.Connection.pas`. The defects, in order of importance:

1. **Head-on collision with D2, swept under the rug by the docs.** The actor-origin events (`seMessageEnqueued`/`Delivered`/`Expired`/`DeadLettered`/`Dropped`) are born on an `AmqpPool` worker; calling a user handler synchronously there blocks the actor. The WIP's docs claimed `sem bloquear o engine: callbacks rodam fora do crítico` — which is true about *locks* and false about the *thread*.
2. **Undefined delivery contract.** Best-effort? can it lose? what order? None of that was written, and without it there is no way to write a test that means anything.
3. **`EventSink: TObject` with a cast** to dodge a unit cycle, when the house pattern for exactly this is an interface in `AMQP.Server.Types` (`IAMQPMessageSink`, `IAMQPConfirmRegistry`, `IAMQPDeliveryTarget`).
4. **`except end`** in the dispatch, swallowing any handler exception without counting or exposing it.
5. **Placeholder tests** (`Assert.Pass`; `TestSubscribeSingleHandler` checked `ConnectionCount`, which has no relation to what the test claims to measure), without an FPCUnit mirror.
6. **`AMQP.Server.Events` outside every `.dpr`/`.dproj`** — check [3] of `verifica_espelhos.py` fails.
7. **Eight doc files** in a delivery/marketing tone at the root and in `docs/`, plus build artifacts of the sample without `.gitignore`.

**The method decision:** do not extend that WIP. D29–D36 rewrite it, and the branch is reused only as the starting point of the history.

**The question the decision session existed to answer** was the thread model, and the answer changed the implementation plan. The initial proposal was hybrid — lifecycle **inline** on the read thread (the "safe" events), only actor-origin marshalled. Measured against what the codebase already knows, the "safe" half is not safe: a slow handler on a read thread hangs the frame processing of that connection, **heartbeat included**, until the client drops it. It is less damage than actor starvation, not no damage. And what makes asynchrony cheap was already decided: the record is **flat, a copy by value**, with no pointer to an object that may die before delivery — so there is no lifetime reason to call any handler inline. Hence D30 (uniform) and the corollary that simplified the plan: **the two increments now differ only in *which* events are emitted, not in mechanism**, and no Inc. 1 test needs to be rewritten in Inc. 2 because of a contract change.

### Progress

- **Inc. 1 — the mechanism and the lifecycle events. Done** (FPC/Win64: server **451/451** in three runs in a row, **0 unfreed memory blocks**; it was 435 before). `IAMQPEventSink` in `AMQP.Server.Types` in place of `EventSink: TObject`; `AMQP.Server.EventBus` with the ring, `TAMQPEventNotifierThread` and D31's policy; `Subscribe` with a type mask and re-subscription that replaces instead of duplicating; counters `EventsEmitted`/`Dropped`/`Failed` + `LastEventFailure`; emitters for connection, channel, consumer, ack/nack/reject and publish. The bus comes up **before** the listener and goes down **after** everything — including after the journal —, which is what makes the teardown events be delivered instead of dropped. The WIP's eight docs became one `docs/observability.md`, the sample was rewritten for the new API (with an `.lpi`, so it can be compiled and run here, unlike the `.dproj` alone) and both READMEs gained the section.

  **Four defects the round found**, none of them foreseen in the plan:

  1. **`DrainEvents` is not a barrier for a PRESENCE assertion, and four tests died proving it.** It waits for the ring to empty — and a ring that has *not yet received* the event is already empty. Since the client's `Basic.Publish` has no round-trip, draining right after it returns `True` before the broker has read the frame. The right barrier is by CONDITION (`TCaptura.Espera`, with a deadline and re-check in a loop), along the same line as the "wait for `OnReconnect`, not `IsOpen`" that `CLAUDE.md` already records. `Drain` remains the right barrier for an ABSENCE assertion, as long as it is preceded by an operation WITH a round-trip.
  2. **A channel that dies together with the connection did not emit `seChannelClosed`** — teardown's `ClearChannels` does not go through `DropChannel`, where the emitter was. An observer counting channels would report a leak on every dropped connection. Fixed in `ClearChannels`, with `Reason = 'connection teardown'` distinguishing the two paths, and with a test of its own (`CanalMorreComAConexao_EmiteFechamento`).
  3. **`Dispatch` as a method name shadows `TObject.Dispatch`** (an FPC warning, silent in dcc32) — renamed to `DispatchBatch`.
  4. **A channel closed by the client leaves its owner and becomes a leak in the test.** `heaptrc` reported 38 blocks: a `TAMQPChannel` closed with `Close` leaves the connection's dictionary, so its destructor no longer frees it. The sink reaches the actor through the engine (`TAMQPEngine.Events`, passed on to each queue it creates, along the same line as `Journal`) and the journal directly from the broker.   **D2's anchor test** stands: `HandlerLento_NaoTravaOAtor` puts a handler that sleeps 40 ms per event on an 8-slot ring and publishes 200 messages. What it asserts is not that the events arrived — it is that **the 200 messages got into the queue anyway**, and that `EventsDropped > 0`. If `Emit` waited, it would be 8 s of handler alone and the whole pool (the SAME as the other actors') would go along.

  **Two defects, and the first is the most instructive of the whole front:**

  1. **A unit outside the `.lpk` compiles and kills the program at runtime.** `AMQP.Server.Events` and `AMQP.Server.EventBus` were never added to `pascal_amqp_faa_server.lpk`. In Inc. 1 that went unnoticed because only the test project used them. In Inc. 2, units OF THE PACKAGE (`Queue`, `Engine`, `Journal`) started using them — and since the package's `OtherUnitFiles` points at `..\src\server`, the compiler found them and compiled them **twice**, with distinct `.ppu`s inside and outside the package. While the unit only had types, nobody noticed; the moment it started declaring an **interface**, the two sides disagreed on its layout. Result: **142 access violations, zero compiler messages**. Fixed in the `.lpk` — and check **[3]** of `verifica_espelhos.py` now covers the package, with the mutation (removing the unit from the `.lpk`) verified as caught.

  2. **The bus has to be freed LAST in `TAMQPServer.Destroy`.** The engine, **every queue it owns** and the journal keep an `IAMQPEventSink` pointing at it. Freeing it earlier made the destructor of each of these fields call `_Release` on already freed memory — an AV on exit, with the whole broker having worked up to that point. It is the same lifetime rule the documentation tells the user to follow (`Unsubscribe` before destroying the handler's owner), applied from the inside out. Found by a minimal probe (create/`Start`/`Stop`/`Free`) with `-gl -gh`, which pointed at the line in three seconds after the whole suite only said "access violation".

  **Delphi validation, with counts** (compiled in the IDE — CE has no CLI —, and the `.exe`s run from here): server **457/457 Debug** and **461/461 OpenSSL**, each in **3 runs in a row, 0 Leaked**; unit **121/121**; integration **28/28** in both modes (against the docker RabbitMQ); acceptance **28/28** in both passes. ### Phase 4.1 closes here

Two increments, **all 18 event types with an emitter**, a single contract (best-effort, drops the newest, counts), one notifier thread, and the exception policy that never swallows anything. What the front taught that was not in the plan:

- **`Drain` is not a barrier for a presence assertion** — a ring that has not yet received the event is already empty (Inc. 1);
- **a channel that dies with the connection also closes** — and what found it was counting types in real traffic, not a test (Inc. 1);
- **a unit outside the `.lpk` compiles and kills the program at runtime**, and the day it declares an interface the bill comes due all at once (Inc. 2);
- **whoever is pointed at by an interface dies last** — the bus has to outlive the engine, the queues and the journal (Inc. 2).

The first two became tests; the third became a check in `verifica_espelhos.py`; the fourth became a comment in the destructor, which is where someone will reread it.

## F8 — migration to pascal-common-faa (2026-10-04)

Phase F8 of the `../pascal-common-faa` plan: atomics, `AmqpTickMs`, `TAMQPMonitor`, `TAMQPCondGen`, `TAMQPWorkItem`, `TAMQPThreadPool`, `TAMQPPoolWorker`, `AmqpPool` and `AMQP_WAIT_INFINITE` left `AMQP.Threading` and the code now uses `PcAtomic*`, `PcTickMs`, `TPcMonitor`, `TPcWorkItem`, `TPcThreadPool`, `PcPool` and `PC_WAIT_INFINITE` (submodule `external/pascal-common-faa` at v1.0.1). What stayed in `AMQP.Threading` is `AmqpWallMs` and the `PASCALCOMMON_VERSION < 10000` check. There was no test covering only what went away (the library never had an `AMQP.Threading` suite), so nothing was removed. The rules that stay are in `CLAUDE.md` (section `Dependência: pascal-common-faa` and D37); findings for pascal-common-faa in `.ci/f8-findings-for-pascal-common-faa.md`.

**1 · Shared pool — measured, and the broker got a pool of its own (D37).** A pure rename would put the queue actors in `PcPool`, which belongs to the whole process and has a cap. Before deciding, a test (`TPoolIsolationTests.PcPoolSaturado_BrokerContinuaRespondendo`) saturates `PcPool` with `4 × ProcessorCount + 16` items stuck on an event and does declare/publish/get on the embedded broker. With the actors in `PcPool`: `Queue.Declare` waited the actor's synchronous command's **15 s** and the connection dropped. With a `TPcThreadPool` of `TAMQPServer`'s own: **26 ms**. The client stays in `PcPool` (it is a user callback, the use case of the process pool).

**2 · Item 1's test found a pre-existing double free.** On the first measurement (actors in `PcPool`) the test did not just wait 15 s: it ended in an **access violation** in the broker's `Destroy`, with 33 leaked blocks. Stack (gdb): `TAMQPQueueDef.Destroy` → `FArguments.Free` on already freed memory. Cause: `DispatchQueue` zeroed `LDeclare.Arguments` (the "transferred ownership") only **after** `FEngine.DeclareQueue` returned; the engine hands the table to the queue's descriptor and then still waits for the actor (`Stats`, synchronous), and that `Stats`'s timeout raised — the channel's `finally` freed the table the descriptor already owned. Fixed by passing ownership **before** the call. Only `DeclareQueue` had this shape (it is the only path with a synchronous call to the actor after taking the table). Re-measured: with the actor in `PcPool`, the failure became clean (15 s, connection dropped, 0 leaked blocks).

**3 · Finalization.** One finalization was left in amqp: `AMQP.Transport.OpenSSL`'s `GLibLock`, which only `EnsureOpenSsl` touches. No work item of the library opens a connection (reconnection is a `TThread` of its own); the client's items only touch channel/connection, freed by the user and drained by `DrainInFlight`/`DrainConnCallbacks`, which count from enqueueing; the broker's pool dies in `TAMQPServer.Destroy`, after the engine. The pipes pattern (count until the item's destructor, wait by polling) was not needed.

**4 · Wrong documentation about the pool's Destroy.** The header of `AMQP.Server.Queue` said that the finalization of `AMQP.Threading` freed queued items without executing them. Wrong for what was already in the queue (`Destroy` executes everything); right only for an item received after `Destroy` started. Fixed.

**5 · 64 bits.** The 21 sites of `PcAtomicRead64`/`PcAtomicWrite64` have a `UInt64` target; a `var` parameter requires the exact type, so only the `UInt64` overload matches.

**6 · heaptrc silent on Linux.** In Debian's FPC (the containers), heaptrc's exit dump does not go to stdout/stderr — only with `HEAPTRC=log=<file>`. Measured with a three-line program that leaks 10 bytes. The earlier Linux validations recorded here did not use `log=`, so their "0 leaks" was not observed; this time it was.

**7 · A test with a pre-existing race, exposed by load.** `TRecoveryReplayTests.Rotaciona_QuandoOSegmentoEnche` failed once on Linux with 8 containers in parallel: `ActiveSegment` was already 2 and `Stats.Rotations` still 0. Rotation runs **after** the watermark advances (D24), and `Rotate` opens the segment before counting — the test's `WaitDurable` was no barrier for either of the two reads. The test now waits with a deadline (FPCUnit and DUnitX mirrors).

**8 · An integration failure not reproduced.** In the first Linux round (8 containers without a CPU limit, at the same time), `ConsomeTodas_ComAck_E_Concorrencia` failed in both integration runs (concurrency peak 1: no pair of callbacks overlapped in the 2 s window). ## v0.1.1 — pending items from pascal-dfe-broker's F10 (2026-10-05)

pascal-dfe-broker migrated to v0.1.0 and sent two findings back here (items 4 and 6 of its `.ci/f10-findings.md`). This round closed both, got the suites compiling on Delphi Win64 and bumped the `external/pascal-common-faa` submodule to v1.1.2. The validation found two more defects: one in the broker and one in pascal-common-faa's `TPcThreadPool`. The latter also explains the intermittent F8 had recorded without a cause.

**1 · Closing during reconnection waited for `ReconnectDelayMs`.** `RunReconnect` slept `Sleep(LDelay)` and only then looked at `FDeliberateClose`. Now the wait is `FReconnectWake.WaitFor(LDelay)`, and `Close` signals the event. Test `Close_DuranteEsperaDeReconexao_NaoEsperaODelay` (integration, 3000 ms delay): 3000 ms on the old code, 38 ms on the new.

**2 · With a delay above 12 s, the reconnect thread outlived the connection (confirmed).** `WaitReconnectStopped` polled with a 12 s cap, and the thread was `FreeOnTerminate`. Test `Close_ComReconnectDelayAlto_VoltaComAThreadEncerrada` (60 s delay) on the old code: `Free` returned after 12 s with `AmqpReconnectThreadsAlive = 1`, i.e. the thread was still sleeping and would wake up reading the freed connection. Now the thread is no longer `FreeOnTerminate`: the connection keeps the reference under `FReconnectLock` and joins it once, in `StopReconnect` (`Close`) or before creating the next one. The lock also makes "deciding to reconnect" (on the read thread) and "closing on purpose" atomic. The join has no deadline: the wait between attempts ends immediately, and what may take time is an attempt in progress, bounded by its own timeouts. Giving up halfway would be the use-after-free of before. The case of `Close` called from inside `OnDisconnect`/`OnReconnect`/`OnReconnectFailed`, which run on the reconnect thread itself, came for free. Before, that `Close` got stuck for the 12 s waiting for itself. Now it skips the join (it compares `ThreadID`), and the following `Free`, done from another thread, joins the thread (`Close_DeDentroDoOnDisconnect_NaoTrava`). `AmqpReconnectThreadsAlive` is the observable proof: it drops to zero only when the last thread leaves `Execute`, after the last access to the connection.

**3 · `DrainInFlight` with `PcPool` saturated: measured, documented, no deadline.** `TPoolIsolationTests.PcPoolSaturado_FreeDoCanalEsperaOCallbackEnfileirado`: with `PcPool` saturated for 1.5 s and a delivery queued behind, the channel's `Free` took **1.5 s**. In the same scenario with `CreateChannel(True)` it took **29 ms** (`..._CanalComThreadPropria_NaoDependeDoPcPool`). A deadline has no safe way out: the queued item holds the channel and decrements its counter at the end, and raising an exception in a destructor would leave the channel impossible to free. The decision was to document it in both READMEs and in the comment of `Close` and `DrainInFlight`, and point whoever needs to stop within their own deadline to `CreateChannel(True)`. The client stays in `PcPool` (D37).

**4 · Win64.** `src` had nothing to change: the Windows FPC build is already Win64, and the `{$IFNDEF FPC}` branches use `NativeUInt`/`THandle`. The DUnitX tests had **75** `AreEqual(Integer, NativeInt)` assertions (`Length` of a dynamic array, `.Count` of a generic collection and of `TAMQPFieldTable`, `TValue.GetArrayLength`), which do not infer a single `T` (`E2532`). They got `Integer(...)` on the `NativeInt` side, the same idiom as the `Int64(...)` the code already used on Win32. String `Length` and `Length` × `Length` stayed as they were. The `E2250` in `WillRaise` that F8 recorded did not come back: it was a cascade effect. Delphi compiled the four suites on both platforms and in both configurations, first time.

**5 · Broker: a generated queue name repeated across connections.** Found by acceptance on Delphi Win64/OpenSSL: `Tls_PayloadGrande_Integro` got `405 cannot obtain exclusive access to queue amq.gen-1-13151003`. `GeneratedName` was `amq.gen-<CONNECTION sequence>-<24-bit tick>`. Every new connection started at 1, so one test's connection and the next test's, in the same millisecond, generated the same name, and the previous one's exclusive queue still existed. The comment said "unique within the connection, which is what the spec asks"; for a queue name that is wrong, because the name lives in the vhost. The sequence became process-wide (`GNameSeq`). Test `FilaAnonima_NomeNaoRepeteEntreConexoes` (two live connections, 20 rounds): 405 in 3 of 3 runs before, green after.

**6 · `TPcThreadPool` does not grow in a burst (pascal-common-faa; noted in `.ci/findings-for-pascal-common-faa.md`).** The new pool tests failed on Linux: `PcPool` never reached `MaxWorkers` of our items running. gdb showed 9 threads in the process and 5 idle workers with 18 items in the queue; a pool dump, `workers=6 idle=0 fila=11` with a cap of 16. The cause is in `Queue`: it only creates a worker when `FIdle = 0`, and `FIdle` counts as idle a worker already woken that has not yet taken the item. In a burst against N idle ones, no worker is born. Repro (`build/v011/rajada/Rajada.lpr`, Windows and Linux): with 1 idle worker, 17 blocking items run **1**, and 16 stay in the queue. Two consequences here:
- **F8's intermittent (item 8) was this.** `ConsomeTodas_ComAck_E_Concorrencia` publishes 8 messages with slow callbacks and requires a concurrency peak above 1. With one idle worker in `PcPool`, the 8 deliveries run on it serially (17.7 s). It came back once in this round, with no change in the client. **7 · Submodule at v1.1.2.** v1.1.0 brought `TPcThreadPool.MaxWorkers`, which the pool tests use (`MaxWorkers + 1`, instead of recomputing `max(16, 4 × cores)`, which on Linux would not even give the right number, per item 6). ## v0.3.0 — reconnection: per-phase replay and visible failure (2026-10-15)

Two defects found by pascal-api-infra-faa while measuring the messaging guide (noted in
section 8 of its `docs/plan.md`). Measured before changing, with a RabbitMQ of our own on 5673 and an
instrumented copy of `AMQP.Connection.pas` outside the repository:

- **Replay in hash order.** `RecoverAllChannels` iterated `FChannels.Values` (a
  `TDictionary<Word, ...>`): with channels 1, 2 and 3, 3 came out first. Each channel replayed only its
  own list, so channel 3's `basic.consume` got a `404` before channel 1's declare
  came back (non-durable queue, deleted by `docker restart`); `RunReconnect`'s `except` swallowed it
  and the next attempt repeated the same way. Fix: `TAMQPRecoveryPhase` (derived from the
  payload's method in `AddRecovery`), replay of the whole connection phase by phase, channels in
  `ChannelId` order; `OnReconnectError` + `LastReconnectError` + reason in the text of `EAMQPConnection`.
- **`EWriteError` leaking.** Without `AutoReconnect`, the stream stayed assigned after the drop and
  the RTL's `WriteBuffer` raised. Fix: `FWritable` (the handshake writes through
  `SendHandshakeMethod`) and a write failure wrapped in `EAMQPConnection`.

## v0.4.0 — exception in the consumer callback (2026-10-15)

  `TPcThreadPool` worker does `except end` without a hook. 7 messages with the 4th raising: 7 callbacks, 6
  acks, `list_queues` with 0 ready and 1 unacked; two process restarts: it came back
  `redelivered` and got stuck again both times. **With `Qos(1)`** (which had not been measured there) and

- **The decision** (the user's): event + default. `TAMQPChannel.OnConsumerError(Canal, Entrega,
  Erro, var Acao)`; without a handler (or without changing the action), `Nack` without requeue. The library only settles if
  the delivery is still pending: a set `FUnsettled` of tags of consumers with manual ack,
  under `FSettleLock`, filled at dispatch (read thread, before enqueueing — an `Ack`
  never arrives before the registration), emptied by `Ack`/`Nack` (with `multiple`, every tag up to the
  given one) and at the end of the callback. The initial action is computed before the handler, and the removal is
  checked again, atomically, after it: the handler may have settled on its own.
- **The session epoch that did not stay.** The first design had a session counter per channel,
  so that a callback of the old session would not settle with the tag of a new delivery (tags
  restart at 1). The test that should exercise it failed in a revealing way: the old one raised
  **before** the reconnection, because `RunReconnect` does `DrainAllChannels` before reopening the
  channels. No old callback runs alongside the new session; its `Nack` lands on the dead socket
  (`EAMQPConnection`, swallowed there: the broker has already returned the delivery). The epoch went away; the test became
  `Reconexao_CallbackLevantaNaQueda_MensagemVoltaNaSessaoNova`, which proves what actually
  happens (the message comes back `redelivered` and does not go to the DLQ). `BeginRecover` still clears the
  set, which by then is already empty.
- **Tests**: `AMQP.ConsumerErrorIntegrationTests` (9, mirrored, body generated from FPC), almost
  all with `Qos(1)` and the bad one in front of good ones — without a settle the good ones do not arrive, with

  `amq.direct`, where the DLQ waits under the main queue's key.
- **Mutations** (FPC, against RabbitMQ): removing the re-check after the handler kills

  `CallbackAckouAntesDeLevantar_NaoConfirmaDeNovo`; going back to `raise` kills all 9.

  check was redundant and was removed; no-ack is decided at a single point, the dispatch.

## v0.4.2 — closing a channel with a consumer callback in flight (2026-10-27)

Found by pascal-agenda-faa (its `docs/design.md`, "M4: the broker, the compose file, the
trace"): the consumer stopped right after the handler started, and the whole connection dropped.
`TAMQPChannel.Close` sent `Channel.Close`, waited for the Close-Ok and only then did
`DrainInFlight`; the callback's `Ack` went out on an already closed channel. Measured before changing, with
`AMQP.ChannelCloseIntegrationTests` (5 tests, two channels on the same connection): against
RabbitMQ 3, 4 of 5 dropped with `504 CHANNEL_ERROR - expected 'channel.open'` (the 5th failed because of
a race in the test itself, fixed). A finding along the way: the same 504 when it is the **broker**
that closes the channel (passive declare of a nonexistent queue, 404) with a callback in flight — a path
the "cancel before closing" option alone did not cover.

Decision (the user's): both parts. (1) `Close` cancels the consumers (stops at the first
`Cancel` that fails), drains with the channel open and only then sends `Channel.Close`. (2) `FClosing`
under `FAckLock`, which `Ack`/`Nack` hold from the check until the frame goes out; turned on before
`Channel.Close` and, in a close by the broker, before the Close-Ok (on the read thread) — a silent
no-op, not an exception. A connection drop does not turn the flag on: `Ack` after it keeps raising
`EAMQPConnection`. `BeginRecover` turns it off.

Mutations: without the cancel+drain step, the 3 `Close`/`Free` tests fall (the delivery goes back to
the queue: its `Ack` was discarded by part 2). With `Ack`/`Nack` ignoring `FClosing`,
`FechadoPeloBroker_AckAtrasadoNaoDerrubaAConexao` falls on both brokers, and
`AckDepoisDoClose_NaoDerrubaAConexao` **only on the embedded one** (`504 method 60/80 on channel 1, which
is not open`): RabbitMQ tolerates the manual `Ack` even 300 ms after the Close-Ok, on a channel without
a consumer. Not investigated beyond that; acceptance covers it.

## v0.6.0 — TCP and TLS through pascal-common-faa 1.27.0 (2026-11-02)

Step 5 of the "Migration order" in pascal-common-faa's `docs/transport-design.md` (its decisions T1–T8).

## Mirror checker

*History below; the current state (five checks on the master, after the test kit) is in the section above and in `CLAUDE.md`.*

`tests\tools\verifica_espelhos.py` — runs **without a compiler** and checks the two things that only show up in the Delphi mirror, where each error costs a round-trip through the IDE: (1) code declared **after the `initialization`** (in Pascal a `procedure` there becomes a directive, `E2070` in dcc32); (2) **mirror parity** — every test declared on one side exists on the other, and every fixture **with tests** is registered. The second catches the silent defect: a new fixture not registered in DUnitX **gives no compile error**, it gives a green suite with N fewer tests. It exits with code 1 on divergence, so it can be tied to a hook. **Run it before sending the suite to the IDE.**

It has no exceptions list on purpose: the first version compared every `procedure` and required registration of every class, reported 7 divergences and all 7 were false positives — the fix was to use each dialect's exact discriminators (`[Test]`/`[TestFixture]` in DUnitX; `published` inside a fixture in FPCUnit, with transitive closure over inheritance, because the server fixtures descend from a common `TServerFixture` and not directly from `TTestCase`). Requiring registration only of a fixture **that declares a test** is what leaves a base class out of the count without opening a hole.

In Phase 3's WS5 it gained a **third check**: every unit of `src\server\` has to be listed in **every** `.dpr` that compiles the sub-module, and the sibling `.dproj` has to list the same ones. FPC does not catch this — there the units come from the **package**; in Delphi each project lists them one by one, and a missing one only shows up as `F2613 Unit not found` in the IDE. That is exactly what happened with `AMQP.Server.Header`: it went into the server suite's project in WS3 and was left out of the acceptance one, and the error only showed up in WS5, when `AMQP.Server.Queue` started using it.

The **six** mutations it has to catch (checked): registration removed, `procedure` after the `initialization`, test present on only one side, **DUnitX registration without the `TDUnitX.` prefix**, a `src\server\` unit missing from a `.dpr`, and a unit in the `.dpr` but not in the `.dproj`. The last one came in after the checker itself gave a false negative (Phase 3's WS3): the regex matched `RegisterTestFixture(X)` with or without the prefix, and considered a fixture registered in a file that `dcc32` refused with `E2003`. **The shape of the call matters, not just the name** — in DUnitX registration is a class method and `TDUnitX.` is mandatory; in FPCUnit `RegisterTest` is a free function.
